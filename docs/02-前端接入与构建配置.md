# 02. 前端接入与构建配置

返回核心思想：[构建与进程内绑定](核心思想.md#ask-frontend-build) · 相关细节：[ASK IR 与数值语义](01-ASK-IR与数值语义.md) · [外部产物与执行接口](04-外部产物与执行接口.md) · [工程结构与测试体系](06-工程结构与测试体系.md)

ASK 提供进程内 Python SDK（基于 `nanobind`）、独立 C++ 库（`ASK::Core`）以及命令行工具 `ask-opt`。

直接安装 wheel、从任意路径源码构建，以及把 SDK 和 worker 与源码目录分离的步骤见 [独立安装](安装.md)。

<a id="build-workflow"></a>

## 1. 依赖获取与 CMake 构建

锁定的 SDK 支持 Linux x86-64；构建需要 C++17 编译器、CMake 3.28+、Ninja 和 Python 3.10+（含开发头文件）。LLVM/MLIR（`23.0.0git` 指定提交）和 `nanobind`（`3.1.0`）锁定在 `cmake/llvm.lock.json` 与 `cmake/nanobind.lock.json` 中。其他平台没有随仓提供的 SDK 锁和 CI 验证。

```bash
python3 tools/fetch_deps.py
cmake --preset core
cmake --build --preset core
ctest --preset core
```

- `tools/fetch_deps.py` 默认准备 `llvm` 与 `nanobind`，支持 `--only llvm` 或 `--only nanobind`。脚本会校验归档 SHA-256、检查压缩包路径与软链，并在 `.deps/<dir>/` 下记录收据文件（`.ask-sdk.json` / `.ask-nanobind.json`），已就绪时直接复用。
- `CMakeLists.txt` 根据 `cmake/llvm.lock.json` 自动在 `.deps/` 下定位 `LLVM_DIR` 与 `MLIR_DIR`；使用外部同修订 LLVM 安装时可通过 `-DLLVM_DIR` / `-DMLIR_DIR` 覆盖。

将 ASK 安装到 Python 虚拟环境（默认核心构建）：

```bash
python -m pip install .
```

只有当前环境已安装 `pyproject.toml` 锁定的构建依赖时才使用 `--no-build-isolation`。第三方编译器环境独立配置，不参与 ASK 构建。

<a id="compiler-selection"></a>

## 2. 核心构建与外部 Worker

`CMakePresets.json` 只提供 `core` 预设，包含自有 CPU/CUDA 编译与运行时，不依赖 Triton、PyTorch 或 NumPy。`ASK_TARGET_BACKENDS` 可取 `host` 或 `none`，控制 Host 代码生成。

外部编译器由调用方通过 `CompilerEnvironment` 显式提供 worker 路径和可选 Python 解释器。配置与编译器 ID 不进入 CMake；FugaTensor 的 Triton 接入位于其自身安装包。详见[Worker 配置](04-外部产物与执行接口.md#worker-interface)。

<a id="python-sdk"></a>

## 3. Python SDK：进程内编译器与图构造

Python 接口位于 `python/ask/`，底层绑定为 `ask._native`（`bindings/`）：

```python
from ask import Compiler, Module, TensorType

module = Module()
t = TensorType((16,), "f32")
g = module.graph("axpy", inputs={"x": t}, results=[t])
two = g.splat(g.constant(2.0, dtype="f32"), (16,))
one = g.splat(g.constant(1.0, dtype="f32"), (16,))
g.return_(g.add(g.mul(g.inputs["x"], two, id="scale"), one, id="shift"))

compiler = Compiler()                 # 默认调用进程内 nanobind C++ 扩展
prepared = compiler.prepare(module)   # 类型/形状检查 + 标记提取擦除
optimized = compiler.optimize(module) # 常量折叠 + 死代码消除 + 逐元素融合分组
```

- **进程内调用与伴生 CLI 校验**：`Compiler()` 不传路径时在进程内创建独立 `mlir::MLIRContext` 执行 `prepare` 和 `optimize`。调用 `compile_cuda` 等依赖外部 CLI 的接口前，`Compiler._check_companion()` 会校验伴生 `ask-opt --capabilities` 与内存 `_native` 扩展的构建指纹一致。
- **CLI 模式**：传入 `Compiler("/path/to/ask-opt")` 切换到子进程 CLI 模式，返回相同的 `PreparedModule(ir, report)` 结构。
- **外部多输出**：`module.semantics(..., results=[...])` 声明各结果类型；`graph.external(..., result_types=[...])` 返回对应 `Value` 元组。只有一个结果时仍返回单个 `Value`，也可继续使用 `result_type=`。
- **Python 示例**：
  - `examples/framework_frontend.py`：构造 `P -> Triton F -> Q` 计算图并输出 `prepare` 报告。
  - `examples/optimize_frontend.py`：常量折叠、无用分支消除与多输出融合分组。

<a id="cpp-sdk"></a>

## 4. C++ 原生接入（`ASK::Core`）

C++ 宿主可通过 `find_package(ASK CONFIG REQUIRED COMPONENTS Core)` 链接 `ASK::Core`，调用 `include/ask/Frontend/Compiler.h` 中的 `ask::prepareSource` 与 `ask::compilerCapabilities`。直接持有 MLIR 模块时，可使用 `include/ask/Frontend/Prepare.h` 的 `ask::prepareModule` 和 `include/ask/Transforms/Optimize.h` 的 `ask::optimizeModule`，执行时无需初始化 Python。独立工程示例见 `examples/cpp/CMakeLists.txt` 与 `examples/cpp/frontend.cpp`。

序列化 `prepareSource` / `partitionSource` 的报告时使用 `ask::reportJSON(result.report, result.floatPaths)`，保留外部配置中的浮点类型与负零。LLVM 默认 JSON 输出会将 `1.0` 写成整数词法形式；`floatPaths` 只记录内部类型信息，不进入 worker 协议。CLI 与 Python 绑定共用此序列化入口。

<a id="cli-driver"></a>

## 5. `ask-opt` 命令行参数

| 参数 | 输入 → 输出 | 说明 |
| --- | --- | --- |
| `--capabilities` | 无 → JSON | 输出当前构建支持的后端、外部产物格式、元素类型与主机 `bf16` 硬件支持。 |
| `--prepare` | ASK MLIR → Prepared MLIR | 校验语义与形状、提取并擦除 `ask.mark`，配合 `--report-json` 输出准备报告。 |
| `--optimize` | ASK MLIR → Optimized MLIR | 在 `--prepare` 基础上运行常量/类型折叠、DCE 和逐元素融合分组（支持 `--no-constant-fold` / `--no-dce` / `--no-fusion`）。 |
| `--emit-llvm` / `--emit-object` | 纯自有 ASK MLIR → Host `.ll` / `.o` | 生成 CPU 共享循环 LLVM IR 或本机目标文件。 |
| `--emit-cuda-llvm` | 纯自有 ASK MLIR → NVPTX `.ll` | 按 `--cuda-arch <sm>` 与 `--cuda-block-size` 生成自有 CUDA kernel LLVM IR。 |
| `--partition` | ASK MLIR → 带 kernel 函数的 MLIR + 执行计划报告 | 校验、推导形状并优化后按外部边界切分；配合 `--report-json` 输出 `execution_plan` 与 `step_sources`，支持 `--no-optimize`，步骤仅为 `owned` 或 `external`。 |
| `--check-llir` / `--optimize-llir` | 原生 `.ll` → `.ll` | 验证或清理原生 LLVM IR（保留内联 PTX 与目标 intrinsic）。 |

<a id="version-contract"></a>

## 6. 版本契约与分发产物

不同版本字段描述不同边界，不应一起递增：

| 字段 | 当前来源与约束 |
| --- | --- |
| ASK 发布版本 | `python/ask/_version.py` 的 `__version__` 是唯一来源，当前为 `0.1.0`。CMake `project()`、`ASK_VERSION`、capabilities 的 `ask_version` 和 Python 分发元数据均读取它。当前格式为 `major.minor.patch`。 |
| C++ 包兼容性 | `ASKConfigVersion.cmake` 采用 `ExactVersion`；指定版本的 `find_package` 只接受同一版本，尚未承诺跨版本 API/ABI 兼容。LLVM/MLIR 还必须匹配 SDK 锁的版本、修订及同一安装前缀。 |
| 原生构建身份 | `build_id` 由构建目录、发布版本、LLVM 修订、Host 开关和 Python ABI 计算。它不包含源码内容哈希；同版本不能代替 CLI 与扩展的完整 capabilities 校验，也不能据此证明两次构建源码相同。 |
| 数据协议 | ASK IR 与报告 schema 为 `1`，外部 worker 协议和规范化 CUDA invocation 为 `2`。这些字段各自校验，不表示 ASK 包或适配器版本。 |

`Compiler()` 会拒绝 Python 源码与原生扩展的版本不一致。需要伴生 `ask-opt` 时，还会比较双方完整 capabilities。显式 `Compiler(executable=...)` 保留 CLI 接入方式，不加载原生扩展。CMake 配置 wheel 时也会拒绝 Python 分发版本与原生发布版本不一致。

`pyproject.toml` 记录包名 `ask-compiler`、Python 下限、README 和 Linux/Alpha 分类。仓库尚未声明许可证和公开项目地址，因此元数据中也未填写。wheel 包含 Python SDK、原生扩展、伴生 CLI 及 C++ 安装文件，不携带 LLVM SDK、Triton、GPU 驱动或 `ptxas`。本机 wheel 未经过 manylinux 修复，也不表示可在任意 Linux 发行版运行；CUDA 编译和执行仍需对应外部工具及驱动。

在仓库根目录准备好 SDK 后，可以构建源码包，再由源码包构建 wheel：

```bash
python -m pip install build==1.3.0
sdk="$(python -c 'import json, pathlib; print((pathlib.Path(".deps") / json.load(open("cmake/llvm.lock.json"))["directory"]).resolve())')"
python -m build --outdir dist \
  -Ccmake.define.LLVM_DIR="$sdk/lib/cmake/llvm" \
  -Ccmake.define.MLIR_DIR="$sdk/lib/cmake/mlir"
python tools/check_metadata.py --dist-dir dist
```

`tools/check_metadata.py` 检查版本、依赖锁、README 元数据及核心包内容，产物目录应只包含本次的一份 sdist 和一份 wheel。Python 3.10 运行该检查需要 `tomli`（上述 `build` 环境会安装它）。源码包保留构建文件、依赖锁和获取脚本，排除 `.deps/`、`build/`、`dist/`、虚拟环境和缓存；离开仓库构建时必须重新获取依赖或像上例传入外部 SDK 路径。

自动检查与隔离安装执行见 [CI 与分发验证](06-工程结构与测试体系.md#continuous-integration)。工作流生成检查产物，不上传包索引或创建发布。
