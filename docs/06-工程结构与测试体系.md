## 1. 仓库目录结构

```text
ask/
├── CMakeLists.txt / CMakePresets.json / pyproject.toml
├── .github/workflows/ci.yml # Linux CPU 构建、契约检查与安装验证
├── cmake/                  # LLVM / nanobind 锁文件、可选适配器白名单与 CMake 包导出模板
├── tools/
│   ├── fetch_deps.py       # 拉取与校验锁定版 LLVM/MLIR SDK 和 nanobind 源码
│   ├── ask-opt.cpp         # 原生命令行编译驱动
│   ├── check_metadata.py   # 检查版本单源、依赖锁与 sdist/wheel 元数据
│   ├── run_ci_tests.py     # 运行 CPU CTest 并拒绝缺失或跳过的测试
│   └── smoke_wheel.py      # 隔离安装环境中的编译器与 CPU 执行冒烟
├── include/ask/            # 公共 C++ 头文件（IR、Frontend、Transforms、Lowering、LLIR、Adapters、Runtime）
├── lib/                    # 公共 C++ 实现（ask_core、ask_compilers、ask_runtime）
├── bindings/               # nanobind 进程内 Python 扩展（ask._native：编译器桥接与常驻 CUDA 会话）
├── python/ask/             # Python SDK（IR 构造器、Compiler、双层缓存驱动、运行时封装）
├── adapters/
│   ├── registry.json       # 允许构建的第三方编译器名录
│   └── triton/             # Triton 3.7.1 适配器（worker、AST/标记融合、C++ 边界校验与专属测试）
├── examples/               # Python 与独立 C++ 接入示例
├── tests/                  # 单元测试、物理 GPU 测试、IR 夹具与共享数值参考库
└── docs/                   # 架构与工程文档
```

`.deps/`、`build/` 和编译运行缓存由 `.gitignore` 排除在版本库之外，依赖版本通过 `cmake/*.lock.json`、`adapters/*/dependencies.lock.json` 与 `tools/fetch_deps.py` 锁定。

## 2. 五个 CTest 测试集与运行方式

执行 `ctest --preset core`（前 4 项）或 `ctest --preset all`（全部 5 项）时运行以下目标：

| CTest 名称 | 入口位置 | 覆盖范围 |
| --- | --- | --- |
| `ask-compiler-adapter` | `tests/cpp/test_compiler_adapter.cpp` | C++ `CompilerAdapter` 注册表、白名单隔离与未知编译器拒绝。 |
| `ask-boundary-inline` | `tests/cpp/test_boundary_inline.cpp` | C++ 通用 LLVM 值边界内联核心（多参数、多站点、定长向量、非法 helper 与支配违规回滚）。 |
| `ask-unit` | `tests/test_*.py` | 纯 CPU 单元测试：SDK 与单步 RNE 常量、`ask` IR 正反例校验与高层图优化、Host CPU 代码生成执行、自有 CUDA 降级与启动契约离线校验、缓存并发/损坏恢复与 CAI 描述符校验、6 种精度边界参考值，以及 `fetch_deps.py` 解压与 CMake 白名单测试。 |
| `ask-gpu` | `tests/gpu/test_gpu_*.py` | 物理 NVIDIA GPU 测试（缺少驱动或 `ptxas` 时跳过）：`test_gpu_native.py` 验证自有 CUDA 全精度、6×6 转换、异构多端口、ABI v2 共享内存、零拷贝重复提交与并发流；`test_gpu_triton.py`（启用 `triton` 构建时）验证 `ASK → Triton → ASK` 融合、FMA 隔离、双层缓存命中与跨会话 `__cuda_array_interface__` 串联。 |
| `ask-triton` | `adapters/triton/tests/test_*.py` | 启用 `triton` 适配器时注册：检验 `worker.py` 导出协议、AST 静态融合判定、Python 策略与旧产物迁移，以及不依赖物理 GPU 的 `ask-opt --fuse-external` LLVM 融合与防篡改校验。 |

单独运行某组测试：

```bash
# 运行纯 CPU 单元测试
PYTHONPATH=build/core/python:python:tests ASK_OPT=build/core/bin/ask-opt \
  ASK_BOUNDARY_INLINE_BIN=build/core/ask-boundary-inline-test \
  python3 -m unittest discover -s tests -p "test_*.py" -v

# 运行 GPU 硬件测试（core 测自有 CUDA，all 同时测自有 CUDA + Triton 融合）
ctest --preset all -R ask-gpu --output-on-failure
```

`tests/gpu/` 不放置 `__init__.py`，使顶层 `unittest discover -s tests` 仅发现纯 CPU 单测模块，物理 GPU 编译执行留给 `ask-gpu`。

<a id="matrix-and-reference"></a>

## 3. 共享多精度测试矩阵与独立数值参考

`tests/support/` 提供各后端共用的数值参考与图矩阵：

1. **精确数值参考（`tests/support/pointwise.py`）**：用 Python 任意精度整数实现 IEEE-754 单步最近偶数舍入（RNE）、次正规数（subnormal）sticky bit、`fma` 单次舍入对比、32/64 位二补数回绕以及饱和 `cast_reference`。测试样本覆盖 `2**60 + k`（检验 64 位整数高位与低位精度）、`f16`/`bf16` 半 ULP 舍入边界、`-0.0`、`±inf`、`NaN` 以及非整块尾元素（如 `size = 129`）。
2. **矩阵规划器（`plan_matrix`）**：同一套图拓扑定义（多维形状、多标记站点、`F` 开启/关闭浮点收缩、混合精度 `f32` 中间累加等）在 Host CPU、自有 CUDA 和 Triton 融合测试间复用，按 dtype 与图拓扑正交去重。

## 4. CI 定义与验证边界

[GitHub Actions 工作流](../.github/workflows/ci.yml)在 `push`、`pull_request` 和手动触发时使用 Ubuntu 24.04 x86-64，定义三组构建：

| 构建 | Python | 验证内容 |
| --- | --- | --- |
| `core` | 3.10、3.13 | 源元数据、两个 C++ 测试集、`ask-unit`；从 sdist 构建 wheel，并在新虚拟环境中安装执行。 |
| `all` | 3.13 | 同样的 CPU 测试，加 `ask-triton` 的真实 Triton 导出、LLVM 内联和拒绝路径测试；不要求物理 GPU。 |

工作流只缓存锁文件对应的 LLVM 压缩归档，每次仍由 `fetch_deps.py` 校验 SHA256 并解压。构建固定使用两个并行任务，避免静态链接 LLVM/MLIR 时耗尽托管 runner 内存。

[run_ci_tests.py](../tools/run_ci_tests.py)明确选择 CPU 测试集，检查 CTest 的 JUnit 报告：缺少预期测试集、Python 未发现测试、CTest 失败或 `unittest` 内部跳过都使检查失败。这里没有运行 `ask-gpu`，因此绿色结果不代表 CUDA 驱动、设备执行或零拷贝行为已经通过硬件验证。物理 GPU 检查仍需在具备驱动与工具的环境中运行：

```bash
ASK_REQUIRE_CUDA_DEVICE=1 ctest --preset all -R '^ask-gpu$' --output-on-failure
```

`core` 的打包步骤先生成 sdist，再从该 sdist 构建 wheel。LLVM SDK 不进入发布包，构建时通过显式路径指向已校验的 SDK。[check_metadata.py](../tools/check_metadata.py)检查源码和产物契约；[smoke_wheel.py](../tools/smoke_wheel.py)以新虚拟环境的 `python -I` 运行，检查 Python、发行元数据、原生扩展与随包 `ask-opt` 的版本和能力一致，并编译、链接、执行一个包含 i32 溢出回绕的 CPU 图。Python 3.13 的 `core` 作业还将 CMake 包安装到临时前缀，再独立构建、执行 [C++ 示例](../examples/cpp/frontend.cpp)。

测试报告与构建产物保留七天供检查，工作流不上传 PyPI 或创建发布。工作流文件本身不证明远端运行成功；实际结果以对应提交的 Actions 记录为准。Python 3.10 和 3.13 是这里配置的验证版本，包元数据中的 `>=3.10` 也不表示每个更新版本都已经验证。版本兼容规则见 [版本契约与分发产物](02-前端接入与构建配置.md#version-contract)。
