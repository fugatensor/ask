# A 层：把计算图整理成可以降级的输入

[返回顶层设计：A 层](核心思想.md#ask-a) · [文档索引](README.md)

本文说明 A 层准备怎样实现。先看一条贯穿后续阶段的计算链，所有加乘都按 i32 位模式计算，溢出后取模 2^32：

```text
P: t[i] = x[i] + 1
F: u[i] = t[i] * 2    # 外部编译器提供实现
Q: y[i] = u[i] + 3
0 <= i < N
```

A 层收到的是“先算 t，再算 u，最后算 y”。它要把这句话补全：每个值是什么类型，F 究竟做什么，谁还会使用 t，以及哪些操作不能移动。补全后的图叫 `SemanticModule`；执行分组、参数连接和依赖顺序放在 `RegionPlan` 中。B 层拿到两者就能开始准备正常执行；只有启用某项优化时，才额外提出它需要的候选和分析请求。

## 1. 先确定这次交给 ASK 的图

上层框架负责生成基础 ASK IR，可以使用 ASK 的 builder，也可以在框架侧将自己的 IR 转成 ASK IR。A 层接收这份已表达操作和数据连接的 ASK IR，不承担任意上层 IR 的前端转换。类型和约束仍需检查，不能因为图来自某个框架就跳过。

第三方计算以 `ask.external` 标出，框架同时提供对应编译器的 DSL、语义和实现引用。A 层按语义推导形状，B 层再编译该 DSL。具体操作与输入包见[ASK IR 定义](ask-ir/00-结构类型与操作.md#external)，这里继续说明处理顺序。

图的操作和连接关系必须在编译时确定。上面的 P/F/Q 可以有多个输入、分叉和汇合，但不能包含“运行时看 x 的值再决定执行哪个子图”的节点。这种分支以及图级循环由上层框架处理，再调用选中的 ASK 图。

这不禁止 F 的实现内部使用循环，也不禁止 B 层为 `0 <= i < N` 生成循环和尾部判断。A 层只需知道这个算子的结果和读写行为；B 层把自有和外部实现整理为原生 LLVM IR 后，再由启用的 Pass 查询所需信息。

本例先取一个确定的 N，例如 10。输入 x 是只读的 i32 数组，y 是单独的输出数组，t/u 不返回给调用方。编译请求还会指定 `TargetProfile`，即本次生成代码的目标；它不改变这里“加一、乘二、加三”的含义。

## 2. 查清每个操作的含义，再考虑它的实现

只有名字 `F` 不够。A 层用操作的 `semantic_key`——命名空间、名称和版本——查询注册表。本例中，F 的描述需要说明：输入一个 i32 张量，输出相同形状的 i32 张量，对每个元素执行模 2^32 的乘二，不改输入，也不读写额外状态。

注册表里的描述与编译实现分开。前者让 A 层检查程序，后者告诉 B 层找哪个适配器生成 F。一个操作可以有多个实现，但这次选中的 F 实现及其配置要记下来；后续融合不能要求它换分块、布局或执行顺序。

A 层不解析 F 的 DSL 算法，只检查语义和实现引用；图编译请求仍要提供或按摘要引用对应 DSL，由 B 层路由编译。某个配置若只能导出合法可调用产物，可以保留独立执行，但不算原生 LLVM 接入成功。若注册表不知道它会不会写外部状态，就记为未知，不能当成没有额外行为。

这里还要固定数值规则。本例不能给加乘附加“不会溢出”的假设。换成浮点操作时，要另说清精度、舍入、NaN、有符号零，以及是否允许改变求值顺序或收缩乘加。若未允许重结合，后续就不能把 `(a+b)+c` 改成 `a+(b+c)`。归约还要说明累加类型和允许的求值次序。这些设置组成 `NumericPolicy`，随图传下去。

同一个语义版本出现互相冲突的定义、实现引用不存在的操作，或描述引用了不存在的输入端口，都在这一步报错。注册表版本也要随图保存，避免缓存把旧语义的产物当成新语义的实现。

## 3. 沿着 x、t、u、y 检查类型和形状

现在知道 P/F/Q 各自做什么，可以从输入开始推导。x 的类型为 `tensor<10xi32>`，P 输出 t 的类型仍然是 `tensor<10xi32>`；F、Q 同理。如果 F 声明输出 9 个元素，Q 却需要 10 个，这张图不能进入降级。

常量 1、2、3 的用法也必须明确。本例把它们作为逐元素算子的标量参数。若以后支持两个张量之间的广播，操作描述必须给出维度如何对齐、哪些长度允许广播，以及输出位置对应哪个输入位置，不能继承某个上层框架没有写明的默认规则。

逻辑形状和存储方式分别记录。若 x 是一个 view，A 层还需保留它的起始偏移和 stride；`x[i]` 不一定就是 `base + i*element_size`。B 层需要这些信息生成地址，但 A 层此时不决定第 i 个元素由哪个线程或向量 lane 处理。

N=0 是合法形状，不能因为没有元素就让后续访问一个占位地址。计算元素数量、字节数和 stride 时也要检查整数溢出；检查通过前，不能把这些结果拿去分配或做地址计算。

首版要求形状在编译前给定。遇到尚未具体化的 N，返回明确的“不支持未具体化形状”，由调用方提供尺寸后再编译。以后可以在同一张静态图上支持符号维度：例如记录 `M >= 0`、两个输入的某一维相等，再由求解器返回已证明、矛盾或未知。求不出来不等于条件成立，也不意味着要在 A 层加入动态分支。

将来加入调用前检查时，还需区分两类条件。尺寸不满足操作要求，属于输入错误；尺寸满足操作要求，只是不满足某个融合方案的整除条件，则选择其他合法版本。检查必须发生在该方案的访问和副作用之前，不能先执行一半，再重跑未融合版本。具体尺寸及所采用的假设都要进入缓存键。

## 4. 给值编号，列出它们的全部使用者

类型检查完成后，给 x/t/u/y 分配稳定的 `ValueId`，例如 `v_x/v_t/v_u/v_y`。这些编号表示逻辑值，不是地址。打印 IR 时 `%3` 变成 `%8`，不应影响编号。

P 的输出位置和 F 的输入位置分别有 `PortId`。它们虽然连接着同一个 `v_t`，却承担不同角色：正常调用时，要把 P 的输出 buffer 接到 F 的输入参数；如果以后启用访存优化，还要继续定位“P 在哪里写出 t”和“F 在哪里读入 t”。编译分组再用 `RegionId` 标识。前一种参数连接是执行所需信息，后一种指令级追踪按需建立，详见[跨层追踪](02-跨层身份与追踪契约.md)。

接着建立使用者列表。本例得到 `uses(v_t) = {F.in}`、`uses(v_u) = {Q.in}`。如果图里还有 `R(t)`，列表必须包含 R；如果 t 是函数返回值，也算一次不能丢掉的使用。后续决定能否删除 t 的中间存储，就是查这份列表，而不是只看 P/F/Q 这一条链。

张量更新产生新的逻辑值。若程序确实要原地写某块存储，就用明确的 buffer 读写来表示，而不是让同一个 `ValueId` 悄悄变成另一份数据。两个逻辑值最终是否复用同一块内存，留给后面的存储分配；A 层不能从编号不同推断地址不同。

## 5. 补上数据连线没有表达的顺序

本例的数据边已经要求 P 在 F 前、F 在 Q 前。但换一个 F：它除了计算 u，还会更新随机数状态，或者写一条日志。这些行为没有出现在 t/u 的连线上，如果只按数据边排序，就可能把它移错位置或执行两次。

因此每个操作还要报告读、写、分配和释放了哪些 buffer 或状态。对可能冲突的访问，按上层声明的程序顺序加顺序边。在 ASK IR 中通过效果 token 表达，分组后写入执行依赖表，降级时继续携带。内部有分支的 F，需要报告所有可能路径上的行为。token 及其验证规则见[效果顺序](ask-ir/00-结构类型与操作.md#external)。

这里还需要查别名，即两个入口是否可能指向同一块存储。本例明确要求 x 和 y 分离；一般情况下，两个 buffer 参数不能仅因名字不同就当成不重叠。分析结果可以是确定相同、可能重叠或确定不重叠。view 的两个范围是否分离，要由偏移和长度算出来。若中间调用可能改写 t 所在的存储，就不能继续把 P 的输出当成 F 一定会读到的值。

“没有写内存”也不等于“可以任意移动”。例如除法可能只在除数非零时有定义，调用可能不返回。删除、复制和提前执行操作之前，还要检查这些条件。A 层若用 MLIR 承载图，可以复用它的内存效果和可推测执行接口；这些图级结果仍需明确传给后续阶段，不能假定 MLIR 属性会自动成为原生 LLVM IR 的分析结果。[MLIR Side Effects & Speculation](https://mlir.llvm.org/docs/Rationale/SideEffectsAndSpeculation/)

到这里，`SemanticModule` 才完整：它保存操作及语义版本、值类型、使用者、数据与状态依赖，以及数值规则。保存操作的源位置，是为了出现“F 的结果形状与 Q 不匹配”时能指出原图中的位置。

## 6. 先把正常执行的分组交出去

规划从 `[P] [F] [Q]` 开始。P 写 t，F 等 P 完成后读 t 并写 u，Q 等 F 完成后读 u。`RegionPlan` 记录这三个分组、端口连接及完成依赖；B 层再为每组准备实现，后端确认参数、目标代码和启动方式都能兑现。

这条路径不需要先证明 P/F 能传递 SSA 值，也不要求给出 F 内部每次读取的逻辑索引。完整访存追踪是某些优化的输入，不是普通调用的准入条件。F 的原生 LLVM IR 中即使保留 inline PTX 或目标 intrinsic，只要整个实现符合已声明的行为，并被所选后端支持，就可以继续准备执行；A 层不负责把这些目标指令全部翻译成自己认识的算子。

首期真实外部实现只接 Triton。框架提交的实现引用关联编译器和 DSL，B 层通过统一的 `export(request) -> LLIRArtifact` 请求编译并取得产物；语义和参数绑定仍与 A 层的端口连接对应，具体接入内容见[第三方 LLIR 接入 API](08-第三方LLIR接入API.md)。

F 的已选实现和配置随计划保存。以后启用融合时，只能尝试调整 P/Q 来配合 F，不能要求 F 换一种调度，也不能要求外部编译器修改源码或开放私有阶段。

即使图是 `F1 → P → F2`，三者执行方式不同也不自动造成接入失败：原始分组可以通过约定的 buffer 和完成依赖交换数据。只有准备合并它们时，才需要证明执行方式能够配合。

## 7. 启用优化后，再提出它要回答的问题

如果本次启用了融合 Pass，再沿图检查相邻区域。本例 P/F/Q 都是同一索引域上的逐元素计算，t/u 只被下一项使用，可以提出 `[P,F]`、`[F,Q]` 和 `[P,F,Q]` 三个候选。候选数量与区域大小设上限；关闭融合时，不必做这项枚举。

A 层知道“F 需要 t 的第 i 个元素”，还不知道哪个低层执行实例产生它。融合 Pass 因而请求边界访问分析，逐项检查：F 每次读取是否有对应写入，P 的值能否在 F 使用的位置提供，删除写出后是否还有其他使用者，以及原来的读写顺序是否保持。这些尚待证明的问题称为 `ProofObligation`。

问题没有答出来，就不采用依赖它的改写，仍使用前面准备的正常分组。不能把“F 已成功接入”当成“F 的每一处访存都已经能优化”。其他 Pass 也各自声明需要什么；例如只检查入口签名的 Pass 不需要完整元素映射，删除中间 store 的 Pass 则必须查清全部可能的读取。

若 F 是归约，融合候选使用它实际的索引关系，不能沿用本例的一对一对应。若两个外部实现要求冲突，拆开候选，选择一侧融合或都不融合，不修改 F1/F2。候选依据索引、使用者和读写信息产生，不依据某个模型的常见形状猜测正确性。

候选可以互相重叠，最终执行分组不能重叠。选择 `[P,F]` 后，不能再同时执行 `[F,Q]`，否则 F 被执行两次。要么执行 `[P,F] [Q]`，要么选择另一个完整分区；复制计算若以后确有需要，应作为单独变换证明。合法方案是否值得采用，由 [C 层的相应 Pass](04-C层统一处理与可选优化.md)继续判断。

## 8. 在交接前检查引用是否还对得上

图在规范化时可能被改写，例如删除无用操作或合并相同计算。每次改写都要更新值和端口的对应关系，并使旧的使用者、别名和规划结果失效。`SemanticModule.revision` 标明图的版本；`RegionPlan.semantic_module_revision` 必须与它一致，否则不能继续用旧计划。

退出 A 层时，检查所有操作都能查到语义，类型和形状没有矛盾，全部数据及状态依赖仍在，每个需要执行的操作都出现在正常执行分组中。只把 F 标记为“未知读写”可以继续按原顺序编译；连 F 的签名都不知道则不能继续。

测试可以直接从本例改起：把 F 的输出长度改错，应在 A 层报错；增加 `R(t)`，计划必须保留它对 t 的使用；让 F 更新状态，计划必须保留状态顺序；增加图级运行时分支，应要求上层处理。N=0 和 i32 溢出输入则应仍按已声明的语义通过。

通过这些检查后，将 `SemanticModule`、`RegionPlan` 和端口身份交给 [B 层](03-B层多源降级与低层归一化.md)。若启用的 Pass 请求更细的信息，再按[跨层身份与追踪](02-跨层身份与追踪契约.md)从原生 LLVM 的指针、访存和向量值中找回逻辑元素；未建立这项分析不妨碍原始分组执行。
