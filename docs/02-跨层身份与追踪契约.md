# 跨层追踪：优化需要时，怎样从 LLVM IR 找回逻辑值

[返回顶层设计：跨层追踪](核心思想.md#ask-architecture) · [文档索引](README.md)

本文说明拟议的追踪实现，继续使用 A 层的例子：`P: t=x+1`、`F: u=t*2`、`Q: y=u+3`，每一步均按 i32 模 2^32 计算。

A 层知道 F 读的是 t。B 层接收的 ASK LLIR 是原生 LLVM IR，解析后得到 `llvm::Module`；其中的 `Function`、`Instruction` 和 `Value` 描述具体代码。只要参数绑定、目标和代码生成都成立，这份代码就可以独立执行，不需要先恢复每条指令对应哪个高层元素。

本篇处理额外的一步：某个 Pass 想把 F 的读取换成 P 算出的值时，怎样找回“这次读取对应哪一次写入”。它是按需运行的分析，不是接入检查的必经步骤；结果只供声明需要这些信息的 Pass 使用。

高层 `ask.external` 声明第三方计算边界并关联其 DSL；纯追踪操作 `ask.mark` 只提供站点线索。两者的定义、插入和清除规则见[ASK IR 标记算子](ask-ir/01-标记算子与追踪.md)。形状和正常调用通过独立绑定保留，不依赖标记存活。

## 1. 先把“哪个值”和“哪个地址”分开

四种编号解决四个不同问题。本例中：

| 编号 | 它让后续代码查到什么 |
|---|---|
| `ValueId = v_t` | 高层的逻辑张量 t，以及谁使用它 |
| `PortId = P.out / F.in` | t 从哪个输出产生，又从哪个输入进入 F |
| `BufferId = b_t` | 当前存放 t 的分配或外部绑定 |
| `RegionId = r_P / r_F` | 当前计划把相应操作交给哪个编译区域 |

P.out 和 F.in 连接同一个 `v_t`，却不能用一个端口编号代替。后续要分别检查写出和读入。`b_t` 也不能代替 `v_t`：同一块内存可能先存 t，后来被复用来存别的值。

这些编号在编译单元内唯一，并能写入文件。不能拿对象地址或 LLVM 打印出来的 `%0` 当编号，否则重载文件或插入指令就会失去对应关系。进程内的 `IRReference` 可以绑定当前模块中的 `Value`；写入文件时，改为产物内容摘要、函数/参数身份及快照内的指令定位信息。重载后先核对内容，再重新绑定，不能把旧指针拿到新 `LLVMContext` 中使用。

## 2. 在降级入口记下端口，出口再找到访问

ASK 自己降级 P 时，知道 P.out 对应哪个结果或输出参数。处理 F 时，先从接入产物中的调用说明找到 F.in 对应哪个 LLVM 参数；如果启用的 Pass 需要访问关系，再从该参数沿定义—使用链查找。参数绑定是正常调用所需信息，内部逐条访问的映射则可以缺省。

完整关系放在随模块保存的独立表 `BoundaryMap` 中，IR 里可以附简短的 metadata 引用帮助定位。这样一条向量访问可以关联多个逻辑元素，一个逻辑值也可以关联多条访问，不必把长表达式全部塞进指令。

首期由 Triton 适配器通过公开接口导出产物，第三方入口统一为 `export(request) -> LLIRArtifact`。外部编译器若提供公开的 Pass 扩展点，可以在那里补充映射；若只提供原生 LLVM IR，就在 ASK 导入后按需分析。不能要求提供方修改源码或使用私有钩子来补齐追踪。

原生 LLVM 模块可以完整接入，而 `BoundaryMap` 为空或只覆盖部分边界。只有可调用产物、没有 LLVM IR 的实现也可以按调用执行，但不进入指令级 Pass。是否接入、是否可以执行、某个 Pass 是否获得所需信息，分别判断，不用一个 `fusion-ready` 标志包办三件事。

LLVM 优化不能保证替 ASK 传播自定义标记：不能识别或无法保持的指令 metadata attachment 会被丢弃。模块级 named metadata 通常应保留，但这也不保证其中记录的元素对应关系在指令改写后仍然正确。因此表中的版本和重新分析不可省略。[LLVM Metadata](https://llvm.org/docs/LangRef.html#metadata)

F 本身的执行策略也在这里固定。下面对 F 内部的分析只是为了找到数据，不能借此改变它的分块、遍历或同步方式；需要调整的是 ASK 自己的 P/Q。

## 3. 从地址算回逻辑元素

先看连续存储的本例。若每个 i32 占 4 字节，P 的某次写入和 F 的某次读取可能分别使用：

```text
P: address = base(b_t) + 4*i
F: address = base(b_t) + 4*j
```

追踪从已知的输出参数或分配出发，给它标上 `b_t`。沿 LLVM 定义—使用链走到 `getelementptr` 时，按模块 `DataLayout` 计算字节偏移；走到 load/store 时，记录访问字节数和算出的逻辑索引。只有进一步证明 `i == j`，才知道它们访问同一个元素。相同 base 还不够。

原生 LLVM 的不透明指针 `ptr` 不携带元素类型。访问 i32 还是 i64，要读 load/store 自己的类型；GEP 则使用它的源元素类型。不能因为两个访存的指针相同，就把不同宽度的读写当成同一个值。[LLVM Opaque Pointers](https://llvm.org/docs/OpaquePointers.html#migration-instructions)

遇到 view，地址还要包含起始偏移和 stride。广播 view 可能让多个逻辑位置读同一个存储位置；负 stride、零 stride 和非连续布局也不能套用上面的 `4*i`。索引表达式只处理当前实现能准确解释的形式，首版可以从简单仿射表达式开始。

指针 cast 也不能一律当成无事发生。地址空间转换、指针转整数再转回指针，需要目标说明其含义；解释不了就返回 `unknown`。地址表达式要保存地址空间和索引位宽，后者不一定与指针表示宽度相等。不能通过覆写 `DataLayout` 字符串让一段已有代码适应不同目标；布局改变后，相关地址分析也必须重算。[LLVM Data Layout](https://llvm.org/docs/LangRef.html#data-layout)

如果 P 一次处理 W 个元素，低层结果是向量，映射还要多一维：

```text
logical_index = q*W + lane
valid = 0 <= lane < W AND q*W + lane < N
```

例如 N=10、W=4，最后一次计算只有 lane 0、1 对应有效元素。不能只记“这个向量来自 t”，还得记每个 lane 对应哪个 i，以及何时有效。F 若使用另一种分组方式，就用两边的索引关系逐项对齐；不能仅凭向量宽度相同判断。

这时得到的 `IndexRelation` 连接逻辑元素、低层执行实例和向量 lane。启动配置足够让原代码运行，却未必说明每个逻辑元素归哪个实例处理；融合若需要这种详细执行映射，必须另行提供或从当前代码证明。高层分块和调度信息在降级后可能已经不存在，不能仅凭拿到了 LLVM IR 就假定能够还原。

## 4. 再查 F 读到的是哪一次写入

即使地址相同，也还没找到可转发的值。假设 P 写完 t 后，一个调用又改了 t，F 读到的就是后一次写入。直接把 F 的 load 换成 P 的计算结果会出错。

所以每次访存都记录成 `AccessEvent`，包含读或写、字节范围、掩码和执行位置。对 F 的读取，分析沿数据与执行顺序查找可能到达它的写入；遇到可能重叠的写入或未知调用，就把它加入候选，不能继续假定 P 是唯一来源。

这里要使用 A 层的别名结果，并结合低层实际地址。两个指针可能重叠、地址传给了未知调用，或者存储在不同循环迭代里被反复写入，都可能改变答案。同一个 `BufferId` 只说明存储对象相同，不说明内容从未变过。

找到唯一的生产写入后，还要检查掩码覆盖。F 每次实际读取的位置，P 都必须实际写过。如果 F 的某个 lane 有效而 P 对应 lane 无效，就不能转发。inactive lane 若有指定填充值，也要保留这个值，不能随便接上一个未定义结果。

普通读写、volatile 访问和原子访问分别记录。即使算出的数值一样，删除 volatile 访问或原子操作仍可能改变程序行为；首版直接拒绝这类边界的融合即可，不把它们当成普通 load/store。

inline PTX 和目标 intrinsic 可以原样留在模块中，由目标后端处理。若它们参与当前访问链，而本分析不知道其读写、同步或指针捕获行为，就把这些影响记为未知。未知可能覆盖整块存储甚至整个候选区域，不能只跳过这一条指令便继续删除前后的访存。其他 Pass 是否仍能运行，要看它读取和改写的对象是否受这些影响；不存在“所有 Pass 都能绕过不认识的代码”的承诺。

至此，一个 `BoundaryEntry` 才有实际用途：它把 `v_t / P.out / F.in` 连接到低层定义和访问，附上逻辑索引、地址、掩码以及可能的写入来源。C 层需要的是这组关系，不是 `ValueId -> pointer` 的简单字典。

## 5. 分支和循环出现时，把路径也带上

这里处理的是降级后或 F 实现内部的控制流；A 层仍然只接收静态控制图。比如 F 的地址在两条路径间选择：

```text
p = select(cond, base + 4*i, base + 4*j)
```

它不能被记录成无条件读取 `t[i]`。关系应是 `cond` 成立时读 i，否则读 j。LLVM 的 `PHINode` 同样按每个前驱块及其输入值保留路径，除非已经证明所有来源对应同一个元素。

循环还要区分迭代。第 k 次迭代访问同一地址，不代表它读到第 k-1 次迭代之前的内容。分析需要跟踪迭代变量和写入之间的关系；可以使用 LLVM 的循环、支配与内存分析辅助判断，也可以先只支持直接能求解的简单循环。达到分析预算仍得不到答案，就标记未知，停止依赖它的改写，正常调用路径仍然存在。

这决定了映射必须允许多对多。一个高层值可能被展开成多个低层定义；多个来源经过公共计算合并，也可能指向一个低层值。合并来源列表只是记录历史，不能代替“它们数值等价”的证明。

## 6. IR 改写后，旧关系不能继续照用

假设先得到 `i = q*4 + lane`，之后又把 P 改为宽度 8。原来的映射看起来仍有变量 q 和 lane，但已经错了。向量化 Pass 必须重新写成 `i = q*8 + lane`，并更新有效掩码；只把旧属性复制到新操作上没有用。

其他改写按同一原则处理。循环展开产生多个副本，要为各副本加迭代范围；公共计算合并要合并来源并保留各自条件；存储复用要更新 `BufferId`、生命周期和写入事件；删除指令后要移除悬空引用。若某个 Pass 不能更新关系，就将受影响部分标为失效，等真正需要它的 Pass 请求重算。

LLVM 的 `ValueHandle` 可以跟踪对象删除或 RAUW（把某个值的所有使用替换为另一个值）。但它只能帮助找到对象，不能证明新值仍对应同一个逻辑元素，也不会自动解释原地修改的索引。克隆和内联时应保存旧 `Value` 到新 `Value` 的对应关系，再更新表；能直接利用 `ValueToValueMapTy` 的操作使用它，不能取得完整对应关系时重新分析。[ValueHandle](https://llvm.org/doxygen/ValueHandle_8h_source.html)、[ValueMapper](https://llvm.org/doxygen/ValueMapper_8h_source.html)

链接多个模块也会改变函数、全局变量和局部对象。先为各产物区分命名空间，记录入口和依赖符号如何合并或改名，再重新绑定映射；不能只拿旧函数名查找。链接不是融合，链接成功也不表示原有访问证明仍然有效。链接后若不能可靠更新关系，就先丢弃可选映射，再按当前模块重建。

ASK 自有 Pass 和公开扩展点内的适配器 Pass 可以显式完成这些操作。外部管线里的其他 Pass 只有在公开机制保证关系仍有效，或者出口重建成功时，才能继续信任映射。不能因为没有收到“失效通知”就认定它没变。

映射按版本绑定到 IR：

```text
BoundaryMap {
  schema_version
  semantic_module_revision
  lowered_ir_revision
  entries
}
```

`schema_version` 用于读取序列化格式；另外两个版本分别锁定高层图和低层代码。引用的对象、假设或布局发生改变，相关映射及融合证明就要更新或失效。IR 和表一起提交；变换失败时一起恢复，不能留下新代码配旧表。

LLVM Pass 返回的 `PreservedAnalyses` 要与 ASK 的映射依赖对应。改了某个函数的地址计算，依赖它的跨区域表不能因为自己存放在模块层就继续有效。处理任意不认识 ASK 映射的优化 Pass 时，默认使受影响映射失效，而不是要求这个 Pass 自动理解 ASK 的 metadata。

## 7. Pass 读取分析前，分清“知道多少”和“是否过期”

条目里的 `precision` 表示本次分析知道多少：`exact` 是在列明条件下精确对应；`conservative` 是列出了全部可能来源；`unknown` 是无法给出足以继续分析的关系。这和版本是否有效是两回事：旧版本的 exact 不能使用，当前版本的 unknown 则是一次正常的分析结果。

每个边界还要记录覆盖范围。没有出现在表里的读取不能被当成不存在，否则漏记一条 load 就可能错误删除它需要的写入。部分边界能追踪、其他边界未知时，可以分别处理，不必把整张图都判死。

需要这项分析的 Pass 先比对版本，再检查所有引用仍能找到，访问类型与字节宽度吻合，条件中的变量在使用处有定义，存储没有提前释放。然后确认它准备改写的范围内，全部相关读取和可能干涉的操作都有记录，并能定位产生映射的 Pass、适配器和输入快照。只读入口签名或做其他无关检查的 Pass，不必先建立这张表。

这些检查能发现悬空引用、版本错配和漏覆盖，不能单靠表格证明适配器的地址推导一定正确。推导规则还要测试：给同一输入分别运行未融合和融合代码，比较结果，并加入不应融合的反例。

正常的未知结果使依赖它的优化不采用。如果可选表漏记访问或引用了旧指令，报告映射错误并禁用相关改写；重新验证后仍合法的原模块可以按原调用计划执行。若损坏的是 LLVM IR、必需参数绑定或目标信息，则属于接入或执行错误，不能靠关闭优化掩盖。

## 8. 本例最终交出去什么

对启用的 P→F 融合候选，分析应该给出：F 的每次有效读取对应 t 的哪个 i；该位置的值来自 P 的哪次写入；中间是否有别的写入；对应 SSA 结果在哪个执行位置可用。若继续尝试 F→Q，再为那条边请求分析；没有启用融合时，无须为整条链预先算完这些关系。

本例若全部对应，融合 Pass 才有理由尝试把 P 的 `x[i]+1` 结果直接交给 F 的乘二，再把结果交给 Q 的加三。追踪阶段仍不删除访存，也不宣布融合成功；顺序、其他使用者、同步和资源检查由 [C 层的相应 Pass](04-C层统一处理与可选优化.md)完成。

这项可选分析的测试围绕同一条链展开：N=10、W=4 检查尾部掩码；把 F 的读取改成 `t[i+1]`，确认不会只凭同一 buffer 转发；插入可能写 t 的 inline asm，确认相关存储不能被删除；修改向量宽度或链接后保留旧映射，确认使用前被拒绝。另测不带 `BoundaryMap` 的原生模块仍能正常接入与执行，避免把优化的要求重新变成接入门槛。

这些关系如何装入降级产物，见 [B 层](03-B层多源降级与低层归一化.md)。
