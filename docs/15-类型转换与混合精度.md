# 类型转换与显式混合精度

[返回顶层设计](核心思想.md#ask-c) · [文档目录](README.md) · [ASK IR 类型](ask-ir/00-结构类型与操作.md#types) · [框架 API](10-上层框架接入.md#dtype-path) · [多精度测试](14-多精度测试.md)

每个 ASK SSA 值都有自己的元素类型。`ask.cast` 改变这个类型；`ask.add`、`ask.mul` 仍要求两个输入和结果的类型相同。因此，上层框架可以明确选择“低精度存储、f32 计算”，编译器不会在降级时替它猜一次精度提升。

## 1. 六种类型怎样表示

| Python dtype | ASK MLIR 元素类型 | LLVM 计算值 | 每元素存储字节 | Triton 数据指针签名 |
|---|---|---|---:|---|
| `bool` | `i1` | `i1` | 1 | `*i1` |
| `i32` | `i32` | `i32` | 4 | `*i32` |
| `i64` | `i64` | `i64` | 8 | `*i64` |
| `f32` | `f32` | `float` | 4 | `*fp32` |
| `f16`，也接受 `fp16` | `f16` | `half` | 2 | `*fp16` |
| `bf16` | `bf16` | `bfloat` | 2 | `*bf16` |

bool 缓冲区每个元素占一个字节，值为 0 或 1，不把八个布尔值压进一个字节。进入 LLVM 计算时使用 `i1`，读写缓冲区时完成相应转换。ShapeSnapshot 的 `element_type` 使用 `bool`，`type` 则保留 `tensor<...xi1>` 这样的 MLIR 文本；`element_bytes=1` 用于容量和地址检查。

i32 和 i64 按有符号整数解释，加乘分别保留低 32 位和低 64 位。`9223372036854775807 + 1` 因此得到 `-9223372036854775808`，降级不能附加未经证明的 `nsw` / `nuw`。bool 可以作为输入、常量、输出和 cast 的输入输出，不能直接参与 `ask.add` / `ask.mul`；要计算就先显式转成整数或浮点。

## 2. cast 的结果由哪些规则决定

Python 调用是 `graph.cast(value, dtype="f32", id=..., value_id=...)`。它生成真正的 `ask.cast` 操作，保留标量或张量种类、rank 和各轴尺寸。六种类型之间的 36 个转换方向都合法，同类型转换也合法。

| 转换 | 结果规则 |
|---|---|
| 数值 → bool | 非零为 true；`+0`、`-0` 为 false；NaN 为 true |
| bool → 整数或浮点 | false 为 0，true 为 1；转整数时使用零扩展 |
| i32 → i64 | 符号扩展，负数仍为负数 |
| i64 → i32 | 保留低 32 位，再按有符号 i32 解释 |
| 整数 → 浮点 | 直接舍入到目标格式，使用最近偶数舍入；范围不足时可以得到无穷 |
| 浮点 → 整数 | 向零截断，超出范围饱和到目标整数上下界；NaN 为 0 |
| 浮点 → 浮点 | 最近偶数舍入；扩展时精确保留值；f16 与 bf16 互转经过 f32 |

例如 f32 的 `3.9 → i32` 得到 3，`-3.9 → i32` 得到 -3，`+inf → i32` 得到 2147483647。浮点转整数必须实现这些边界规则，不能直接生成遇到越界就产生 LLVM poison 的普通转换。

常量折叠和运行时代码使用同一套语义。整数折叠使用 APInt，浮点与转换折叠使用 APFloat；均匀张量仍表示为标量常量加 `splat`，不会展开成整块常量数据。`rounding`、`overflow` 或 fast-math 属性不能偷偷覆盖 cast 的固定规则。

构图和输入编码另有一条检查：Python 有限数若在写入声明格式时变成无穷，会报输入越界；显式 NaN / 无穷可作为浮点输入。这不禁止一张合法图在运算或 cast 中产生无穷。i32 / i64 的 Python 输入也必须先在声明范围内，不能靠运行入口自动回绕非法输入。

## 3. f32 中间结果必须写进图

下面是可直接打印为 MLIR 的图。输入和输出为 f16，两次加法在 f32 中完成，最后才舍回 f16：

```python
from ask import Module, TensorType

module = Module()
tensor = TensorType((10,), "f16")
graph = module.graph("mixed", inputs={"x": tensor}, results=[tensor])
x32 = graph.cast(graph.inputs["x"], dtype="f32", id="widen")
large = graph.splat(graph.constant(1024.0, dtype="f32"), (10,))
negative = graph.splat(graph.constant(-1024.0, dtype="f32"), (10,))
added = graph.add(x32, large)
restored = graph.add(added, negative)
y = graph.cast(restored, dtype="f16", id="narrow")
graph.return_(y)
print(module.to_mlir())
```

取 `x = 1 + 2^-10`。如果两次加法都是 f16，`(x + 1024) - 1024` 得到 1，小数中的一个 ULP 丢失；上图保留 `1 + 2^-10`。bf16 对应 `x = 1 + 2^-7` 和 `(x + 128) - 128`，显式 f32 中间结果同样保留这个 ULP。

这说明的是逐元素表达式的计算精度；目前没有据此实现 reduce 算子。低精度 `ask.add` / `ask.mul` 仍在每步结束时舍回其声明类型，即使后端为实现单个低精度操作临时使用 f32，也不能跨过这次舍入继续累加。优化可以把同形状、不同 dtype 的 cast 和算术放进同一个循环，但不能删掉有数值意义的转换。

## 4. 跨 F 边界时，保留哪一个类型

当前 GPU 图路径仍要求一个 external、单输入单输出、同形状逐元素访问；图输入、F 输入、F 输出和图输出使用同一种存储 dtype。P/Q 内部可以显式转成其他类型，在 F 边界和最终输出前再转回存储类型。不同输入输出存储类型、归约或多个 external 不在这条融合路径中。

F 的计算类型由提交的 DSL 决定。例如低精度 F 想用 f32 计算，可以在自己的源码中写：

```python
value = tl.load(t + i, mask=i < N, other=0)
result = (value.to(tl.float32) * 2.0).to(value.dtype)
tl.store(u + i, result, mask=i < N)
```

适配器验证数值数据流中的显式 `.to(...)`，边界标记仍传递原来的存储类型。ASK 不根据 P/Q 的类型替 F 插入转换，也不修改 F 的 FMA、布局或启动选项。F 的 cast 遵循原编译器的数值语义；本章的饱和、NaN 等 ASK cast 规则只约束 `ask.cast`，不能据此改写任意 Triton 转换。接入检查见 [GPU 融合](12-GPU融合与IR缓存.md)。

cast 产生新的逻辑值，标记继续只追踪它所附着的那个值。形状推导复制尺寸，保留目标 dtype；external 的 `same_as` 也只复制尺寸，结果 dtype 仍来自语义签名。ShapeSnapshot 同时记录转换前后的类型、尺寸和元素字节数，不从低层指针反推。具体规则见 [ASK IR 形状推导](ask-ir/02-形状推导与约束.md)。

## 5. 编译目标和实际硬件分别检查

bf16 可以在任何主机上构图、推导形状和常量折叠；请求生成或执行含 bf16 的代码时才需要目标支持。检查包括中间值：输入和输出都是 f32，但中间转过 bf16，也有 bf16 要求。

CUDA 导出按请求使用普通 `sm >= 70` 目标，不再固定 sm80；含 bf16 时编译目标至少为 sm80。这里只接受普通整数架构，不接受 `90a` 这类后缀目标；Triton、锁定 LLVM 后端和 ptxas 还要分别支持该具体架构。实际运行再检查所选 GPU，bf16 要求 compute capability 的 major 至少为 8；不支持时在创建 context、加载模块、分配设备内存之前报错。缓存命中不能跳过检查。工具链不认识编译目标、设备不支持 bf16、设备不能加载该 cubin 是三类不同问题，不能合并成一个“类型不支持”。

普通导出也检查 F 的内部类型。适配器从 Triton 公开的 `compiled.asm["ttir"]` 读取实际类型标记，排除注释、字符串和符号名，写入产物的 `required_element_types`。因此 f32 端口内部执行 `bf16 → f32` 转换时，需求不会被不透明 LLVM 指针隐藏。端口本身声明 bf16 时在调用编译器前拒绝过旧目标；只有编译后才看得到的内部 bf16 在发布产物前检查。运行器合并产物、融合报告和边界记录中的需求。

host 后端使用本机 CPU 名称和 feature 生成 LLVM 与目标文件。x86 检查 `avx512bf16` 或 `avxneconvert`，AArch64 检查 `bf16`；只有 AMX 的矩阵 BF16 feature 不足以证明此后端需要的转换能力。缺少对应 feature 或架构未接入时，在 host LLVM / object 写出前报错。支持机器上仍保持 bf16 存储和每步舍入：内部用 f32 执行单次算术，再严格按位舍回 bf16。这避免某些原生窄化指令 flush 非正规数，并不允许保留 f32 中间结果跨越下一次 ASK 运算。

`host_bf16_hardware_supported` 报告当前 CPU 的检查结果，元素类型能力列表描述对应编译路径的能力。它们都不能替代 CUDA 实际设备检查。本轮开发机器没有 CPU BF16 feature，因此支持分支的真实 CPU 执行不能由拒绝测试替代。

## 6. 同一张图怎样覆盖转换和混合精度

[pointwise.py](../tests/support/pointwise.py) 的 `DTYPES` 列出上述六类；`build_module` 接受存储 `dtype`、显式 `compute_dtype`、`roundtrip_dtype` 和目标 `arch`。这些是共用测试构图器的参数，不是生产编译器会自动改变精度的开关。

`cast-bool` 到 `cast-bf16` 六张配置分别选择一次 `存储类型 → 目标类型 → 存储类型`。遍历六种存储类型就得到 6×6 方向矩阵；host、真实 Triton 导出和 GPU 冷热缓存复用这组图。`mixed-accumulate` 用上面的 ULP 例子区分低精度与 f32 中间结果；`mixed-special` 和 `mixed-F-contract-*` 检查特殊值与 F 的原 FMA 策略。

数值参考 `cast_reference` / `round_reference` 使用独立有理数运算，不调用生产编码器。样本覆盖整数上下界、截断、饱和、NaN、无穷、带符号零、非正规数和舍入中点。常量折叠另以同一参考检查 36 个转换方向；运行时对照不能只检查转换后的 LLVM 指令名称。

完整运行命令和冷/热缓存检查见[多精度测试](14-多精度测试.md)。该章与 [GPU 验证记录](12-GPU融合与IR缓存.md#6-如何复现数值验证) 区分已有实测和新增矩阵，生成了测试计划或通过模拟设备拒绝测试，都不算完成 GPU 数值验证。
