# 用 ask.mark 记录值经过哪里

以下是尚未实现的设计。[返回顶层设计：A 层](../核心思想.md#ask-a) · [ASK IR 索引](README.md)。

上层框架产出基础高层 ASK IR，其中第三方编译片段用 `ask.external` 声明语义和编译边界，并关联对应编译器的 DSL。`ask.external` 是执行 F 计算的操作，不是 identity。通过高层图接入 Triton 片段时，这项声明和 DSL 输入必须具备。

本篇的 `ask.mark` 是另一种可选标记：插入编译过程，记录一个值从哪个端口经过。它不执行 F，不是外部调用占位，也不要求某种优化。删掉它后，`ask.external` 及其 DSL 引用仍然存在。ASK IR 采用 A 层的 MLIR `ask` dialect；最终 LLIR 仍是原生 LLVM IR。

## 1. 标记只返回输入，不产生计算

定义：

```text
ask.mark : T -> T
mark(x) = x
```

T 可以是 ASK 支持的标量或 tensor 类型。输入和输出类型必须完全相同，包括元素类型、rank、各维度和类型中已有的布局信息。标记不能转换精度、改变形状、复制 tensor、创建视图或分配缓冲区。

它没有读写、分配、释放、同步或其他可观察效果，也不检查运行时数据。它不改变求值次数、线程参与范围或调度要求。不能用 `!ask.token` 给它串效果链，不能让它承担某种“等前面的计算完成再记录”的职责。效果链与计算操作见[结构、类型与操作](00-结构类型与操作.md)。

记录发生在编译器读取 IR 时，写入编译期的 `MarkTable`；程序运行时没有日志写入、回调或计数器。最终执行路径必须已经去掉所有标记。

## 2. 在输入输出之间插入标记

沿用 `P: t=x+1`、`F: u=t*2`、`Q: y=u+3`，每一步按模 2^32 计算。框架已经在 ASK IR 中声明 `ask.external`，其实现引用指定 `compiler_id` 和 `DSLSource`。下面再在这个计算操作的前后添加可选追踪标记：

```mlir
%t_in = "ask.mark"(%t) {
  mark_id = "m_F_in",
  value_id = "v_t",
  port_id = "F.in",
  role = "input"
} : (tensor<10xi32>) -> tensor<10xi32>

%u = "ask.external"(%t_in) {
  semantics = @scale2_i32_v1,
  implementation = @triton_scale2
} : (tensor<10xi32>) -> tensor<10xi32>

%u_out = "ask.mark"(%u) {
  mark_id = "m_F_out",
  value_id = "v_u",
  port_id = "F.out",
  role = "output"
} : (tensor<10xi32>) -> tensor<10xi32>
```

`ask.external` 的定义与模块内符号绑定见[结构、类型与操作](00-结构类型与操作.md)，这里省略注册表绑定声明。`@scale2_i32_v1` 说明 F 的计算含义；`@triton_scale2` 关联 Triton 编译器与实际提交的 DSL，供 B 层发起编译。真正产生新逻辑值 u 的是 `ask.external`；两个 `ask.mark` 分别只透传 t、u，不能代替该声明或 DSL，也不能证明 F 内部的元素对应关系。

标记有四项说明：

| 属性 | 含义 |
|---|---|
| `mark_id` | 本次插入站点的编号，用于查找其后发生的克隆、合并或消除 |
| `value_id` | 它记录的逻辑 `ValueId`，必须与操作数已经绑定的逻辑值一致 |
| `port_id` | 可选的 `PortId`；输入或输出标记需要，内部值标记可以省略 |
| `role` | `input`、`output` 或 `value`，说明这个站点原先记录的用途 |

`role` 是来源说明，不是内存读写声明；`output` 标记不能因此被当作 store。编号使用所属编译单元的命名空间，避免不同导入产物中都叫 `m0` 的站点互相覆盖。

## 3. 一个逻辑值，可以有两个 SSA 名字

上例中的 `%t` 与 `%t_in` 是两个不同的 MLIR SSA 定义。它们的 `SSARef` 不同，但都对应逻辑值 `ValueId = v_t`。`ask.mark` 不为 `%t_in` 发明一个新的逻辑张量。

```text
SSARef(%t)    -- logical_value --> v_t
SSARef(%t_in) -- logical_value --> v_t
traceIdentity(%t_in) = %t
```

`SSARef` 只在对应 IR 快照中定位定义；不能把打印出来的 `%t_in` 或进程内对象地址当作持久编号。序列化使用产物摘要、模块 revision 及快照内定位信息，重新加载后再次绑定。

如果 v_t 已经关联某个 `BufferId`，标记结果关联同一存储；尚未决定物化方式时，`bufferIdentity` 保持未知。不涉及存储的标量可以明确记为不适用。不能为了填写这个字段提前分配缓冲区。同一 BufferId 也不能说明缓冲区内容从未被后续写入修改。

形状表按 `(ValueId, semantic_revision)` 保存事实，因此 `%t` 和 `%t_in` 使用同一份形状记录。形状推导只需要沿 identity 关系转发，不执行广播或维度运算。未知维度仍是同一个未知维度，不生成一个新的独立符号。具体规则见[形状推导与约束](02-形状推导与约束.md)。

## 4. 操作 verifier 检查什么

`ask.mark` 必须恰好有一个 operand 和一个 result，没有 region、successor 或效果 token。verifier 检查 T 是否属于允许的值类型，以及输入输出类型是否完全一致。

随后检查属性：`mark_id` 和 `value_id` 必须有效；`role` 必须是已定义的取值；`input/output` 必须引用存在且与逻辑值相符的端口。`value` 标记可以没有端口，但仍需有对应的逻辑值。首次建立站点时不能让同一 `mark_id` 同时声称两个不同逻辑值或两组矛盾的端口信息。

类型相等可以使用 MLIR 的 `SameOperandsAndResultType` 约束，形状和结果类型推导返回操作数类型。它不应宣称内存读写效果，并提供相应的可推测执行说明；具体 traits 与接口按锁定 MLIR 版本实现。[MLIR 操作定义](https://mlir.llvm.org/docs/DefiningDialects/Operations/)、[副作用与可推测执行](https://mlir.llvm.org/docs/Rationale/SideEffectsAndSpeculation/)

identity 折叠规则是“用 operand 替换 result”。它不进行算术，不改变浮点值的位模式，也不插入验证或冻结值的操作。合法操作可以删除；某个分析希望多看它一会儿，不改变这条语义。

## 5. MarkTable 保存站点，再记录它的变化

`MarkTable` 是追踪信息，不是形状或调用 ABI 的唯一存放处。后续没有一个标记存活时，独立的形状快照、端口绑定和调用说明仍必须足够支撑正常降级与执行。

一条记录至少能回答下列问题：

```text
MarkRecord:
  site = (compilation_unit_id, mark_id)
  logical_value = ValueId
  port = optional PortId
  role = input | output | value
  source = source_location, producer_version, pass_or_plugin_version
  semantic_revision
  occurrences = [(ir_revision, operation_ref, operand_SSARef, result_SSARef)]
  bufferIdentity = optional BufferId
  lower_links = optional [(artifact_digest, llir_revision, BoundaryMap_entry)]
```

`mark_id` 标识原来的插入站点，不承诺此后永远只有一个同名操作。克隆可以产生多个相同来源的 occurrence，各自用 revision 和操作引用区分。站点说明必须一致；如果确实要记录另一处新插入点，就分配新的 mark_id。

ASK 自有变换或受支持的插件记录事件，事件包含变换前后 revision、输入 occurrence、输出引用及产生事件的 Pass：

- `duplicated`：一个站点对应多个副本。分别记它们的路径、索引范围等已知信息，未知的留空，不能复制一份旧映射冒充每个副本都正确。
- `merged`：多个来源落到同一个定义。保留来源集合及成立条件；不同逻辑 ValueId 不因共用一个 SSA 定义就自动改成同一个 ID。
- `eliminated`：标记或其对应定义被删除。注明删除的是标记本身还是计算定义；若只删标记，记录 result 已转发到哪个 operand。
- `lost`：出口找不到有效对应，也没有可靠的变换记录。它表示追踪链中断，不能推断原计算被删除。

事件是编译过程记录，不是等价证明。只有观察到并验证过的关系才能成为 `BoundaryMap` 条目。外部 Pass 没有回报事件时，不能自行补写“保持不变”；跨层映射的验证规则见[追踪契约](../02-跨层身份与追踪契约.md)。

## 6. 在 ASK 自有流程中，先提取，再去标记

ASK 可以控制自己的一小段处理顺序：

```text
build and verify ASK IR
register marker sites and SSA identity links
infer shapes; mark forwards the operand's shape facts
export current MarkTable and independent shape/port bindings
replace every mark result with its operand; erase the mark
verify the marker-free IR; publish the new revision
continue normal optimization and lowering
```

为收集形状、端口和位置，ASK 可以在这段明确的阶段中暂缓 identity erase。暂缓依靠 Pass 顺序，不依靠伪造副作用。若中间确实调用会折叠或删除标记的工具，就先提取记录，或通过改写监听更新已观察到的关系；不能假定纯 identity 会一直留下。

构图入口也要遵守这个顺序：先登记站点再允许折叠，不能用 `createOrFold` 立即消掉操作后，才指望一次遍历找回它的属性。

MLIR 的通用规范化可以消除无效果且无使用的操作，也支持 identity 折叠，因此标记的消失是合法情况。[MLIR Canonicalization](https://mlir.llvm.org/docs/Canonicalization/)

删除时先核对输入输出类型及 identity 关系，再完成 RAUW 和 erase，随后更新表中的引用。遇到类型不符、悬空引用或错误的逻辑值绑定，应报告输入或变换错误，不添加 cast、不造一个 dummy 值把删除“做成功”。试改失败则丢弃副本，恢复原有效 IR 和对应表；没有合法原输入就停止该次编译。

可选追踪导出失败与 IR 无效不同。若 IR 有效但只能恢复部分追踪，记录缺项，仍可去掉标记继续编译；依赖缺失信息的优化以后跳过。必需的形状或调用资料若不完整，按对应阶段的错误处理，不能指望把 marker 留到运行时补齐。

## 7. 标记不能延长值或缓冲区的生命

在原始 MLIR use-list 中，`ask.mark` 确实使用了 operand；因此不能简单拿 `hasOneUse()` 的结果当作真实消费者数量。ASK 的使用分析先穿过 identity 链：标记结果的计算消费者才是真实使用者，MarkTable 中保存的一条记录不算使用者。

如果某个计算结果只被几个没有真实消费者的标记引用，导出已有信息后去掉标记；原计算若也无副作用，就可以正常 DCE。既不能让 MarkTable 持有关系阻止删除，也不能因为存在一个 `output` 标记就把值提升成用户输出。

执行布局、缓冲区物化和释放分析在去标记后进行，或者明确使用上述透明使用关系。若 tensor 将来绑定到 buffer，标记不增加一次 retain，不延长异步完成事件，也不触发复制。这样追踪开关不会靠保活死值改变原有存储计划。

## 8. 外部编译器愿意接收时，才插入标记

外部编译器必须提供公开支持的插件、Pass 或导出扩展点，ASK 才在那条路径上插入标记。外部能加载 `ask` dialect 时使用同一 identity 定义；不识别它时，只能使用该公开接口支持、可合法降级的同义载体，并在接入说明中写清楚其 identity、无效果及清除规则。

找不到这种公开方式就不插入。不能要求解析器容忍一个没有语义的未知操作，也不修改外部源码、复制改写私有编译阶段或私接内部对象。

外部优化可以克隆、合并或提前删除标记。适配器只导出仍能验证的记录；不承诺标记穿过外部 O3 后仍有一一对应的指令。缺少记录时在 ASK 导入原生 LLVM IR 后重新分析，分析不了就保留未知。

F 的既有执行策略不为追踪改变。不能关闭 F 的优化、换布局、改线程映射或插入同步来保住标记。公开插件若会让标记参与调度或物化决策，应在那些阶段前去掉标记，或证明编译器按透明 identity 处理；做不到就不用这条插入路径，退回正常导出。

## 9. Triton 先编译声明的 DSL，再按需建立追踪记录

首期 Triton 路径从 `ask.external` 的实现引用取得框架提交的 `DSLSource`，按固定配置通过公开接口编译 DSL，导出原生 LLVM IR。这条流程不要求 pre-LLVM hook，也不要求在 Triton 内部插入 `ask.mark`。

ASK 按真实 `port_map` 将逻辑端口绑定到 LLVM 参数、返回值或写出指针，才能正确调用产物；这部分绑定不能用可选追踪代替。需要后续追踪时，再据此建立 MarkTable 中的边界记录。没有这些额外记录，DSL 编译、正常导入和调用仍应成立。接口见[第三方 LLIR 接入 API](../08-第三方LLIR接入API.md)。

例如 `F.in -> LLVM argument 0` 可以建立一条低层边界记录，引用已有的 `ValueId = v_t` 和 `PortId = F.in`。这条记录表示从哪个参数开始分析，不表示已经找到了所有读取，更不表示已证明每个读取都对应 t[i]。它是 MarkTable 中的编译期记录，不是在 LLVM IR 中插入一个 `ask.mark` 函数调用。

如果将来公开插件可以提供更早的有效记录，可作为可选增强；基础接入和正常代码生成不依赖它。对带 inline PTX 的访问无法解释时，记录 `unknown`，模块仍可以按目标支持情况导入和代码生成，不强行将它变成普通 load/store。

LLVM metadata 可以携带简短的站点或表项引用，但不是稳定的追踪存储，更不是融合证明。指令被改写后，metadata 可能消失；即使还在，所指元素、mask 或执行位置也可能已经变化。表项必须绑定当前产物和 revision，并在使用前重新验证。[LLVM Metadata](https://llvm.org/docs/LangRef.html#metadata)

ASK 自有降级怎样继续传递已提取信息，见[降级与信息保留](03-降级与信息保留.md)；使用这些信息的可选优化见[顶层 C 层](../核心思想.md#ask-c)。

## 10. 用反例检查这是不是纯标记

先做最小成功例：在 P/F/Q 两个边界插入标记，完成形状推导并导出表，再删除标记。去标记后的计算应与不插标记时相同，执行结果保持 i32 回绕规则，目标代码中没有标记调用或追踪访存。

再逐项验证容易写错的地方：

- 将 `tensor<10xi32>` 标成 `tensor<8xi32>` 或 f32：verifier 拒绝，不能把它当 reshape 或 cast。
- 为 marker 的 result 创建新 ValueId、新 ShapeState 或新 BufferId：身份检查拒绝；新的只有 SSA 定义。
- 用 `ask.mark` 包住效果 token，或添加 `keepalive`、假 load/store、`asm sideeffect`、不透明调用来强留标记：不属于本操作定义，不能作为实现方案。
- 只剩 marker 使用一个纯计算结果：提取信息后，marker 和死计算都应可删除，缓冲区也不能因此保活。
- 标记被克隆或合并：表能记录多个 occurrence 和多个来源；标记被外部优化抹掉：记录缺失，正常导入执行仍通过。
- 导出表后又改了索引或 buffer 绑定：旧 lower link 失效，不能只因 mark_id 相同就继续用于边界替换。
- 最终降级还残留 marker 或无语义载体：阶段检查失败，不把它编成运行时 no-op 调用来交差。

更完整的贯穿示例与验收组合见[示例与验证](04-示例与验证.md)。
