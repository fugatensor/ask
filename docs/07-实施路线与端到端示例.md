# 按一个例子把编译器做出来

[返回顶层设计](核心思想.md#ask-minimal-loop) · [文档索引](README.md)

下面安排完整编译器的实现顺序。当前初稿已跑通高层图准备、自有 i32 / f32 / f16 图的 host 代码生成，以及 Triton DSL 导出后由 ASK 读取原生 LLVM IR；尚未完成下面的混合图执行验收。可运行的范围见[框架接入](10-上层框架接入.md)。首期只接入 Triton，其他外部编译器随后扩展。融合可以一直关闭，不影响前四步验收。

## 1. 定下输入和参考答案

整个开发过程使用同一段计算：

```text
P: t[i] = add_wrap_i32(x[i], 1)
F: u[i] = mul_wrap_i32(t[i], 2)    # Triton 提供
Q: y[i] = add_wrap_i32(u[i], 3)
```

每一步保留整数结果的低 32 位。N 在编译时确定，x 只读，y 是单独的分配，t/u 不返回给调用者。参考实现必须显式处理整数回绕，不能依靠宿主语言的无限精度整数默认行为。

例如 `x = [-2, -1, 0, 1]` 时，按有符号整数显示的结果是 `[1, 3, 5, 7]`。另加溢出用例：输入位模式 `0x7fffffff`，P 得到 `0x80000000`，F 得到 `0`，Q 得到 `3`。结果按位模式比较。

## 2. 先让原生 LLVM 文件进入 ASK

实现[接入 API](08-第三方LLIR接入API.md)中的离线入口：使用 LLVM reader 读文本或 bitcode，构造 `llvm::Module`，运行 verifier，保存内容和诊断。

这一步的输入可以没有算子绑定、launch 或追踪表。输出要明确：模块已接收；哪些执行信息未提供；哪些分析尚未请求。不要因为缺少这些信息就把合法 LLVM 文件判为非法，也不要因为解析成功就声称已经可运行。

准备普通 LLVM 指令、目标 intrinsic、inline asm 三类样本。合法的内联 PTX 应能随模块保存；损坏的 SSA 或类型则必须被拒绝。再读回保存结果，确认入口、地址空间、属性、汇编约束和依赖没有丢失。

这一阶段同时确定所有权：编译会话管理 LLVMContext 和 Module；磁盘保存 IR 与说明文件，不保存 LLVM 对象地址。

## 3. 接入真实 Triton，重新生成并运行 F

提取外部编译器产物要处理导出阶段、参数特化、启动配置、依赖和工具链版本。首期锁定一个 Triton 版本、匹配的 LLVM 工具链和一个实际目标配置，完成一个真实导出器。扩展接口仍按编译器无关方式定义。

流程是：

```text
固定 F 的源码、常量、编译选项、目标与启动方式
  -> 通过公开接口编译并取得 llir 和调用信息
  -> ASK 直接解析原生 LLVM IR，检查入口与参数绑定
  -> 保留其中的 intrinsic 和 inline PTX
  -> 生成目标代码，加载并执行 F
  -> 与参考计算、原始 Triton F 比较
```

此时不要求完整 BoundaryMap，也不要求解释每条 PTX。后端能处理这些目标操作、调用说明正确，就应能通过这一步。对含内联 PTX 的真实导出样本至少保留一个回归用例，防止后来把“没有追踪表”误写成导入门槛。

必须验证 ASK 接收的 IR 确实用于重新生成并执行代码。仅保存一份 IR，然后一直调用原始二进制，不能证明这条路径已经完成。原始二进制可以作对照或独立回退产物，两种结果分开记录。

后端可以直接调用相应目标工具链。Triton 的公开阶段覆盖机制也可用于同入口 ABI、同启动和资源要求的初期验证，但不能把它当成任意 LLVM 文件的通用编译 API。具体限制见[代码生成](05-代码生成与运行时.md)。

再测试缺少 grid、参数对应错误、目标不匹配、未解析的外部符号。它们应停在各自的检查位置，不能等到错误指针进入设备后才暴露问题。解析通过和运行条件齐全分别报告。

## 4. 把三个入口接成正常执行的图

实现 ASK IR 的 builder，并用一个框架侧前端生成同一张静态图。ASK 的图入口只接收生成好的基础 ASK IR；第三方 F 以 external 节点标记，同时附上 Triton DSL：

```text
P.out -> t -> F.in
F.out -> u -> Q.in
users(t) = {F}
users(u) = {Q}
outputs = {y}
```

类型、形状或语义引用错误时，指出具体连接。给 t 增加一个使用者后，使用表必须跟着变化。图中的动态控制仍交给框架；F 内部的循环和 mask 不受这个限制。

P/Q 走 ASK 自有降级，F 使用上一步接入的实现。三者都可以是原生 LLVM 模块，仍按三个入口执行：

```text
allocate t, u
run P(x, t)
wait until t is ready
run F(t, u)
wait until u is ready
run Q(u, y)
release t, u after their last users finish
```

在选定目标上检查 N=0、N=1、普通长度和尾部不足一个处理块的长度。零长度应按已定义的调用策略处理，不盲目发出非法的零尺寸启动。除数值结果外，还要检查事件依赖和缓冲区释放时机。

到这里，首期的“统一接入并执行”已经完成。它不依赖融合。若某个实际目标无法运行这条路径，应报告未完成，不能用测试替身或尚未实现的解释器替代真实验收。

## 5. 接上通用分析和可选 Pass

先做不依赖高层追踪的能力，例如列举入口和依赖、检查调用关系，以及 LLVM 规则允许的局部常量折叠。每次变换更新 IR revision，并正确使受影响分析失效。

在样本中放入语义未知的 asm，分别检查两件事：依赖其访存效果的移动被跳过；已经证明与之无关的计算仍可优化。不能通过删掉 asm 或假定它没有副作用让测试通过。

这一步验收 Pass 的输入要求、`applied/skipped/invalid` 诊断和失败恢复。对试改制造的无效 IR 保存错误信息，丢弃副本；正式产物不能被半完成的参数或追踪更新污染。细节见 [C 层](04-C层统一处理与可选优化.md)。

## 6. 有需要时，再做跨层追踪和融合

先针对一个边界解释清楚：F 的哪次读取对应 t 的哪个元素，由哪个执行实例读取，mask 是什么，生产值何时可见。普通 LLVM 地址分析不能覆盖的目标操作，需要经过验证的分析模型；没有模型就留下未知项。

只有这些信息足够时，才尝试将 P(i) 放到 F 原读取位置。保持 F 的执行策略，必要时重新编译 ASK 自有 P。通过后再处理 `F → Q`，最后检查 t/u 是否真的可以删除。详细证明步骤见 [C 层的融合部分](04-C层统一处理与可选优化.md)，追踪更新规则见[跨层身份](02-跨层身份与追踪契约.md)。

成功例之外，逐项增加反例：偏移读取、不一致 mask、多消费者、别名重叠、跨实例依赖、原子或未知副作用、必须保留的数值转换。应保留的调用和存储必须仍在；跳过优化后结果继续正确。

追踪恢复率、融合成功率、执行正确性和性能分别统计。融合后还可能因寄存器压力或其他资源开销变慢，减少中间存储不能替代实际测量。

## 7. 接第二个编译器之前检查什么

先用小型导出器测试接口：它只返回 LLVM 文本和调用说明，不使用 Triton 专有对象。ASK 核心应能直接接收，不需要新增一个按编译器名字分支的解析器。这是接口隔离测试，不算支持了第二个真实编译器。

真实接入新编译器时，优先补它的公开导出回调和参数绑定；有新目标时补目标后端；只有想运行更强的优化时才补相应分析。三类工作分开验收，避免每接一个编译器都重写整条流水线。

工程目录和验证分工见[工程组织](06-工程组织与验证.md)。D 层不在当前设计中。
