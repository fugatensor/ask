# 构建 ASK 时选择哪些第三方编译器

[返回顶层设计：工程约束](核心思想.md#ask-engineering) · [适配器接口与目录](17-第三方编译器适配与注册.md) · [文档目录](README.md)

这里的第三方编译器指 Triton 这一类：接收框架提供的 DSL，为 `ask.external` 生成实现。LLVM/MLIR 是 ASK 的基础设施；host、CUDA 是目标代码生成和执行后端。构建分别选择它们。

<a id="selection"></a>

## 1. 一个选项控制编译器集合

```text
ASK_THIRD_PARTY_COMPILERS = none | all | <id>[;<id>...]
默认：none
```

| 配置 | 实际结果 |
|---|---|
| `none` | 保留 ASK 核心、Python API、nanobind 绑定和运行时，不包含第三方适配器 |
| `all` | 启用当前 [registry.json](../adapters/registry.json) 中全部适配器 |
| `triton` | 只启用 Triton |
| 分号分隔的 ID | 启用指定集合，去重并排序 |

当前真实适配器只有 Triton，因此 `all` 与 `triton` 的集合相同。测试替身不进入名录。新增适配器后，`all` 才随源码一起扩大。

空配置、空列表项、未知名称、`none;triton` 和 `all;triton` 都报错。**Python 绑定属于基础组成，三种模式都构建，不设独立关闭选项。**

<a id="commands"></a>

## 2. 配置与构建

先按[仓库 README](../README.md#构建)准备锁定的 LLVM/MLIR 和 nanobind。基础绑定需要 Python 解释器及匹配的扩展开发文件；`Python_EXECUTABLE` 选择它使用的解释器。

```bash
cmake --preset core \
  -DLLVM_DIR="$PWD/.deps/llvm-1f126a6d-ubuntu-x64-1/lib/cmake/llvm" \
  -DMLIR_DIR="$PWD/.deps/llvm-1f126a6d-ubuntu-x64-1/lib/cmake/mlir"
cmake --build --preset core
ctest --preset core

cmake --preset triton \
  -DLLVM_DIR="$PWD/.deps/llvm-1f126a6d-ubuntu-x64-1/lib/cmake/llvm" \
  -DMLIR_DIR="$PWD/.deps/llvm-1f126a6d-ubuntu-x64-1/lib/cmake/mlir" \
  -DASK_TRITON_PYTHON_EXECUTABLE=/opt/triton-env/bin/python
cmake --build --preset triton
ctest --preset triton
```

`all` 预设采用同样的基础依赖路径，并要求为所有选中适配器准备环境。也可直接指定 `-DASK_THIRD_PARTY_COMPILERS=triton`；多个名称必须给整个值加引号，避免 shell 解释分号。

`ASK_TARGET_BACKENDS` 当前接受 `none` 或 `host`。它控制 ASK 自有 host 代码生成，不控制第三方编译器集合。基础 CUDA 运行时在全部模式中构建，按需加载驱动，不需要构建机安装 CUDA SDK。GPU 代码生成目前由调用方显式提供 `llc` 与 `ptxas`，尚无集成式 `ASK_TARGET_BACKENDS=cuda` 选项。

<a id="core"></a>

## 3. `none` 保留什么

`none` 保留 ASK IR、形状推导、自有 lowering、LLVM 导入与优化、设备张量、常驻 Session 和异步执行。它也能 `prepare` 含 `ask.external` 的图，检查语义和类型并生成待编译请求。

真正编译外部 DSL 时才检查允许集合；未启用的 ID 在启动 worker 和查询外部 IR 缓存前被拒绝。两种其他请求不需要源编译器：

- `--check-llir` / `--optimize-llir` 检查已有 LLVM 文件。
- 加载已生成的规范化 CUDA v2 产物与 cubin，按 ABI 和实际硬件执行。

第二条不接受第三方的 Python launcher 或 `CompiledKernel` 对象。ASK 必须拥有代码、参数映射和启动说明，才能独立加载。当前执行接口的限制见[常驻运行时](16-Python绑定与常驻运行时.md)。

<a id="targets"></a>

## 4. 核心库与适配器分开链接

| 目标 | 职责 | 依赖方向 |
|---|---|---|
| `ASK::Core` | ASK IR、前端、自有 lowering、通用 LLVM Pass | LLVM/MLIR；不链接适配器或 Python |
| `ASK::Compilers` | 生成的注册表和选中适配器的原生对象 | 公共适配接口及 LLVM |
| `ASK::Runtime` | 设备、模块、张量、stream、event | 按需加载 CUDA driver |
| `_native` | nanobind Python 入口 | 装配 Core、Compilers、Runtime |
| `ask-opt` | CLI、worker 调度和产物验证 | 装配 Core 与 Compilers |

每个适配器在自己的目录定义 `ask_adapter_<id>` OBJECT target。公共装配库收集选中的对象；`none` 的注册表为空。核心融合函数接收一个 `CompilerAdapter` 参数，不自行查找 Triton 工厂。

因此安装后的 C++ 项目可只链接 Core，不必初始化 Python，也不必拥有 Triton 环境。若需要按 ID 查找本次构建的适配器，再显式链接 Compilers：

```cmake
find_package(ASK CONFIG REQUIRED COMPONENTS Core Compilers)
target_link_libraries(my_compiler PRIVATE ASK::Core ASK::Compilers)
```

只使用前端时删除 `Compilers` 即可。实际消费者示例见[examples/cpp](../examples/cpp/CMakeLists.txt)。

<a id="configure"></a>

## 5. 配置只进入选中的目录

顶层按以下顺序工作：

1. [AskCompilerRegistry.cmake](../cmake/AskCompilerRegistry.cmake) 读取显式名录；不扫描目录、Python 包或 entry points。
2. [AskCompilerSelection.cmake](../cmake/AskCompilerSelection.cmake) 把 `none/all/列表` 解析成 ID 集合。
3. 检查基础 LLVM/MLIR、Python、nanobind 与目标选项。
4. 仅对选中的 ID 读取 `registration.json` 并执行该适配器的 `CMakeLists.txt`。
5. 生成 C++ `Manifest.inc` 和 Python `_adapter_registry.json`，用同一集合装配能力报告、目标和安装规则。

未选中的适配器不执行依赖检查，也不注册测试或安装规则。`all` 中任意一个必需环境缺失就配置失败，不静默缩成“这台机器碰巧能用的集合”。

<a id="workers"></a>

## 6. 每个 worker 使用自己的环境

Triton 的解释器选项和 `--probe` 检查都在 [adapters/triton/CMakeLists.txt](../adapters/triton/CMakeLists.txt) 中。`ASK_TRITON_PYTHON_EXECUTABLE` 与基础绑定的 `Python_EXECUTABLE` 可以不同。其他适配器应在自己的目录定义环境策略；原生 worker 不需要伪装成 Python 脚本。

ASK 进程通过 JSON 文件传入 DSL、特化和固定选项，worker 返回原生 LLVM 文本及调用说明。不跨进程传 `llvm::Module*` 或 Python 对象，也不把构建机的 venv 路径写成安装包的固定运行路径。

配置只验证已准备的环境，不运行 `pip install`。依赖由显式步骤取得并记录在适配器的锁定文件中。进程隔离避免两个编译器直接共享原生库对象；它不能让旧 LLVM reader 自动理解新 IR，所以仍要验证 producer/reader 的实际兼容性。

<a id="capabilities"></a>

## 7. 能力查询与 Python 注册

```bash
build/core/bin/ask-opt --capabilities
build/triton/bin/ask-opt --capabilities
```

与编译器集合相关的字段是：

```json
{
  "third_party_compilers": ["triton"],
  "compiler_adapters": [
    {"id": "triton", "protocol_version": 1, "supports_fusion": true}
  ],
  "external_export": true,
  "external_llir_fusion": true
}
```

`none` 的两个数组为空、两个布尔值为 false，基础运行时能力仍为 true。`build_id`、LLVM 修订、Python ABI 等字段用于核对客户端与原生构建。

SDK 先检查原生允许集合，再读取生成的 Python 注册记录，最后导入所选工厂。多个搜索路径若暴露不一致的注册文件会报错；环境缺失、未启用和编译失败分别诊断。旧 `triton_llir_fusion` 字段已由通用字段与逐适配器能力替代。

<a id="install"></a>

## 8. 安装交付构建时选定的集合

```bash
cmake --install build/core --prefix "$PWD/build/install-core"
cmake --install build/triton --prefix "$PWD/build/install-triton"
```

当前使用一个 `Core` 安装组件交付完整选中配置：库、CLI、Python 包、原生扩展、注册表，以及选中适配器的 Python 策略、worker 和锁定记录。**`--component Core` 不会再次裁剪已选适配器。** 需要无第三方安装包就从 `none` 构建安装。之前设计中的 `CompilerTriton` 独立安装组件尚未实现。

这与 `ASK::Core` 库的链接隔离是两件事：triton 安装包携带适配器，但只链接 `ASK::Core` 的 C++ 程序不依赖它。`find_package` 当前识别 `Core`、`Runtime`、`Compilers` 三个组件；不支持的组件请求会失败。

Python wheel 也交付构建时的选择。默认是 `none`；需要 Triton 时通过 scikit-build-core 的 `cmake.define.ASK_THIRD_PARTY_COMPILERS=triton` 及对应解释器选项配置。wheel 的配套 CLI 位于 `ask/_bin/`，适配器资源位于包内 `ask/share/ask/adapters/<id>/`，两者保持相对路径。第三方编译器本体及其 venv 不打进 wheel。

发布包使用干净 staging 目录。普通安装不会替你删除旧前缀里的文件；同一构建目录从 triton 切到 none 后，旧文件即使仍在磁盘，也不会进入新的注册集合。不能依赖目录扫描重新启用它。

<a id="layout"></a>

## 9. 新增适配器时改哪里

新增 `adapters/<id>/`，把构建、原生接口、Python 策略、worker、锁定记录和专属测试放在里面；再给 `adapters/registry.json` 加一条 ID 到目录的映射。顶层 CMake、通用 GPU 编排和运行时无需增加名称分支。接口与逐步验收见[第三方编译器适配与注册](17-第三方编译器适配与注册.md)。

<a id="validation"></a>

## 10. 验证选项确实有效

每次改注册或构建逻辑，至少检查三种配置、干净安装与独立消费者。重点不是能否打印一个开关，而是：none 不执行适配器 probe；选中模式确实链接工厂并安装对应资源；缺失依赖明确失败；Core 消费者无反向适配依赖；旧包和缓存不能绕过允许集合。

当前测试用非 Triton 的边界夹具直接调用 Core，用不同物理 ABI 的 LLVM kernel 验证 CUDA 后端，并另外运行真实 Triton 的导出、融合和 GPU 数值测试。测试替身验证接口，真实编译器测试验证接入，两者都保留。
