# 02. 前端接入与构建配置

返回核心思想：[构建、绑定与适配器白名单](核心思想.md#ask-frontend-build) · 相关细节：[ASK IR 与数值语义](01-ASK-IR与数值语义.md) · [外部编译器适配与边界内联](04-外部编译器适配与边界内联.md) · [工程结构与测试体系](06-工程结构与测试体系.md)

ASK 提供进程内 Python SDK（基于 `nanobind`）、独立 C++ 库（`ASK::Core`）以及命令行工具 `ask-opt`。

<a id="build-workflow"></a>

## 1. 依赖获取与 CMake 构建

构建需要 C++17 编译器、CMake 3.28+、Ninja 和 Python 3.10+（含开发头文件）。LLVM/MLIR（`23.0.0git` 指定提交，与 Triton 3.7.1 上游 LLVM 版本一致）和 `nanobind`（`3.1.0`）锁定在 `cmake/llvm.lock.json` 与 `cmake/nanobind.lock.json` 中。

```bash
python3 tools/fetch_deps.py
cmake --preset core
cmake --build --preset core
ctest --preset core
```

- `tools/fetch_deps.py` 默认准备 `llvm` 与 `nanobind`，支持 `--only llvm` 或 `--only nanobind`。脚本会校验归档 SHA-256、检查压缩包路径与软链，并在 `.deps/<dir>/` 下记录收据文件（`.ask-sdk.json` / `.ask-nanobind.json`），已就绪时直接复用。
- `CMakeLists.txt` 根据 `cmake/llvm.lock.json` 自动在 `.deps/` 下定位 `LLVM_DIR` 与 `MLIR_DIR`；使用外部同修订 LLVM 安装时可通过 `-DLLVM_DIR` / `-DMLIR_DIR` 覆盖。

将 ASK 安装到 Python 虚拟环境（如 [FugaTensor 的 `tools/bootstrap.py`](../../fugatensor/docs/architecture/04-ASK桥接与多后端执行.md#bootstrap-and-config)）：

```bash
python -m pip install . --no-deps --no-build-isolation \
  -Ccmake.define.ASK_THIRD_PARTY_COMPILERS=all
```

## 2. 构建预设与第三方编译器白名单

`CMakePresets.json` 定义三个构建预设：

| Preset | `ASK_THIRD_PARTY_COMPILERS` | 作用 |
| --- | --- | --- |
| `core` | `none` | 自有 CPU + 自有 CUDA 编译与运行时，不依赖 Triton、PyTorch 或 NumPy。 |
| `triton` | `triton` | 在 `core` 基础上编译并注册 `adapters/triton/` C++ 边界校验器、worker 与专属测试。 |
| `all` | `all` | 启用 `adapters/registry.json` 中登记的全部第三方编译器适配器。 |

构建选择规则见 `cmake/AskCompilerSelection.cmake` 与 `cmake/AskCompilerRegistry.cmake`：

- 启用哪些适配器仅由 `ASK_THIRD_PARTY_COMPILERS` 和 `adapters/registry.json` 决定；环境中装有 `triton` 包不会在 `core` 构建中被自动引入。
- 配置 `triton` 或 `all` 预设时（如 `cmake --preset all -DPython_EXECUTABLE=/path/to/.venv/bin/python`），`adapters/triton/CMakeLists.txt` 默认将 `ASK_TRITON_PYTHON_EXECUTABLE` 设为 `${Python_EXECUTABLE}`；仅在 SDK 与 Triton worker 分属不同虚拟环境时才需单独指定 `-DASK_TRITON_PYTHON_EXECUTABLE=...`。

## 3. Python SDK：进程内编译器与图构造

Python 接口位于 `python/ask/`，底层绑定为 `ask._native`（`bindings/`）：

```python
from ask import Compiler, Module, TensorType

module = Module()
t = TensorType((16,), "f32")
g = module.graph("axpy", inputs={"x": t}, results=[t])
two = g.splat(g.constant(2.0, dtype="f32"), (16,))
one = g.splat(g.constant(1.0, dtype="f32"), (16,))
g.return_(g.add(g.mul(g.inputs["x"], two, id="scale"), one, id="shift"))

compiler = Compiler()                 # 默认调用进程内 nanobind C++ 扩展
prepared = compiler.prepare(module)   # 类型/形状检查 + 标记提取擦除
optimized = compiler.optimize(module) # 常量折叠 + 死代码消除 + 逐元素融合分组
```

- **进程内调用与伴生 CLI 校验**：`Compiler()` 不传路径时在进程内创建独立 `mlir::MLIRContext` 执行 `prepare` 和 `optimize`。调用 `compile_cuda` 等依赖外部 CLI 的接口前，`Compiler._check_companion()` 会校验伴生 `ask-opt --capabilities` 与内存 `_native` 扩展的构建指纹一致。
- **CLI 模式**：传入 `Compiler("/path/to/ask-opt")` 切换到子进程 CLI 模式，返回相同的 `PreparedModule(ir, report)` 结构。
- **Python 示例**：
  - `examples/framework_frontend.py`：构造 `P -> Triton F -> Q` 计算图并输出 `prepare` 报告。
  - `examples/optimize_frontend.py`：常量折叠、无用分支消除与多输出融合分组。
  - `examples/triton_fused_gpu.py`：编译并在 GPU 上用 `ExecutionSession` 运行 `ASK -> Triton -> ASK` 融合核。

## 4. C++ 原生接入（`ASK::Core`）

C++ 宿主可通过 `find_package(ASK CONFIG REQUIRED COMPONENTS Core)` 链接 `ASK::Core`，直接调用 `include/ask/Frontend/Compiler.h` 中的 `ask::prepareModule`、`ask::optimizeModule` 与 `ask::capabilitiesJson`，无需依赖 Python 解释器。独立工程示例见 `examples/cpp/CMakeLists.txt` 与 `examples/cpp/frontend.cpp`。

## 5. `ask-opt` 命令行参数

| 参数 | 输入 → 输出 | 说明 |
| --- | --- | --- |
| `--capabilities` | 无 → JSON | 输出当前构建支持的后端、已启用适配器、主机 `bf16` 硬件支持与协议版本。 |
| `--prepare` | ASK MLIR → Prepared MLIR | 校验语义与形状、提取并擦除 `ask.mark`，配合 `--report-json` 输出准备报告。 |
| `--optimize` | ASK MLIR → Optimized MLIR | 在 `--prepare` 基础上运行常量/类型折叠、DCE 和逐元素融合分组（支持 `--no-constant-fold` / `--no-dce` / `--no-fusion`）。 |
| `--emit-llvm` / `--emit-object` | 纯自有 ASK MLIR → Host `.ll` / `.o` | 生成 CPU 共享循环 LLVM IR 或本机目标文件。 |
| `--emit-cuda-llvm` | 纯自有 ASK MLIR → NVPTX `.ll` | 按 `--cuda-arch <sm>` 与 `--cuda-block-size` 生成自有 CUDA kernel LLVM IR。 |
| `--fuse-external` | 含 `ask.external` 的 ASK MLIR → Fused NVPTX `.ll` | 调用外部适配器导出 LLVM IR，校验边界并内联前后自有算子。 |
| `--check-llir` / `--optimize-llir` | 原生 `.ll` → `.ll` | 验证或清理原生 LLVM IR（保留内联 PTX 与目标 intrinsic）。 |
