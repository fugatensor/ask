# 04. 外部编译器适配与边界内联

返回核心思想：[外部适配与通用值边界融合](核心思想.md#ask-external-fusion) · 相关细节：[ASK IR 与数值语义](01-ASK-IR与数值语义.md#external-declaration) · [图优化与自有代码生成](03-图优化与自有代码生成.md) · [常驻运行时与多级缓存](05-常驻运行时与多级缓存.md)

当计算图中包含 `ask.external`（例如 `P: t = x + 1 → F: Triton kernel → Q: y = u + 3`）时，ASK 需要调用外部编译器把 DSL 变成原生 LLVM IR，并在安全的前提下把前后自有计算 `P`、`Q` 融进 `F` 的同一个 GPU kernel 里，省去 `t` 和 `u` 落盘全局显存的往返带宽。

为了避免把外部编译器的版本细节硬编码进公共核心，ASK 将这套机制拆成**插件式适配器目录**与**编译器无关的通用 LLVM 值边界内联核心**两部分。

<a id="adapter-architecture"></a>

## 1. `adapters/<id>/` 插件式注册架构

所有第三方编译器专属代码都隔离在 `adapters/<id>/` 目录下，公共核心通过 `include/ask/Adapters/Compiler.h`（C++）与 `python/ask/adapters.py`（Python）按显式注册表调度：

- **`adapters/registry.json`**：中央白名单，仅记录允许构建的编译器 ID 到子目录名的映射（当前登记 `"triton": "triton"`）。
- **`adapters/<id>/registration.json`**：声明该适配器的协议版本、C++ `CompilerAdapter` 工厂符号、Python 策略工厂路径、独立导出 `worker` 脚本名以及兼容参数别名。
- **`adapters/<id>/dependencies.lock.json`**：锁定外部编译器包名、精确版本号（当前锁定 `triton==3.7.1`）及配套的 LLVM 提交哈希。

只有在 CMake 构建时通过 `ASK_THIRD_PARTY_COMPILERS` 显式选中的适配器才会被编译进 `ask_compilers` 静态库并写入构建期生成的注册表；公共层绝不扫描 Python `entrypoints` 或隐式 `import` 环境中偶然存在的包。关于 Triton 目录内部各文件的详细清单，也可参见 [`adapters/triton/README.md`](../adapters/triton/README.md)。

<a id="export-protocol"></a>

## 2. 跨进程导出协议与标准执行契约（ABI v2）

为什么导出外部 DSL 要走独立 `worker` 子进程（如 `adapters/triton/worker.py`）？因为外部编译器（如 Triton）往往绑定特定 Python 环境、带有全局编译缓存甚至环境变量要求。通过 JSON 请求/响应协议（`protocol_version = 1`）隔离后，宿主框架进程完全不必导入 Triton：

1. **请求（Request）**：包含 DSL 原文、`entry`、`signature`、`source_bindings`（如 `{"inp": "input:0", "out": "output:0"}`）、`constants`（如 `N`、`BLOCK`）、`options`（如 `num_warps`、`enable_fp_fusion`）、`target`（`arch`、`warp_size`）、`grid` 以及是否请求融合标记（`fusion.enabled`）。
2. **原子响应与标准契约（Artifact）**：worker 调用外部编译器的**公开 API**（对 Triton 3.7.1 为 `ASTSource` + `triton.compile` + `compiled.asm["llir"]`）导出原生 LLVM IR，经临时文件原子替换写出 JSON 产物。产物向公共层交付统一的 **`invocation` v2 执行契约**：
   - `payload` / `entry`：原生 LLVM IR 文本与物理 kernel 函数名。
   - `port_map`：逻辑端口（`input:0`、`output:0`）到物理参数序号、形状、`element_type` 和连续行主序布局的映射。
   - `invocation`：`version = 2`、`kind = "cuda-kernel"`、`grid` `[gx, gy, gz]`、`block` `[bx, by, bz]`、`shared_bytes` 以及完整物理参数列表（例如 Triton 3.7.1 自动追加的未使用 scratch 指针会被验证并显式绑定为 `"null"`，公共 CUDA 运行时只需按列表填参，无需写死“Triton 有 4 个参数”）。
   - `required_element_types`：包括端口类型及从 `ttir` 中真实识别出的内部 `bf16` 依赖，防止在低于 `sm_80` 的显卡上带病运行。

<a id="boundary-inliner"></a>

## 3. 通用 LLVM 值边界内联核心（`lib/LLIR/Inline.cpp`）

`include/ask/LLIR/Inline.h` 与 `lib/LLIR/Inline.cpp` 是纯粹的 LLVM IR 变换引擎，里面没有任何一行 Triton 专属判断。它接收两样东西：

1. **已确认的值边界（Value Boundary Sites）**：指明外部 `llvm::Module` 中哪些指令站点代表逻辑输入刚读入后的值（`input` 站点），哪些站点代表逻辑输出即将写出前的值（`output` 站点），支持单参数或多参数、标量（整数/浮点/`i1`）与定长向量（当外部编译器生成向量化 `ld.global.v2` / `v4` 时，同一逻辑边界可对应多个站点）。
2. **ASK 生成的 Typed Helper 模块**：由 `lib/LLIR/Fuse.cpp` 将外部算子前驱 `P` 和后继 `Q` 的 ASK 自有子图编译成无内存副作用、无分支外溢的纯值变换 LLVM 函数（例如 `@ask_pre_helper(val)` 与 `@ask_post_helper(val)`）。

内联核心在**克隆出的模块副本**上按严格顺序工作：

1. 校验 helper 模块只含纯计算指令（禁止非法全局访存、未知外部调用或越界副作用），校验每个边界站点的 LLVM 类型与 helper 签名精确匹配，并检查支配关系（Dominance）。
2. 将 helper 模块链接进外部模块副本，在所有输入边界站点后将原始值替换为 `call @ask_pre_helper(raw)`，在所有输出边界站点前将待写出值替换为 `call @ask_post_helper(computed)`。
3. 内联全部 helper 调用，移除恒等追踪标记指令，并对新模块运行 `llvm::verifyModule`。
4. **原子回滚保证**：上述任一环节若失败，直接丢弃副本、保持输入 `llvm::Module` 分毫未改，并返回明确诊断。

<a id="triton-fusion"></a>

## 4. Triton `P → F → Q` 融合证明顺序

固定 `F` 的线程布局和访存方式不变、让 ASK 的 `P` 和 `Q` 去适应 `F` 的寄存器值流——这是 ASK 跨编译器融合最核心的工程决策。具体到 Triton 适配器（`adapters/triton/fusion.py` 与 `adapters/triton/lib/TritonBoundary.cpp`），融合前必须依次通过四道关卡：

1. **AST 静态数据流证明**：解析用户 `@triton.jit` 源码，确认入口只对绑定为 `input:0` 的指针做一次带掩码 `tl.load`，经纯逐元素表达式（允许局部变量重绑定、仿射偏移别名、位置/关键字参数及显式 `.to(...)` 类型转换）后，用**完全等价的偏移与掩码**对 `output:0` 指针做一次 `tl.store`；不含跨线程 `tl.sum` / `tl.dot` / 原子操作或共享内存交换。
2. **公开 API 注入恒等位标记与双编译比对**：在 load 结果后和 store 值前通过 Triton 公开的 `tl.inline_asm_elementwise` 插入只复制位的恒等内联汇编标记（`bool` 用 `mov.pred`，16/32/64 位分别用 `mov.b16` / `mov.b32` / `mov.b64`）。worker 同时编译**未加标记的原版 DSL**与**加标记版 DSL**，比对两者的 `ttgir` blocked layout、`num_warps`、`shared_bytes` 和物理参数签名完全一致——证明标记没有扰动 Triton 的布局与寄存器规划。
3. **C++ 原生边界与掩码等价校验（`TritonBoundary.cpp`）**：在 LLVM IR 层回溯每个标记站点的指针地址计算与 `pred` 掩码条件，按真实元素字节宽度证明其恰好对应 `0 <= idx < N` 的连续线性元素边界，不越界污染尾块元素。
4. **交由通用内联器合入 `P` 与 `Q`**：校验通过后调用上一节的 `inlineValueBoundaries` 内联 `P`/`Q` helper 并抹除标记；最终产物的输入/输出端口形状更新为整个 ASK 图的真实多维形状，整条 `P → F → Q` 链在 GPU 上只需一次 `cuLaunchKernel`。

<a id="fma-and-numerics"></a>

## 5. 跨编译器浮点收缩（FMA）与转换语义隔离

把 `P`、`F`、`Q` 放进同一个 `llvm::Module` 交给 `llc` 时，有一个极易踩坑的数值细节：**Triton 默认允许浮点乘加融合成 FMA（`enable_fp_fusion=True`），而 ASK 自有的 `P` 和 `Q` 默认禁止 FMA（要求乘法和加法各自独立 RNE 舍入）。** 如果简单地给 `llc` 传 `-fp-contract=fast`，`P` 和 `Q` 里的 `a * b + c` 就会被误融合成 FMA；反过来如果传 `-fp-contract=off`，又会剥夺用户 Triton kernel `F` 原本开启的 FMA 优化！

ASK 在 `TritonBoundary.cpp` 中精确解决了这个问题：

- 在内联 `P`、`Q` **之前**，适配器按 `F` 自身的 `enable_fp_fusion` 策略，只给 `F` 原有的 LLVM 浮点指令显式打上或清除 `contract` fast-math 标志；
- ASK 为 `P`、`Q` 生成的 helper 指令不带 `contract` 标志；
- 最终调用 `llc` 时统一使用 **`-fp-contract=on`**（仅对带有 `contract` 标志的指令允许生成 `fma.rn`）。

这样在同一条融合后的 PTX kernel 里，`F` 的乘加照常生成硬件 FMA（当用户设置 `enable_fp_fusion=False` 时则严格不生成 FMA），而 `P` 和 `Q` 的乘加以及饱和类型转换始终严守 ASK 的数值定义，两边互不干扰。
