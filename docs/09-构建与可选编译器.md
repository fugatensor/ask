# 构建 ASK 时选择哪些第三方编译器

[返回顶层设计：工程约束](核心思想.md#ask-engineering) · [工程组织](06-工程组织与验证.md) · [文档目录](README.md)

这里的第三方编译器指 Triton 这一类：接收框架提供的 DSL，为 `ask.external` 生成实现。LLVM/MLIR 是 ASK 自身的基础设施；CPU、CUDA 等是代码生成和执行后端。三者分别管理。

仓库已有 CMake 工程与编译器初稿：实现了编译器选择、原生 ASK IR 准备、nanobind Python 绑定及 Triton worker。本文仍包含后续安装、运行时和多后端设计；当前可执行步骤见[仓库 README](../README.md)，前端子集见[上层框架接入](10-上层框架接入.md)。LLVM/MLIR 版本以仓库锁定记录及配置检查为准。

<a id="selection"></a>

## 1. 用一个选项表达三种选择

构建系统采用 CMake，常用生成器为 Ninja。第三方编译器使用一个字符串选项：

```text
ASK_THIRD_PARTY_COMPILERS = none | all | <compiler-id>[;<compiler-id>...]
默认：none
```

| 配置 | 含义 |
|---|---|
| `none` | 保留 ASK 核心、Python API 和原生绑定；不接入任何第三方编译器 |
| `all` | 启用当前源码版本的支持名录中的全部真实适配器 |
| `triton` | 只启用 Triton |
| 用分号分隔的名称列表 | 将来支持多个编译器后，启用指定集合 |

**Python 绑定是基础组成，不设独立开关。** `none`、`all`、`triton` 都构建、安装和测试它；`none` 只裁剪 Triton 这类 DSL 编译器，不裁剪框架接入接口。

首期只实现 Triton，因此它实现并进入支持名录后，`all` 与 `triton` 展开成同一集合。`all` 不表示已经支持所有深度学习编译器，也不包括计划中的适配器或测试替身。新适配器进入名录后，升级源码再选择 `all` 才会把它加入；正式发布要记录展开后的具体集合。

名称使用注册表中的小写 ID。允许去掉每项首尾空白，重复 ID 去重，再按名称排序。空字符串、空列表项、未知 ID，以及 `none;triton`、`all;triton` 这样的混用一律报错。不能把拼错的名称当成关闭支持。

不再同时设置 `ASK_ENABLE_TRITON` 一类独立布尔开关，否则列表与布尔值会出现两份冲突配置。CMake cache 的 `STRINGS` 属性只作为 GUI 提示，真正的校验由 ASK 完成。[CMake cache 字符串](https://cmake.org/cmake/help/latest/command/set.html)、[STRINGS 属性](https://cmake.org/cmake/help/latest/prop_cache/STRINGS.html)

## 2. 开发者怎样配置

准备匹配的 LLVM/MLIR、Python 解释器与开发文件，以及锁定的 nanobind 后，在仓库根目录使用以下形式。`LLVM_DIR`、`MLIR_DIR` 通过本机配置指定，示例省略其重复部分。`Python_EXECUTABLE` 选择基础绑定的解释器；它必须有匹配的开发文件。锁定源码由 `python3 tools/fetch_nanobind.py` 显式获取，版本与校验值见 [nanobind.lock.json](../cmake/nanobind.lock.json)。

```bash
# 只构建 ASK 自身
cmake -S . -B build/core -G Ninja \
  -DASK_THIRD_PARTY_COMPILERS=none
cmake --build build/core

# 启用全部已支持编译器；各编译器的环境须已按锁定记录准备
cmake -S . -B build/all -G Ninja \
  -DASK_THIRD_PARTY_COMPILERS=all \
  -DASK_TRITON_PYTHON_EXECUTABLE=/opt/ask-envs/triton/bin/python
cmake --build build/all

# 只启用 Triton
cmake -S . -B build/triton -G Ninja \
  -DASK_THIRD_PARTY_COMPILERS=triton \
  -DASK_TRITON_PYTHON_EXECUTABLE=/opt/ask-envs/triton/bin/python
cmake --build build/triton
```

目标后端单独选择：`ASK_TARGET_BACKENDS` 默认 `host`，当前实现只接受 `none` 或 `host`；完整列表接口及集成式 CUDA 代码生成 target 尚未实现。基础 C++ CUDA 运行时已包含在所有模式中：按需加载驱动，不要求构建机安装 CUDA SDK；GPU 代码生成目前通过显式指定的 LLVM `llc` 与 `ptxas` 完成。`host` 选择构建机器架构的 ASK 自有代码生成；完整混合图调度另行实现。`none` 保留 IR 检查与分析，不能生成 host 代码。将来 CUDA 后端落地后，配置形式计划为：

```bash
cmake -S . -B build/triton-cuda -G Ninja \
  -DASK_THIRD_PARTY_COMPILERS=triton \
  '-DASK_TARGET_BACKENDS=host;cuda' \
  -DASK_TRITON_PYTHON_EXECUTABLE=/opt/ask-envs/triton/bin/python
```

列表整体加引号，避免 shell 把分号当作命令分隔符。选择 Triton 不自动开启 CUDA；选择 CUDA 也不自动安装 Triton。CUDA 后端要求的 LLVM target、SDK 和代码生成工具必须检查，运行设备与驱动则在运行阶段检查。构建通过不代表机器上已有可用 GPU。

仓库预设提供 `core`、`triton`、`all`，分别使用上述独立构建目录。建议最低 CMake 3.28，预设使用 schema 6 中已有的功能；本机路径写入不入库的 `CMakeUserPresets.json`。最低工具版本随锁定 LLVM/MLIR 的要求提高，不跟随开发机上碰巧安装的版本变化。[CMake Presets](https://cmake.org/cmake/help/latest/manual/cmake-presets.7.html)

## 3. 无第三方模式仍然能做什么

`none` 保留 Python API、nanobind 原生绑定、ASK IR、形状推导、自有 lowering、原生 LLVM 导入与验证、通用 Pass、产物格式，以及选中的目标后端。全部由 ASK 自有操作组成的图，可以沿 A/B/C 层正常编译。构建仍需要 LLVM/MLIR、Python 开发文件和 nanobind；缺少其中一项就配置失败，不悄悄生成缺少 Python 接口的安装包。

解析 ASK IR 时保留 `ask.external` 的定义，因而可以读图、检查类型和报告诊断。但要编译一张包含 `compiler_id="triton"` 的图，驱动先检查本次构建是否启用了 Triton；未启用就返回 `CompilerNotEnabled`，指出 external 节点和所需 ID。这一步发生在加载 DSL、启动 worker 和查询外部编译缓存之前。

三个入口要区别处理：

| 请求 | `none` 下的规则 |
|---|---|
| 编译含 Triton external 的 ASK IR 与 DSL | 拒绝，需要支持该编译器的构建 |
| 导入一份来源是 Triton 的 LLVM 文件 | 允许；producer 是来源记录，不会触发 Triton 加载 |
| 加载已编译的 `ExecutablePackage` | 由其 ABI、后端和运行依赖决定，不要求重新编译源 DSL |

最后一项要求包内有代码、参数与启动说明，并由 ASK 的 loader/launcher 独立执行。如果只有 Triton 的 `CompiledKernel` 对象或 Python launcher 闭包，就仍依赖 Triton，不能作为独立运行时产物交付。

同样，Triton Kernel Override 会调用 Triton，属于启用该集成后的验证路径。`none` 的 LLVM 代码生成要使用独立 ASK 后端，不能绕去调用 override。具体路径见[代码生成与运行时](05-代码生成与运行时.md)。

## 4. 依赖方向决定选项是否真的有效

ASK 核心不反向链接某个编译器适配器。工具使用同一份通用进程代理，按明确的组件清单连接选中的 worker；目标后端通过自己的接口装配。

```text
ask-compile / 对外编译 API 的装配层
  ├─ Python API -> nanobind 扩展 -> ASK 编译与运行时公开接口
  ├─ ask_pipeline -> ask_ir, ask_shape, ask_llir, ask_adapter_protocol
  ├─ ask_runtime + 选中的 target backends
  └─ 通用 process exporter
         └─ 仅选中的 worker 描述 -> IPC -> 各编译器独立 worker
```

| 构建部分 | 依赖 | `none` 时 |
|---|---|---|
| ASK IR、分析、自有降级与 LLVM Pass | 锁定的 LLVM/MLIR SDK | 保留 |
| `ask_adapter_protocol` | ASK 请求、DSL 来源和 LLIRArtifact 数据格式 | 保留，不依赖某个编译器 |
| `ask_exporter_triton` | 验证并打包 Triton worker 与组件说明的目标 | 不创建 target |
| Triton worker | 独立 Python 环境中的锁定 Triton | 不查找、不导入、不安装 |
| 目标后端 | 对应 LLVM target、目标工具和运行时接口 | 按 `ASK_TARGET_BACKENDS` 选择 |
| ASK 原生 Python bindings | 锁定 nanobind、Python Interpreter 与 Development.Module | 必需；与 all/triton 相同 |

Triton worker 与 ASK 的 Python 绑定是两件事。框架侧通过 nanobind 调用 ASK 的 C++ 编译入口和常驻运行时，绑定依赖核心，核心不反向依赖绑定。外部 DSL 仍通过 `export(request)` 的进程代理交给独立 worker，不在框架进程里导入 Triton。显式指定 `ask-opt` 的客户端路径继续用于 CLI 调试与兼容。实际接口见[框架接入](10-上层框架接入.md)和[设备执行](16-Python绑定与常驻运行时.md)。

首期编译器差异放在组件说明和 worker 中，`ask_exporter_triton` 不要求产生一份 Triton C++ 共享库。CLI 按已安装清单建立通用代理，不静态引用 `TritonAdapter` 符号；因此只安装 Core 时不会留下必须由 Triton 组件解析的链接依赖。通用进程通信代码的存在，也不意味着 none 模式允许启动未启用的编译器。

完整源码构建必须准备 Python 的扩展模块开发文件和 nanobind；构建时还可能使用 lit、`llvm-tblgen`/`mlir-tblgen`。这里构建的是由 Python 加载的扩展，不要求把解释器嵌入 C++。安装后的纯 C++ 调用方使用 `ASK::Core` 时不必初始化或加载 Python，也不需要 Triton。[LLVM 构建要求](https://llvm.org/docs/GettingStarted.html#software)、[MLIR Python bindings](https://mlir.llvm.org/docs/Bindings/Python/)

CMake 只在选中适配器后进入它的子目录，在子目录内查找该适配器的依赖。`EXCLUDE_FROM_ALL` 不够，因为它仍会执行子目录配置。核心公开头文件不出现 Triton 类型；依赖通过具体 target 声明，不用全局 include/link 路径。`PRIVATE` 也不等于彻底隔离依赖：静态库的实现依赖仍可能需要最终链接器解析，所以隔离主要靠 target 结构和进程边界。[add_subdirectory](https://cmake.org/cmake/help/latest/command/add_subdirectory.html)、[target_link_libraries](https://cmake.org/cmake/help/latest/command/target_link_libraries.html)

## 5. 配置时先算清集合，再查依赖

顶层配置按固定顺序执行：读支持名录；解析选择；定位 LLVM/MLIR、Python 与 nanobind；检查所选目标；只验证所选编译器环境；创建对应 targets；生成配置摘要。选中的必需依赖缺失或平台不受支持时直接失败，不把 `all` 静默缩成“机器上能找到的那些”。

支持名录由仓库显式维护，不扫描 `adapters/` 目录猜测，也不 import 插件来询问其身份。每项记录 compiler ID、适配器目录、协议版本、支持平台和兼容记录。只有实现及必要验收已完成的条目才能进入 `all`；测试 mock 放在测试目录，不进入这张表。

选择器在 `cmake/AskCompilerSelection.cmake` 中实现，独立完成以下解析步骤：

```cmake
function(ask_resolve_compilers requested supported output)
  if("${requested}" STREQUAL "")
    message(FATAL_ERROR "ASK_THIRD_PARTY_COMPILERS must not be empty")
  endif()
  set(ids "")
  foreach(raw IN LISTS requested)
    string(STRIP "${raw}" id)
    if("${id}" STREQUAL "")
      message(FATAL_ERROR "Empty compiler ID")
    endif()
    list(APPEND ids "${id}")
  endforeach()
  list(LENGTH ids count)
  if(count EQUAL 1 AND "${ids}" STREQUAL "none")
    set(selected "")
  elseif(count EQUAL 1 AND "${ids}" STREQUAL "all")
    set(selected "${supported}")
  else()
    foreach(id IN LISTS ids)
      if("${id}" STREQUAL "none" OR "${id}" STREQUAL "all")
        message(FATAL_ERROR "none/all must be used alone")
      endif()
      if(NOT id IN_LIST supported)
        message(FATAL_ERROR "Unknown compiler '${id}'; supported: ${supported}")
      endif()
    endforeach()
    set(selected "${ids}")
  endif()
  list(REMOVE_DUPLICATES selected)
  list(SORT selected)
  set(${output} "${selected}" PARENT_SCOPE)
endfunction()
```

顶层将 `ASK_THIRD_PARTY_COMPILERS` 声明为默认值 `none` 的 `CACHE STRING`，不使用 `FORCE` 覆盖调用方。函数输出 `ASK_ENABLED_COMPILERS` 后，只对其中的 ID 执行 `add_subdirectory`。将展开值写入 manifest，不反过来覆写用户的 `all` 请求值。[CMake list](https://cmake.org/cmake/help/latest/command/list.html)

LLVM/MLIR 采用同一锁定工具链，通过 `find_package(LLVM CONFIG REQUIRED)` 与 `find_package(MLIR CONFIG REQUIRED)` 定位实际安装包，消费其提供的 targets。检查版本、构建选项、ABI 和需要的目标组件；两个 package 能找到，不代表可以把不同构建的库混用。[LLVM 的 CMake 接入](https://llvm.org/docs/CMake.html#embedding-llvm-in-your-project)

## 6. 每种编译器独立准备环境

启用 Triton 时，`ASK_TRITON_PYTHON_EXECUTABLE` 必须指向本次使用的解释器。配置脚本只用它检查锁定的 Python/Triton 版本、worker 协议和所需公开接口；不改基础绑定所用的 Python 解释器，也不把 worker 环境拿来解析 Python 开发库，更不会悄悄换成系统环境。基础绑定的解释器与 worker 的解释器可以不同。检查导出接口不能以执行一次 GPU kernel 为前提。

`all` 将来可能包含依赖不同 Python 或原生库的编译器，因此每个编译器有自己的环境路径与 worker。它们向 ASK 传递源码包、版本化说明和 LLVM 文本/bitcode，不共享进程内编译器对象或 `llvm::Module*`。

构建默认只检查已准备的依赖，不联网下载、不在配置过程中执行 `pip install`。环境创建与依赖安装是显式准备步骤，使用仓库锁定记录；部署机器按相同记录重新创建环境。venv 通常不能直接搬到另一目录或机器，安装包不把构建机的绝对解释器路径当成长期可用路径。[Python venv](https://docs.python.org/3/library/venv.html)

框架侧的 `DSLSource` 必须能在 worker 中解析。若上层传入 callable，客户端先通过受支持的方式提取源码、入口、捕获的编译期值与依赖，组成有摘要的源码包。不能提取就明确报不支持；对象地址、`repr` 或任意 pickle 不能替代跨进程源码约定。接口定义见[第三方接入 API](08-第三方LLIR接入API.md)。

锁定记录分别保存 ASK LLVM/MLIR 修订、nanobind 版本与源码摘要、构建工具要求，以及每个 worker 的 Python、编译器、适配器和依赖版本。兼容记录还包括生产者 LLVM、ASK reader、IR 格式、目标代码生成工具与已跑过的验证。进程隔离能避免原生库直接冲突，不能保证不同版本的 LLVM IR 互读。[LLVM IR 兼容政策](https://llvm.org/docs/DeveloperPolicy.html#ir-backwards-compatibility)

这些版本要由真实导出、导入和执行测试确定。本文不填一组未经验证的 LLVM/Triton 版本来冒充支持承诺；首个实现落地时，版本锁定及对应测试结果必须一起提交。

## 7. 注册、安装和诊断使用同一份选择结果

配置完成生成构建清单，至少包含：

```text
build_id
requested_compilers          // none、all 或原始列表
enabled_compilers            // 已展开、排序的 ID 与适配器版本
target_backends              // 与编译器集合分别记录
adapter_protocol_version
toolchain_and_dependency_lock_digest
python_bindings_enabled     // 所有合法构建均为 true，不是另一个选择开关
python_bindings             // nanobind
nanobind_version
python_abi
```

安装后可以查询“这个构建启用了什么”，运行时再检查“选定环境现在能否使用”。Triton 环境被移走时，结果是已启用但环境缺失；GPU 驱动暂不可用时，报告执行环境不可用。两者都不能偷偷修改出厂的启用集合。

`register_exporter(id, version, export)` 的类型与 SDK 可以保留，但注册必须匹配构建的允许清单。`none` 中注册 Triton 返回 `CompilerNotEnabled`；指定模式不加载其他 ID。默认不扫描 Python entry points 或用户插件目录，即使系统安装了 Triton，也不会重新启用被裁掉的支持。

后续新增第三方集成仍只需实现导出回调，再把它的 ID、来源和环境要求显式加入构建名录。测试替身通过测试专用注册环境使用。这是功能配置约定，不宣称能隔离恶意插件代码。

## 8. 安装包不能重新引入未选择的依赖

安装分为 Core、目标后端和各编译器集成组件。Core 包含 Python 包与原生扩展，不另设可关闭的 Python 组件。Core 不携带 Triton worker，也不在其 package 配置中查找 Triton。目标后端只引入自己的代码生成和运行依赖。每个已选择的编译器集成安装 worker 代码、组件与协议说明及环境锁定记录，部署时再绑定实际环境路径。通用进程代理属于核心基础设施。

CMake 的构建选择、安装 `COMPONENT` 和下游 `find_package` 的组件是三件事，必须分别实现。关闭适配器时不创建其 target；安装组件只筛选已经存在的安装规则；ASK 包配置按请求加载对应 targets 或检查组件数据。Core 与可选的原生库拆分 export set；首期 Triton 组件主要是 worker 和说明文件，不必伪造一份可链接库。不能让 Core 的 export 文件强迫寻找未安装的可选组件。[CMake 安装与导出](https://cmake.org/cmake/help/latest/command/install.html#export)、[可迁移 package 配置](https://cmake.org/cmake/help/latest/module/CMakePackageConfigHelpers.html)

例如未来的下游用法是：

```cmake
find_package(ASK CONFIG REQUIRED COMPONENTS Core)
target_link_libraries(my_tool PRIVATE ASK::Core)
```

这个消费路径可以需要匹配的 LLVM/MLIR 开发包，但不能要求 Triton，也不能强迫 C++ 消费者链接 Python 解释器。若请求未安装的 CompilerTriton 组件，则明确失败。已有可独立执行的产物通过 runtime/backend 加载，不经编译器组件。

安装清单还要反映实际安装的组件：启用清单取构建允许集合与安装组件的交集。仅安装 Core 时，安装后的有效编译器集合为空，不得照抄构建树中 `all` 的完整注册表；组件匹配还要核对同一 build ID 和协议版本。

开发时默认使用不同构建目录与安装前缀。同一目录由 triton 切到 none 时，重新生成 targets、测试、清单和注册表；Python 绑定始终保留；旧适配器文件即使仍留在磁盘上也不得被自动发现。普通安装不会自动删除旧前缀中的遗留文件，发布包应在干净 staging 目录生成，或由包管理器按组件卸载。

## 9. 仓库中各文件负责什么

下面是完整目标布局；当前文件以仓库为准，部分组件注册表、清单和安装分层仍待补齐：

```text
CMakeLists.txt                       # 解析选项，查核心依赖，装配目标
CMakePresets.json                    # core / triton / all，共用基础配置
cmake/AskCompilerSelection.cmake     # 选择器与错误诊断
cmake/AskCompilerRegistry.cmake      # 真实适配器的支持名录
cmake/AskToolchain.cmake             # LLVM/MLIR 与构建选项检查
cmake/ASKConfig.cmake.in             # 按安装组件加载 targets
cmake/dependencies.lock.json         # ASK 工具链及兼容记录的索引
bindings/                           # 必需的 nanobind 薄绑定
python/ask/                         # 构图 API、设备张量与编译客户端
adapters/triton/CMakeLists.txt       # 仅选中后处理本适配器
adapters/triton/worker/              # 公开 DSL 编译与 LLIR 导出
adapters/triton/requirements.lock    # worker 环境的锁定依赖
backends/<target>/CMakeLists.txt     # 独立目标后端
tests/build-config/                 # 选项、隔离、安装与切换验证
```

将来加入新的编译器时，增加适配器目录、锁定记录和名录项，再接入相同测试。核心 CMake 不出现一串按编译器名称拼接私有库路径的分支。运行时的 external 编译流程保持[原设计](03-B层多源降级与低层归一化.md)：检查 ASK IR 中的实现引用，再把 DSL 路由到已启用的导出器。

<a id="verification"></a>

## 10. 怎样证明三个模式确实不同

| 构建或环境 | 必须验证的结果 |
|---|---|
| none，完全没有 Triton | 原生扩展能 import；自有图通过进程内入口准备/优化，LLVM 导入通过；编译 Triton external 明确拒绝 |
| none，系统恰好装有 Triton | 仍不查找、导入、安装或注册它；构建结果不因环境变化而多出适配器 |
| triton，指定锁定环境 | 只生成对应代理和 worker，能编译提交的 DSL 并导出真实 LLIR |
| triton，依赖缺失或版本不匹配 | 配置失败，给出解释器和缺失项，不退回 none |
| all | 包含相同基础绑定；编译器集合恰好等于支持名录；其中一项必需依赖缺失就失败 |
| 任一模式缺少 Python 开发文件或 nanobind | 配置失败，不跳过绑定 |
| 非法值与多项列表 | 拒绝未知 ID、空项和混用；去重与排序确定 |
| triton → none → triton | 更新清单、targets 与测试，旧安装文件或缓存不能偷偷启用适配器 |
| 单独安装并消费 Core | 安装后的 Python 扩展可用；C++ 可独立链接且运行时不加载 Python/Triton |
| 支持目标的 none 构建加载独立执行包 | 不 import 原编译器；由实际后端完成加载和调用 |

选择器可以用虚拟名录测试多个名称的集合运算，但虚拟条目不进入生产支持清单，也不算支持了第二个编译器。首次只有 Triton 时，all 与 triton 相同是预期行为。

无 GPU 的 CI 跑配置、核心、协议和安装测试；有目标设备的 CI 再跑真实 Triton DSL → LLVM → ASK 代码生成 → 执行。真实执行未跑要明确标记，不能拿 mock 或配置成功替代。关闭第三方支持的核心构建也不能被迫运行 Triton 测试。

外部图编译在查缓存前仍检查 compiler ID 是否启用。离线 LLVM 和独立执行包则按内容、ABI、工具链及目标兼容性验证缓存，不因 producer 恰好叫 triton 就全部拒绝。这样裁剪的是编译器集成，正常的统一 LLVM 处理能力仍然保留。
