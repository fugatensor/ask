# 第三方编译器适配与注册

[返回顶层设计：B 层](核心思想.md#ask-b) · [构建选择](09-构建与可选编译器.md) · [产物契约](08-第三方LLIR接入API.md) · [文档目录](README.md)

ASK 的核心不应该知道 Triton 的 `BLOCK`、`num_warps` 或 PTX 标记格式。它需要知道的是：该找谁编译 DSL，返回的 LLVM 入口怎样调用，以及一次优化所需的边界是否已经得到证明。本章描述当前代码怎样把这些职责拆开。

目前真实适配器仍只有 Triton。接口用非 Triton 的 C++ 边界夹具和直接编写的 LLVM GPU kernel 验证过；这些测试不计入支持名录，也不表示已经接入第二种编译器。

## 1. 一种编译器，一个目录

```text
adapters/
  registry.json                 # 只登记 ID -> 目录
  triton/
    registration.json           # 工厂、协议、可选融合能力、Python 入口
    CMakeLists.txt              # 本适配器的依赖检查、目标、安装、测试
    worker.py                   # 在独立环境调用公开编译 API
    fusion.py                   # DSL 标记插入与来源证明
    python/__init__.py          # 环境检查、缓存身份、旧产物迁移
    include/ask/Adapters/...
    lib/TritonBoundary.cpp      # 识别并检查 Triton LLVM 边界
    dependencies.lock.json
    requirements.lock
    tests/                     # 本适配器的单元与集成测试
```

公共接口在 [Compiler.h](../include/ask/Adapters/Compiler.h) 和 [adapters.py](../python/ask/adapters.py)。LLVM helper 的构造与内联仍在 `lib/LLIR/`，CUDA 参数封送与执行仍在运行时。通用测试、上层示例可以使用 Triton，但不承载它的适配实现。

依赖方向是：

```text
ask-opt / _native
  ├─ ASK::Core       # ASK IR、形状、自有降级、通用 LLVM 变换
  ├─ ASK::Compilers  # 注册表 + 构建时选中的适配器对象
  └─ ASK::Runtime    # 设备、模块、张量和事件

选中的适配器 -> 独立 worker -> 第三方编译器
```

`ASK::Core` 不链接 `ASK::Compilers`。C++ 调用方可以只链接 Core，自己给 `fuseExternal` 传入一个适配器描述；也可以显式链接 Compilers，使用本次构建的注册集合。核心头文件不包含 Triton 类型。

## 2. 请求怎样走到适配器

上层先生成 ASK IR。`ask.external` 引用的实现记录包含 `compiler`、DSL 源码、源入口、源参数绑定、常量、目标和固定选项。`prepare` 检查图并产生 `external_requests`，此时不启动外部编译器。

`signature` 是 ASK 请求协议中的类型描述，使用 `i1/i32/i64/fp16/bf16/fp32` 及对应指针形式；适配器把它转换为自己编译器需要的签名。它不要求其他 DSL 接受 Triton 的类型对象。当前常量特化仍限于整数，grid 要求三个具体维度；这些是现有请求协议的范围。

真正导出时，驱动按请求中的 `compiler` 查注册表。它先检查 ID 是否启用，再解析环境和启动 worker。未启用的编译器不能靠系统中安装了同名 Python 包，或留下了旧缓存来绕过检查。

Python 调用按 ID 提供环境：

```python
from ask import Compiler, CompilerEnvironment

compiler = Compiler()
kernel = compiler.compile_cuda(
    module,
    compilers={
        "triton": CompilerEnvironment(
            python="/opt/triton-env/bin/python",
            worker="/path/to/ask/adapters/triton/worker.py",
        ),
    },
    llc="/path/to/pinned-llvm/bin/llc",
    ptxas="/path/to/ptxas",
    cache_dir="build/cache",
    output_dir="build/run-001",
)
```

`compile_cuda` 对含 external 的图使用单个 external 的逐元素融合路径；无 external 的基础图直接使用 ASK 自有 GPU 降级。环境参数已经不绑定 Triton；若以后注册另一个编译器，只需换 ID 和环境。它必须提供本入口需要的融合能力。仅导出 LLVM、不支持融合的适配器可用 `ask-opt --export-external`。

CLI 采用可重复参数，一张图中的多个 external 可以分别选择编译器：

```bash
build/triton/bin/ask-opt graph.mlir --export-external \
  --compiler-python triton=/opt/triton-env/bin/python \
  --compiler-worker triton="$PWD/adapters/triton/worker.py" \
  --export-dir build/export-001 -o build/prepared.mlir
```

Python worker 需要解释器；原生可执行 worker 可以不提供 `--compiler-python`。worker 接收 `--request FILE --output FILE`，读写 JSON，失败返回非零退出码。完整的请求和响应示例可查看一次导出生成的 `external-0.request.json` / `external-0.artifact.json`。

普通安装的 CLI 默认在前缀下的 `share/ask/adapters/<id>/` 找 worker；wheel 将配套 CLI 放在 `ask/_bin/`，worker 放在包内 `ask/share/ask/adapters/<id>/`。Python `CompilerEnvironment` 目前要求显式 worker 路径。构建树下使用 `PYTHONPATH=build/triton/python:python`，这样 SDK 能读到与原生构建一致的注册信息。

## 3. 先交付能调用的 LLVM，再考虑融合

worker 返回原生 LLVM 文本、实际入口、目标、参数映射和启动说明。公共驱动检查协议、源码摘要、固定配置、LLVM verifier 和物理函数签名，然后调用适配器的 `validateArtifact` 检查它自己的来源约定。源入口与降低后的 LLVM 符号可以不同。

CUDA 执行契约现在使用 `invocation.version = 2`：

| 字段 | 核心使用它做什么 |
|---|---|
| `port_map` | 逻辑端口到实际参数的映射；携带 `element_type`、具体 `shape` 和 `layout` |
| `invocation.arguments` | 按 LLVM 参数顺序封送；每项写明 `argument`、`llvm_type`、`binding` |
| `invocation.grid` / `block` | 启动的三维尺寸 |
| `invocation.shared_bytes` | 本次启动需要的动态共享内存字节数 |
| `codegen` | 标准化的 `fp_contract` 和 `ptx_version` |
| `required_element_types` | 包括中间计算类型；用于 BF16 等设备能力检查 |
| `producer_metadata` | 原编译器的附加信息；通用执行路径不解析 |

例如一个输出位于第 3 个物理参数的入口，可以写成：

```json
{
  "invocation": {
    "kind": "cuda-kernel", "version": 2,
    "grid": [2, 2, 2], "block": [3, 2, 2], "shared_bytes": 48,
    "arguments": [
      {"argument": 0, "llvm_type": "ptr addrspace(1)", "binding": "input:0"},
      {"argument": 1, "llvm_type": "ptr", "binding": "null"},
      {"argument": 2, "llvm_type": "ptr addrspace(1)", "binding": "output:0"}
    ]
  },
  "port_map": [
    {"argument": 0, "logical_port": "input:0", "element_type": "f32", "shape": [96], "layout": "contiguous_row_major"},
    {"argument": 2, "logical_port": "output:0", "element_type": "f32", "shape": [96], "layout": "contiguous_row_major"}
  ],
  "codegen": {"fp_contract": "off", "ptx_version": 80},
  "required_element_types": ["f32"]
}
```

这是执行字段片段，不是一份完整产物；对应 LLVM 函数必须真的有这三个指针参数。`null` 表示 ABI 明确允许传空指针，不会自动分配 scratch。

运行时不根据 `N` 推断元素个数，不根据 `num_warps` 推算 block，也不假设有两个尾部 scratch 参数。形状来自 `port_map`，物理参数来自 `invocation`。生产者适配器负责把自己的公开信息转换成这些字段。

高级执行 API 通过 `submit_many(inputs, outputs)` 支持多输入输出，各端口可有不同形状和存储类型，均采用连续布局。底层 Session 支持 1–64 个 64 位指针参数，可含明确的空参数，支持地址空间 0 和 1。按值标量参数及运行时 scratch 分配尚未实现。自有 GPU 图直接生成这套契约，见[第 19 章](19-自有GPU降级.md)；目前 Triton 高层融合路径仍有单输入、单输出及相同 shape/dtype 的边界证明限制，这不再是公共执行 API 的限制。

## 4. 融合接口只交付已经检查过的边界

接入一个编译器不要求支持融合。`registration.json` 的 `supports_fusion` 声明能力；实际请求仍必须逐次验证，不能用这个布尔值替代合法性证明。

原生 `CompilerAdapter` 有三个回调：

| 回调 | 输入与责任 |
|---|---|
| `validateArtifact` | 对照原始请求检查该编译器的产物、配置和来源证据 |
| `prepareFusion` | 在本次导入的 LLVM 模块中找边界；检查访问、mask 和数值规则，返回 `PreparedFusion` |
| `finalizeArtifact` | 融合后移走或作废只适用于原始 payload 的私有证明 |

`PreparedFusion.inputs/outputs` 中每个 `ValueBoundary` 提供：标记调用 `marker`、真正的数据 `value`、可选的 `predicate` 和 `passthrough`。通用核心不猜“标记第几个参数是值”，也不解析某种内联 PTX 字符串。

适配器要证明替换这些值不会改变 F 的访存和执行策略。Triton 的检查在它自己的目录内：识别源码、验证公开 identity 标记、核对地址和掩码，并把 F 隐含的数值许可落实到其 LLVM 指令。其他编译器可以用自己的标记和证明方法，不必伪装成 Triton 的 PTX 协议。

核心随后构造 ASK helper，验证类型、支配关系、helper 纯度和调用位置，再进行内联。规则见[通用 LLVM 值边界内联](13-通用LLVM值边界内联.md)。某个边界证明不了，就拒绝这次显式融合请求；当前 `compile_cuda` 不会自动建立多 kernel 回退计划。

`prepareFusion` 中的指针只属于本次导入的模块，不能存进缓存。融合后的形状快照由 ASK 图重新附加；旧 producer 证明不能继续声称自己描述了改写后的代码。`finalizeArtifact` 专门处理这一步。

## 5. 缓存也通过接口取得编译器差异

Python 的 `CompilerAdapter.cache_identity(request, environment, timeout=...)` 返回 `producer`、`adapter`、`dsl`、`target`、`numerics` 和 `config` 六项身份。适配器负责核对第三方环境、源码及它自己的脚本版本；不要把会改变产物的私有选项遗漏在键外。

通用编排再加入 ASK 图、形状快照、LLVM 修订、工具摘要、注册记录和环境摘要，交给同一个 IR 缓存。PTX/cubin 使用独立的可执行缓存。缓存失效规则不需要逐个编译器复制一遍，核心也无需了解 Triton 包怎样计算指纹。

生成的 v2 可执行产物可以在 `none` 安装中加载；加载只依赖目标、ABI 和硬件，来源名不会触发编译器导入。旧 v1 Triton 产物需要重新生成，或显式调用适配器的 `normalize_legacy_artifact` 验证并迁移。运行时不会为了猜测旧字段偷偷加载 Triton 适配代码。

## 6. 新增一个编译器的具体步骤

1. 新建 `adapters/<id>/`，放入 worker、Python 策略、原生描述、锁定记录和测试。ID 使用小写字母、数字和下划线，首字符为字母。
2. 写 `registration.json`：`id`、`native_factory`、`protocol_version`、`supports_fusion`、Python `module` / `factory`。Python 模块放在本目录的 `python/`，构建时安装为 `ask._adapters.<id>`。
3. `CMakeLists.txt` 检查自己的依赖，定义 `ask_adapter_<id>` OBJECT target，将自己的 worker/resources 安装到 `${ASK_ADAPTER_INSTALL_DIR}/<id>`，注册自己的测试。未选中时该文件不会执行。
4. 原生工厂返回 `CompilerAdapter`。只支持导出时保留 `prepareFusion=nullptr`，并声明 `supports_fusion=false`。Python 工厂返回同 ID 的 `CompilerAdapter` 子类。
5. 在 [registry.json](../adapters/registry.json) 加一条 ID 到目录的映射。通用 CMake 生成原生注册表和 Python 注册记录；不用修改 `gpu.py`、`Fuse.cpp` 或给运行时增加名称分支。
6. 先验证真实 LLVM 导出和独立代码生成；再测选中/未选中、错误环境、缓存身份、安装包。支持融合时另外测正确边界、拒绝错误边界及数值结果。

适配器可以只导出某个目标。换一个同样输出 NVIDIA LLVM 的生产者时复用 CUDA 后端；换成新的目标则需要另外实现代码生成与执行后端。目录隔离解决的是编译器接入，不能使目标相关的 intrinsic 或内联汇编跨硬件运行。
