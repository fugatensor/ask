# B 层：多源降级与低层归一化

[返回顶层设计：B 层](核心思想.md#ask-b)

B 层把 ASK 自有计算和外部编译产物放到同一低层表示中；能否执行、某个 Pass 能否优化，再分别检查。初稿已实现自有 i32 / f32 / f16 图到 host LLVM、Triton DSL 导出，以及独立的原生 LLVM 解析验证；本章还包含后续区域规划和完整产物管理。当前入口见[框架接入](10-上层框架接入.md)。

## 1. 从 A 层拿到什么

沿用下面这张图，`x`、`t`、`u`、`y` 都是一维 `i32` 张量，加法和乘法按模 `2^32` 计算：

```text
P: t[i] = x[i] + 1
F: u[i] = t[i] * 2       // 外部编译器提供
Q: y[i] = u[i] + 3
```

A 层接收上层框架已经生成的基础高层 ASK IR，再交付 `SemanticModule`、区域划分和输入约束；本次编译请求指定 `TargetProfile`。框架用 `ask.external` 标出第三方编译区域，并提供该编译器的 DSL 与实现引用。B 层需要为 P/Q 生成代码，并路由编译 F。第一步先保证三个入口可以顺序执行；消掉 `t`、`u` 是后续可选 Pass 的工作，不是接收 F 的前提。

ASK LLIR 在这里明确指**原生 LLVM IR**：文本 `.ll` 或 bitcode `.bc`，进入 ASK 后表示为 `llvm::Module`。第三方编译器内部可以使用 MLIR，也可以使用自己的 IR；只要最终输出符合约定的 LLVM IR，就走同一套接收流程。B 层不要求第三方采用相同的 dialect 或 Pass 顺序，但也不负责把任意上层 IR 或 LLVM IR 反向构造成第三方 DSL。

图拓扑仍在编译时固定。B 层生成的元素循环、条件和掩码属于算子内部实现，图级数据相关分支和循环由上层框架处理。首版使用静态形状，以后可以在相同图拓扑上支持符号维度。

## 2. 取得 F：先接 Triton，接口留给其他编译器

图编译先检查实现的 `compiler_id` 是否在当前构建启用清单中。未启用时报告 `CompilerNotEnabled`，在加载 DSL、启动工作进程和查询外部编译缓存前停止。独立 LLVM 文件导入不按 producer 名称调用编译器，因而仍可使用；选择规则见[构建设计](09-构建与可选编译器.md#core)。

A 层的 `ask.external` 用 `semantics` 符号引用解析到带 `semantic_key` 的 `OperatorSemantics`，说明 F 的签名、数值语义和副作用；`implementation` 符号引用解析到 `ImplementationReference`。这是图中的编译边界，不是纯追踪标记 `ask.mark`。节点与记录的完整定义见[ASK IR 的 external 输入约定](ask-ir/00-结构类型与操作.md#external)。

上层框架提供的 `ImplementationReference` 关联 `compiler_id`、`DSLSource`、`source_bindings`、`constants` 和 `fixed_options`。`DSLSource` 包含 `source_ref`、内容 `digest`、`language`、源入口 `entry` 与源码依赖 `deps`。B 层解析来源并核对摘要，将其放入 `ExportRequest.source`，按 `compiler_id` 路由到对应导出器；不另建一套语义注册表，也不猜测 DSL。客户端接收的 callable 必须在提交独立 worker 前整理成可解析的源码及捕获值、依赖内容；做不到就报告不支持，不能用对象地址充当源码或版本。

编译前的 `source_bindings` 说明 DSL 源参数对应哪个逻辑输入输出或常量。例如 `F(t_ptr, u_ptr, N: constexpr)` 分别关联输入 t、输出 u 和常量 N=10。编译后的 `port_map` 才说明实际 LLVM 参数如何绑定：N 可能已消除，入口可能增加 scratch，输出仍可能通过指针写回。导出器根据本次真实签名回填，ASK 再验证；不能照搬源码参数序号。

首期真实接入只支持 Triton。图编译使用通过 `register_exporter(id, version, export)` 注册的导出器，`export(ExportRequest)` 编译已提交的 DSL 并返回 `LLIRArtifact`。已有 LLVM 文件可以通过 `import_artifact(artifact, binding=None)` 使用低层工具入口；这不是图编译主入口，但两条路径最终使用同一个 LLVM 导入器。第三方不必实现 `probe/normalize/validate` 等 ASK 内部步骤，也不必先提供融合证明。具体字段见[第三方 LLIR 接入 API](08-第三方LLIR接入API.md)。

导出产物使用 `format="llvm-ir"` 或 `format="llvm-bitcode"` 标明内容格式，另外记录入口、生产者和版本、目标、依赖、特化与调用信息。产物中的 `port_map` 把逻辑端口对应到本次导出的物理参数和返回值；`binding` 只引用 A 层已经注册的语义与本次特化，不重复定义算子。常量折叠、隐藏参数或参数拆分改变了物理签名时，应按实际产物返回映射，不能照抄源函数参数序号。

只解析和保存 IR 时可以不提供调用绑定或 launch 信息，`ImportResult` 列出尚缺的执行条件。后续请求编译并执行该入口时再检查这些条件是否补齐，不能把它们都变成 LLVM 文件解析的前提。

Triton 的 `CompiledKernel.asm["llir"]` 已经是原生 LLVM IR。NVIDIA 后端在 `make_llir` 中翻译为 LLVM 模块后返回字符串，编译结果再按阶段名读入 `asm`。它可以直接作为 `llvm-ir` 内容送入 ASK。[Triton 生成 llir](https://github.com/triton-lang/triton/blob/b89bce47e2d9e1c7fb4bd568c1e55e19c476a31e/third_party/nvidia/backend/compiler.py#L492-L544)、[读取阶段产物](https://github.com/triton-lang/triton/blob/b89bce47e2d9e1c7fb4bd568c1e55e19c476a31e/python/triton/compiler/compiler.py#L407-L431)

外部接入只使用公开编译、导出、插件或 Pass 接口，不修改外部编译器源码，不依赖私有钩子，也不复制改写其阶段实现。如果只能取得合法可调用代码，仍可作为 `CallableArtifact` 保留调用；如果连这样的产物也没有，就报告不支持。

## 3. 解析 LLVM IR 不要求理解所有指令的内部含义

文本调用 LLVM assembly parser，bitcode 调用 bitcode reader，得到 `llvm::Module` 后运行 `verifyModule`。解析只说明文件能读懂，verifier 继续检查类型、SSA、控制流等结构是否合法。任一步失败都保留诊断，不把损坏模块交给后续 Pass。[LLVM 文本解析接口](https://llvm.org/doxygen/AsmParser_2Parser_8h_source.html)、[Bitcode reader](https://llvm.org/doxygen/BitcodeReader_8h_source.html)、[Verifier](https://llvm.org/doxygen/Verifier_8h_source.html)

```text
module = parseAssembly(payload) or parseBitcode(payload)
if parsing_failed or verifyModule_reports_error(module):
    return ImportError(diagnostic)
record_module(module, producer_version, content_digest)
```

这是处理顺序的伪代码；实现应使用选定 LLVM 版本的具体 API 和返回类型，并由编译会话管理 `LLVMContext` 与模块的生命周期。

模块可以原样包含目标 intrinsic 和 inline assembly，包括 inline PTX。B 层保留它们的指令、操作数、约束和属性，不为了进入 ASK 就要求先改成通用 load/store。当前 LLVM 版本无法解析的格式必须报错，但 ASK 的某项分析不认识一个合法指令，不应据此拒绝整份 IR。

Triton 的普通访存就可能使用 PTX inline asm。它的 load/store 转换通过 `PTXBuilder` 构造访存，最终创建 LLVM inline asm，因此只查 `LoadInst` 和 `StoreInst` 会漏掉真实访问。[访存生成](https://github.com/triton-lang/triton/blob/b89bce47e2d9e1c7fb4bd568c1e55e19c476a31e/third_party/nvidia/lib/TritonNVIDIAGPUToLLVM/LoadStoreOpToLLVM.cpp#L416-L455)、[inline asm 构造](https://github.com/triton-lang/triton/blob/b89bce47e2d9e1c7fb4bd568c1e55e19c476a31e/third_party/nvidia/lib/TritonNVIDIAGPUToLLVM/PTXAsmFormat.cpp#L98-L114)

通用 Pass 按 LLVM 已声明的效果及保守规则处理这些操作，不靠正则表达式猜测汇编的访存语义。后续若某个优化需要更精确的信息，可以查询专门的目标分析或附带说明；查询失败就保留相关指令和边界。

## 4. 模块接收后，再检查能否执行

一个模块通过 verifier，并不表示当前后端能生成它的机器码，也不表示运行时已经知道怎样启动它。B 层根据编译请求和产物声明建立 `TargetContext`，记录选定的目标、特性、data layout、地址空间与 ABI。原生 LLVM 模块和独立调用产物都使用这份目标说明。

例如，模块中的 inline PTX 可以在接入时原样保留，但代码生成必须交给能处理它的目标后端。不能把 NVIDIA 代码交给另一个后端后，仅修改 target triple 就宣称已经兼容。

执行检查需要的信息可以直接对应到使用位置：

| 需要什么 | 后面用来做什么 | 缺失或冲突时怎么办 |
|---|---|---|
| 入口、物理参数类型和逻辑端口绑定 | 将 P 的输出传给 F，将 F 的输出传给 Q | 不生成该调用；不能猜测隐藏参数 |
| 目标、data layout、地址空间和依赖 | 生成或加载匹配目标的代码 | 缺失则要求明确提供；冲突时拒绝执行 |
| 原编译器的数值代码生成设置 | 保持 F 的舍入、FMA 和非正规数规则 | 补全或落实到对应指令，不能把 F 的放宽许可套到 ASK 区域 |
| 输入输出布局、别名和效果说明 | 安排参数、存储与调用顺序 | 未知效果保守处理；无法满足调用语义时拒绝执行 |
| `invocation` 中的启动及完成信息 | 设置执行参数、连接完成事件、释放临时存储 | 信息不全则停止构造执行计划 |

GPU 的 grid 不能只凭函数签名推导。Triton 在实际调用时另外求值 grid，再传给 launcher；导出器或调用方必须带上相应的启动描述。[Triton grid 求值与启动](https://github.com/triton-lang/triton/blob/b89bce47e2d9e1c7fb4bd568c1e55e19c476a31e/python/triton/runtime/jit.py#L787-L798)

data layout 影响指针宽度、类型大小、对齐和地址计算。产物缺少它时，只能由经过验证的目标约定补充，不能从当前宿主机器猜测。物理 ABI 不同可以通过已验证的 wrapper 封送；目标本身不支持某个 intrinsic 或 asm 时，wrapper 不能解决问题。

因此，接入记录和执行结果分开保存：IR 可以已经接收，但暂时无法在所选目标执行。若另有相同语义、相同固定策略的原始合法调用产物，可以用它执行；否则报告缺少的调用或目标条件。不能用“不做优化”掩盖不可执行的产物。

## 5. 固定 F，再编译 P 和 Q

F 尚未选定时，可以按调用方配置、语义和目标要求选择兼容实现。选定并验证调用方式后，冻结其原始产物、实现配置、数值策略和启动约定。后面的优化不能因为 F 难以分析，就换一个更容易融合的实现或重新选择它的分块与布局。

`external_strategy_digest` 标识这份 F 基线，覆盖代码内容、生产者与版本、实现配置、数值契约和调用描述；已提供的执行映射、遍历次序、存储及同步说明也进入摘要。内部信息缺失时直接保留未知，不要求为了算摘要虚构一份完整执行图。融合后整个模块可以变化，但 F 被承诺保留的策略不能变化。

然后编译 P/Q。只要 F 的输入输出调用要求明确，P 就可以写入符合 F 要求的 `t`，Q 可以读取 F 完成后的 `u`，无须知道 F 每个线程怎样工作。ASK 自有 P/Q 同样降到原生 LLVM IR，再交给 C 层统一处理。

如果随后取得有效的执行映射，可选融合 Pass 可以请求重新编译 P/Q，让相同索引的生产和消费更容易对应。该请求只能改变 ASK 拥有的区域。多个外部算子的固定要求冲突时，拆分候选并保留中间存储，不重调外部算子。

## 6. 追踪信息可以晚于接入得到

普通调用只需知道端口怎样变成参数；消掉 `t[i]` 的存取则要知道哪个低层访问对应这个元素。两者不是同一张表。

`BoundaryMap` 将逻辑值、端口和元素索引对应到低层地址、SSA 值、访存及掩码。`ExecutionMap` 说明这些访问由哪个动态实例执行，彼此有什么顺序、存储可见性和同步关系。它们可以由导出器附带，也可以由 ASK 分析得到，并允许缺省或只有部分结果。详细规则见[跨层身份与追踪](02-跨层身份与追踪契约.md)。

C 层中的每个可选 Pass 查询自己需要的事实。例如消除 `t` 的 Pass 要证明写 `t[i]` 与读 `t[i]` 对应、值在消费前可用、其他消费者及副作用得到保留。若只能知道它们访问同一个 buffer，或者访问藏在尚无法解释的 asm 中，这个优化就跳过。已经接收的模块仍留在统一流水线里，已满足调用条件的入口仍可以执行。

映射必须记录适用的 IR revision。一个 Pass 改了索引、循环或访存，就更新相关映射或使其失效。失效的可选分析可以重算，不能继续授权优化；IR 本身损坏则报告错误。不能把“分析不知道”和“输入非法”归成同一种结果。

## 7. 一起交付代码、调用说明和可选分析

```text
LoweredBundle {
  region_id, semantic_binding, semantic_revision, lowered_revision
  representation: LLVMModule(module) | CallableArtifact(reference)
  target: Optional<TargetContext>
  entry_signature, port_map, invocation, symbol_dependencies
  memory_effects, numeric_contract
  boundary_map: Optional<BoundaryMap>
  execution_map: Optional<ExecutionMap>
  producer, contract_version, content_digest, external_strategy_digest
}
```

C 层用 `representation` 找到可处理的模块或外部调用，存在 `semantic_binding` 时用它找回 A 层语义。只做导入的记录可以暂缺目标、语义绑定或 `invocation`，并附上缺失项；后端和运行时必须在执行前取得完整的目标、签名、依赖与调用说明。可选 Pass 再查询两种映射；它们缺省并不改变模块已经接入的事实。

初期不必把所有 LLVM 模块物理链接成一个大模块。保留独立模块也可以统一管理 Pass、符号、版本和执行计划。只有确实要链接或跨模块变换时，才处理上下文、符号冲突、属性和目标一致性；不能把模块放进同一容器就认为跨边界变换合法。

## 8. 缓存与首期验收

降级缓存将 IR、调用说明和附带分析作为同一份版本化产物保存。键包含语义与常量、DSL 内容及源码依赖摘要、`source_bindings`、生产者及产物依赖内容、目标、数值模式、形状条件、F 基线摘要，以及 LLVM、ASK 契约、导出器和 Pass 配置版本。缓存命中仍检查版本、内容和调用说明，不能把旧 IR 配上新参数映射。磁盘上保存文本或 bitcode 与稳定引用，不保存 `llvm::Module*` 或进程内地址。

可选优化请求重编译 P/Q 时，记录已尝试配置，并受次数和时间预算限制。相同失败配置不重复尝试。预算用尽就保留已有合法执行计划；没有合法计划时返回错误。F 冻结后不通过更换实现重试。

首期用真实 Triton 逐元素 F 验证公开导出、原生 LLVM 解析与验证、目标代码生成、加载和执行，再与 P/Q 组成未融合计划并比较结果。这个阶段允许完全不融合。测试替身可以注入坏 bitcode、错误参数映射或缺失启动信息，但不能代替 Triton 实测，也不要求支持第二套真实工具链。

后续单独验收可选融合：建立有效的访问和执行分析，覆盖普通 LLVM 访存与已支持的目标操作，再验证中间存储消除。测试还要确认未知 asm 会让相关优化跳过，而不会让合法 IR 在接入时被拒绝。
