# C 层：统一处理 LLVM IR，再选择能做的优化

本章描述完整 C 层设计。目前已实现可独立调用的原生 LLVM 基础优化，以及 ASK 自有逐元素计算的高层优化和 host 多输出融合；实际入口和限制见[基础优化](11-基础优化与逐元素融合.md)。跨外部内核融合仍按后文逐步实现。[返回顶层设计：C 层](核心思想.md#ask-c) · [文档索引](README.md)。

## 1. 收到 IR 后，先让它能继续编译

B 层交来的区域可能有原生 LLVM IR，也可能只有一个可调用的外部实现。C 层先检查这些产物，维护执行次序，再安排适用的分析和变换。接入成功不以融合为条件：一个模块可以不做任何跨区域优化，直接交给后端生成代码。

这里的 `LLVMModule` 表示 ASK 已从 `.ll` 或 bitcode 读取的 `llvm::Module` 及其来源记录。它可以含普通 LLVM 指令、目标 intrinsic 和 inline assembly。`BoundaryMap` 可以缺省或只覆盖部分访问；这会限制需要追踪的优化，不阻止其余合法 IR 被接收和编译。导入方式见[第三方 LLIR 接入 API](08-第三方LLIR接入API.md)。

只有可调用产物的区域继续保留调用。C 层知道它的参数、读写效果和完成方式，但不改写它的内部。执行计划仍表示 `P 完成 → F 开始 → F 完成 → Q 开始` 等依赖；不会因为 P/F/Q 出现在同一请求中，就自动将它们放进同一个函数。

第一条基础路径因此很短：

```text
read LLVM IR or retain callable reference
check structure, target assumptions, ABI and dependencies
run the enabled passes whose requirements can be met
send valid modules and the resulting execution plan to code generation
```

这条路径关闭追踪、函数内联和融合后仍应能运行。代码生成与调用另见[后端与运行时](05-代码生成与运行时.md)。

## 2. 区分“模块不能用”和“这次优化做不了”

读取 LLVM IR 后调用 verifier，检查类型、SSA、控制流、函数及指令形式。解析失败或结构无效的模块不能作为正常产物继续传递，也不能因为“可以不融合”就拿它回退执行。

结构通过后，检查选定工具链和目标是否能处理模块：DataLayout、地址空间、入口约定、所需目标特性和外部符号是否有正确解释。已声明的运行库符号可以留待后续链接，但必须知道由谁提供。不能通过随意改 `target triple` 或删掉不认识的属性使模块看起来兼容。

有些限制只影响模块组合。例如 P 和 F 的执行映射不适合合并，但它们分别编译、分别调用都合法，就保留两个模块及调用边界。若某个模块本身不能在本次目标正确编译或调用，则报告不支持；对外部 F，只有同一固定策略下另有已经验证的合法调用产物时，才可选用该产物，不能借此重新选择 F 的实现或配置。

LLVM verifier 不会证明实现符合高层算子定义，也不会证明一段浮点计算与改写前等价。类型正确的 `fadd`、错误的索引和错误的舍入方式都可能出现在结构有效的 IR 中。算子语义由接入描述与对应验证负责；每个变换还要检查自己改变了什么。

因此，缺少逻辑索引映射是一项分析能力缺口；原生 IR 已经损坏是输入或编译器错误；目标没有所需指令是目标不支持。三者不能合并成一句“融合失败”。

导入结果分别记录 IR 是否读取成功、端口绑定和调用信息是否齐全、目标代码生成是否支持，以及各项分析是可用还是未知。不设置模块级的 `can_fuse=True` 开关。`artifact.trace` 可选；某次优化需要其中的信息时，再检查对应范围是否有有效记录。

## 3. inline PTX 可以保留，通用 Pass 不猜它的行为

例如某个 Triton 模块中，访存已经降成 `call asm`，而不是 LLVM 的 `load`。只要所选目标后端支持这段汇编及调用形式，ASK 可以原样保留它并继续代码生成，不要求先把它还原成通用 LLVM 指令。

分析它时必须遵守 LLVM 表达出的操作数约束和效果标志。LLVM LangRef 明确指出，正确性分析不能仅凭 asm 模板字符串推断实际行为。因此不能用字符串匹配看到 `ld.global` 就把它当成普通 `LoadInst`，也不能因为输出类型是 i32 就认为它没有内存效果。[LLVM inline assembly](https://llvm.org/docs/LangRef.html#inline-assembler-expressions)

如果适配器提供额外语义模型，可以在模型覆盖的范围内继续分析。模型要说明它支持哪个工具链版本和哪种导出形式，如何解释地址、访问宽度、掩码、返回值与副作用，并绑定实际产物。仅凭指令名字或一个 `pure=true` 标签不够。无法核验的模型不参与优化，原汇编仍保留。

未知效果只阻止依赖该效果判断的变换。例如不能证明某个 asm 是否改写 t，就不能把 t 的读取跨过它移动；但与该调用和内存都无依赖的常量运算仍可折叠。判断范围应是正在修改的指令、路径与访问集合，不应因模块里存在一个未知调用就关闭全部 Pass。

这里的“无依赖”也需要依据，不能按指令距离划分。如果未知调用可能影响整个函数中的内存，它可以阻止该函数内多处移动或删除访存；并非离它较远的区域就自动安全。

目标 intrinsic 同样按各自定义处理。具有跨线程通信行为的操作，可能依赖参加调用的线程集合；即使它不读写普通内存，也不能随意移出分支或复制到另一处。[LLVM convergent operations](https://llvm.org/docs/ConvergentOperations.html)

## 4. 每个 Pass 说明它需要知道什么

Pass 不按“模块可融合/不可融合”整块放行。驱动对每次具体尝试记录作用范围和前提，再决定运行、跳过或报告无效结果。

例如，函数内一条整数常量折叠只需要该指令的数值规则；删除一个边界 load 还需要知道对应写入、掩码、别名和执行实例；改动函数签名则必须同时处理所有相关调用点。缺少后两类信息，不影响第一类变换。

每次尝试记录以下三种结果：

| 结果 | 含义 | 后续动作 |
|---|---|---|
| `applied` | 已经修改，修改后的 IR 和相关说明通过检查 | 提交新版本，更新或丢弃受影响分析 |
| `skipped` | 无匹配、前提未知、不成立、无收益或预算不足 | 原 IR 保持有效，继续其他独立尝试 |
| `invalid` | 输入无效，或变换制造了无效结果 | 报告具体错误；按第 8 节区分输入错误与试改失败 |

一次 Pass 运行可以有多个局部结果，例如折叠了十条指令，跳过一个未知 asm 附近的变换。报告应指出发生在哪个函数、区域或访问上，以及缺少哪项信息。

```text
for attempt in enabled_passes.enumerate(current_modules):
  scope = attempt.affected_scope()
  facts = obtain_current_analyses(scope, attempt.requirements)
  if facts cannot establish the required conditions:
    record(skipped, scope, facts.reason)
    continue
  if attempt has a cost check and it predicts no gain:
    record(skipped, scope, "no_expected_gain")
    continue
  try_apply_and_verify(attempt, facts)
```

“条件成立”先于“有没有收益”。成本模型只能比较正确方案，不能用性能预期覆盖未知的别名或同步关系。

## 5. 复用 LLVM 分析，但不把它们当成跨线程证明

C 层可以直接使用 LLVM 的分析，不必重写函数内部的全部基础设施：

- `AA`/ModRef 判断地址范围是否可能重叠，以及指令或调用是否可能读写某段内存。
- `MemorySSA` 帮助追踪一个函数中的内存版本和潜在覆盖关系；它本身是函数内分析。[MemorySSA](https://llvm.org/docs/MemorySSA.html)
- `DominatorTree` 检查 SSA 定义是否先于所有使用路径。
- `LoopInfo` 和 `ScalarEvolution` 处理当前 CFG 中的循环、归纳变量和可识别的索引递推。[LLVM LoopInfo](https://llvm.org/docs/LoopTerminology.html#loopinfo)、[ScalarEvolution](https://llvm.org/docs/Passes.html#scalar-evolution-scalar-evolution-analysis)

这些结果能回答“当前函数中这次读取前是否有潜在覆盖”，不能自动回答“另一个 kernel 的第 j 个线程是否已经写完”。SCEV 也不会自动恢复已经丢失的张量布局或任意位运算形成的线程分工。

涉及高层端口、逻辑元素和执行实例的分析，仍使用[跨层身份与追踪信息](02-跨层身份与追踪契约.md)。追踪可以作为可选分析 Pass 尝试恢复；恢复不了就保留未知项，影响的只是依赖这些项的变换。

## 6. 函数内联也是一次可选变换

已实现的公共 C++ 接口及其保证见[通用 LLVM 值边界内联](13-通用LLVM值边界内联.md)。该接口与具体编译器的边界恢复分开，输入模块在失败时保持原样。

普通函数内联可以用来展开 helper。例如 ASK 将 P 生成为 `P_at(x, i)`，在 F 需要 t[i] 的位置插入调用，再将 helper 内联。内联负责展开函数体；调用放在哪里、能否替换 F 原来的读取，仍要先由 ASK 证明。

也可以仅内联一个已有普通函数调用，不改变区域边界。这种变换不需要完整的高层 `BoundaryMap`，但需要满足 LLVM 内联规则，以及相应目标、数值和调用要求。

完整 kernel 的融合不能靠把三个入口标成 `alwaysinline` 完成。原来 P 的一次启动全部完成后才启动 F；把 P/F/Q 的函数体排在同一实例中，只得到该实例内的顺序，不会保留跨实例完成依赖。kernel 入口与普通 device function 也可能有不同调用约定。

函数内联不展开 asm 字符串。helper 内部有 `call asm`，内联之后仍是 `call asm`，第 3 节的限制继续成立。

## 7. 确实有证据时，再尝试消除 P/F/Q 的边界

以下可选融合使用同一例子，所有运算按模 2^32 保留 i32 结果：

```text
P: t[i] = x[i] + 1
F: u[i] = t[i] * 2
Q: y[i] = u[i] + 3
```

F 的执行映射、布局、同步和数值规则固定，ASK 只调整自有 P/Q。对 F 的每个目标读取，先查清原来读的是哪次写入及哪个逻辑元素，再决定是否在原读取位置计算 P(i)。各步遇到的问题有明确去向：

1. **对应哪个写入。** 原生 GEP/地址计算与追踪信息应能说明读取的是 t[i]。若实际读取 t[i+1]，或一个位置被多轮循环覆盖，不能直接传入 P(i)；没有进一步证明就跳过这条边。
2. **这个值是否存在。** 消费者的有效 mask 必须有对应生产值，SSA 定义必须支配使用。若 t 先初始化为零、P 只写前 K 个元素，F 读到后面的元素仍应得到零；不能传一个未计算的 P 值。首版不支持的分支合并、循环携带值或 passthrough 处理保留原访问。
3. **是否发生干涉。** 原来 P 先读完整个 x，再由 Q 写 y；逐元素融合后若 y 与后续要读的 x 重叠，结果可能改变。不能证明无干涉就保留边界。`volatile`、原子、未知调用和有状态效果不适用普通 load/store 删除规则。
4. **是否需要其他实例。** P(i) 与 F(i) 能在同一动态执行实例中先算后用，才直接传 SSA 值；另一个实例供值时，需要另行证明存储可见性、同步参与范围和重用时机。首版不做这种交换，保留独立执行。
5. **t 是否还有人使用。** 如果 t 是用户输出、其他消费者的输入，或者地址已逃逸，就保留需要的 store 和分配；不能只看 F 的 load 已删除。首版可跳过这种候选，后续再支持部分保留存储。
6. **数值是否相同。** i32 回绕不能增加 `nsw`/`nuw`。若浮点边界原来先窄化为 f16 再扩展为 f32，删除访存后仍要保留这次舍入；不自动启用重结合、乘加收缩或忽略 NaN。可观察异常顺序没有专门支持时跳过相关融合。

这些低层循环、分支和 mask 不表示 A 层接管图级动态控制流。根据运行时数据选择哪个图或重复调用多少次，仍由上层框架负责。

证明成立并值得尝试时，在 F 原有执行骨架中插入 P/Q，替换已确认的边界取值，保留 F 的内部运算与同步。下面只展示一个已确定索引 i 的计算片段，省略实际 kernel 的入口、索引生成和地址空间：

```llvm
; x/y 不重叠；当前路径已保证 i 有效；中间值没有其他消费者。
%xp = getelementptr i32, ptr %x, i64 %i
%a = load i32, ptr %xp, align 4
%p = add i32 %a, 1
%f = mul i32 %p, 2
%q = add i32 %f, 3
%yp = getelementptr i32, ptr %y, i64 %i
store i32 %q, ptr %yp, align 4
```

真实 F 的访问若是 inline asm，必须先有第 3 节所述的替换依据，不能照此片段把它强行视作 load。`P → F` 不能处理时，仍可独立尝试 `F → Q`。若有 `F1 → P → F2`，P 无法同时适配两侧固定策略，就只融合一侧或全部保留。

高层追踪、函数内联和这项融合都可以关闭；关闭后，模块仍走第 1 节的代码生成路径。

## 8. 修改连同分析一起提交，失败有原路可退

会改变跨区域关系、签名或执行计划的变换，在副本上试改。副本包含受影响 IR、符号和参数映射、执行计划及追踪信息。不能只保存指令，而把新签名或新依赖提前写入正式状态。

试改后先验证 LLVM IR，再检查本次变换特有的条件。例如边界替换要检查新值的来源、mask 和效果顺序；组合区域还要确认 F 的执行映射、布局、同步及数值规则没有被改变。通过后一起提交新 revision。

任何分析记录都绑定输入 revision。输入在尝试期间变化，就丢弃结果并重新分析。提交后，受影响的 AA、MemorySSA、支配树、循环分析和追踪映射要更新或失效；不能把旧函数里的分析节点继续用于新函数。通过 LLVM Pass Manager 声明分析保留情况，默认只保留确实没有受影响的结果。[LLVM analysis invalidation](https://llvm.org/docs/NewPassManager.html#using-analyses)

`invalid` 分两种处理。输入原本无效，就隔离它，没有另一份合法实现时编译失败；试改制造了无效结果，则报告编译器错误、保存重现材料并丢弃副本。普通模式可继续使用原有效产物，严格验证模式让该错误直接失败。两种情况下都不能把损坏产物包装为 fallback，也不能静默当成一次普通 `skipped`。

没有融合的原方案同样要经过后端生成和调用检查，才能成为可执行回退项。仅仅保存了原 IR 不等于已经有一份能运行的备用二进制。

## 9. 限制尝试次数，再用实际代码生成结果验收

Pass 按固定配置和确定次序运行。请求限制候选数、分析工作量、IR 增长和重试次数；预算用尽就记录 `skipped`，让剩余有效 IR 按原方式继续编译。同一输入 revision 下已经失败的方案不要无限重试。

若后端拒绝某个优化方案的资源需求，只调整 ASK 自有 P/Q、缩小优化范围，或选择已经验证的独立执行方案。不能为了优化重新搜索 F 的分块、布局或调度参数。最终机器码可能产生溢出存储，SSA 值直通不保证物理寄存器或性能结果。

调用前守卫只用于已经证明“条件为真时变换正确”的情况，例如某种布局或合法的不重叠检查。守卫失败选择同语义的有效版本，且必须在受影响的用户操作开始前决定。执行已经开始后报错，应传播执行错误，不能自动重放可能有副作用的整图。

初期验收先证明：真实 Triton 导出可以被读取、检查、保留目标操作、代码生成并正确执行；关闭所有可选跨区域优化，结果仍正确。接着分别测试一个无高层映射的普通 LLVM 优化、一个未知 asm 导致局部跳过的例子，以及试改失败后恢复原产物的路径。

融合属于后续增加的能力。以第 7 节的小例子验证成功路径，再在每个检查步骤加入偏移、mask、alias、数值转换和跨实例依赖反例。追踪恢复率、Pass 应用情况、运行正确性与性能分别报告，不能把“没有融合”写成“接入失败”。测试和实施次序见[工程组织与验证](06-工程组织与验证.md)、[实施路线](07-实施路线与端到端示例.md)。
