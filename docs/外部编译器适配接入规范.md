# 外部编译器适配接入规范

适配器是一个 worker：接收 ASK 导出的请求，调用第三方编译器，返回二进制和启动信息。调用方负责启动 worker、校验和缓存产物，再将其交给 ASK Runtime。FugaTensor 提供了这套调用流程及 Triton worker。

<a id="adapter-contract"></a>

## 1. 进程接口

Worker 提供两个命令：

```text
worker --probe --request /path/to/request.json
worker --request /path/to/request.json --output /path/to/artifact.json
```

`--probe` 根据请求中的源码和编译选项计算依赖指纹，向 stdout 输出 JSON。结果至少包含 `producer: {name, version}` 和非空字符串 `adapter_version`，并记录编译器安装、引用模块、依赖锁等影响编译结果的内容。调用方将整个结果纳入缓存键，并核对实际产物的 `producer`；FugaTensor 已实现这项检查。

编译成功后写入响应 JSON 并返回 0；失败返回非零状态，将诊断写入 stderr。输出通过临时文件原子替换。Python worker 使用指定的解释器运行。

<a id="worker-protocol"></a>

## 2. 请求协议 v2

请求来自 Compiler 结果的 `externalRequestsJSON`；CLI 和完整 JSON 接口通过完整报告的 `external_requests` 提供同一内容，由调用方交给 worker。编译器 ID、图节点 ID 和函数名用于路由与报告，不传给 worker。协议字段如下：

| 字段 | 含义 |
| --- | --- |
| `protocol_version` | 整数 `2`。 |
| `source` / `entry` | 源码快照与入口名称，由 worker 解释。 |
| `signature` | 参数到 ABI 类型的映射。张量使用 `*i1`、`*i32`、`*i64`、`*fp32`、`*fp16` 或 `*bf16`；按值标量类型见下文。 |
| `source_bindings` | 与 `signature` 同名。指针绑定 `input:N` / `output:N`，端口编号连续且一一对应；标量直接绑定布尔、整数或有限浮点值。 |
| `constants` / `fixed_options` | 递归 JSON 编译期常量和固定选项，支持 null、布尔、整数、有限浮点、字符串、数组和对象，具体含义由 worker 定义。 |
| `target` | CUDA 目标，包含 `backend`、`arch`，可携带 `warp_size`。 |
| `grid` | 三个正整数，表示固定启动网格。 |
| `port_shapes` | 每个逻辑输入输出的具体形状，来自 ASK 图校验结果。 |

标量支持 `i1`（布尔）、`i8/i16/i32/i64`、`u8/u16/u32/u64`、`fp16/bf16/fp32/fp64`。`source_bindings = {"x": "input:0", "n": 1024, "scale": 0.5, "y": "output:0"}` 配合对应签名即可传入普通 kernel 标量参数；它们由 CUDA 启动 ABI 按值传递，区别于编译期 `constants`。整数须在相应位宽的范围内；浮点按目标格式 RNE 编码。

启动值在构图时冻结，参与请求缓存和编译包身份；修改值须重新构造调用。`PreparedProgram` 提交时绑定张量缓冲区，保留准备时的标量值。编译期配置的整数范围为 `[-2^63, 2^64-1]`。请求仅携带张量元信息，格式见 [external-compiler-request-v2.schema.json](../schemas/external-compiler-request-v2.schema.json)。

<a id="artifact-contract"></a>

## 3. 最小响应

响应必须恰好包含以下字段：

```json
{
  "protocol_version": 2,
  "format": "cubin",
  "payload": "<base64 编码的 cubin>",
  "entry": "kernel_entry",
  "target": {"backend": "cuda", "arch": 80, "warp_size": 32},
  "producer": {"name": "example", "version": "1.0"},
  "launch": {"grid": [1, 1, 1], "block": [128, 1, 1], "shared_bytes": 0},
  "arguments": ["input:0", {"type": "i32", "value": 1024}, "output:0"],
  "required_element_types": ["f32"]
}
```

`format = "ptx"` 时 `payload` 是 PTX 文本。`target` 必须与请求一致，`launch.grid` 必须等于请求网格；`block` 和 `shared_bytes` 来自实际编译结果。`arguments` 按物理参数顺序排列：每个张量端口恰好出现一次；标量写成仅含 `type`、`value` 的对象，类型、编码值和出现次数必须与请求一致；未使用且允许为空的指针可写 `"null"`。上例要求请求中有一个 `i32` 启动参数绑定 `1024`。

`required_element_types` 声明运行时须检查的张量元素类型，调用方将它与端口类型合并后传给 `Session::load`。生产者按 `target` 编译，负责满足内部指令的架构要求。

FugaTensor 的 [`normalize_artifact`](../../fugatensor/src/fugatensor/_ask/adapters.py) 根据请求构造 `port_map` 和 invocation v2，校验产物后转成原生计划。其它调用方可采用同一规则。格式见 [external-kernel-artifact-v2.schema.json](../schemas/external-kernel-artifact-v2.schema.json)。

## 4. 缓存与支持范围

FugaTensor 查找外部编译缓存前执行带请求的 `--probe`，编译后再次探测，确认期间依赖保持一致。缓存键包含请求、探测结果、worker/解释器文件摘要、环境变量及调用流程的实现摘要；命中后仍校验产物。Worker 的指纹应覆盖自身导入的辅助模块和第三方依赖。

产物使用普通 CUDA kernel、静态连续的多输入多输出、指针与标量混合参数、固定启动配置和动态共享内存。scratch 为空；`null` 用于实际允许为空的指针。启动要求见[可执行产物与端口](外部产物与执行接口.md#binary-artifact)。

<a id="conformance"></a>

## 5. 接入验证

新增 worker 应覆盖多端口及不同形状、混合标量位宽和参数顺序、cubin/PTX 编码、动态共享内存、缓存命中和依赖变化。错误测试包括 worker 失败、损坏产物、目标或端口不匹配。数值结果须在真实 GPU 上验证，并与 CPU 协议测试分开记录。

实现可参考 FugaTensor 的 [Triton worker](../../fugatensor/src/fugatensor/_triton_worker.py)。编译器版本和资源限制由各适配器维护。
