# 09. 外部编译器适配接入规范

返回核心思想：[外部适配与通用值边界融合](核心思想.md#ask-external-fusion) · 相关细节：[外部编译器适配与边界内联](04-外部编译器适配与边界内联.md) · [图切分与多 Kernel 执行计划](08-图切分与多Kernel执行计划.md#complex-external)

ASK 核心不实现第三方 DSL 的解析或算子库。`ask` dialect 的静态图、LLVM 值边界内联、执行计划和 CUDA 运行时只依赖本规范的适配器契约；Triton 只是 `adapters/triton/` 中的一个实现。新增 Triton 同类编译器（MLIR 导出者、Python AST DSL 或其他外部 kernel 编译器）时，不改 `ask_core`、`lib/LLIR/` 或 CUDA 运行时。

<a id="adapter-contract"></a>

## 1. 接入边界与目录

一个适配器由三部分组成：

| 部分 | 必需 | 职责 |
| --- | --- | --- |
| 构建注册 | 是 | `adapters/registry.json` 白名单、`adapters/<id>/registration.json`、`CMakeLists.txt` 与依赖锁。 |
| 导出 worker | 是 | 独立进程读取请求 JSON，写出[外部 kernel artifact](../schemas/external-kernel-artifact-v1.schema.json)；不向 ASK 返回 Python 对象、编译句柄或依赖。 |
| C++ 注册描述符 | 是 | 提供 `native_factory` 返回 `CompilerAdapter`；`validateArtifact` 可空。只有逐元素值边界融合才需要 `prepareFusion` / `finalizeArtifact`。 |

目录约定：

```text
adapters/
├── registry.json                  # {"schema_version": 1, "compilers": {"<id>": "<dir>"}}
├── <id>/
│   ├── registration.json          # id、协议版本、工厂、worker、可选融合能力
│   ├── dependencies.lock.json     # 生产者版本、adapter_version、LLVM 版本/修订
│   ├── worker.py | worker         # 实现请求/响应协议
│   ├── include/ask/Adapters/      # 可选 C++ 适配器声明
│   ├── lib/                       # 可选 C++ 边界校验
│   └── tests/                     # 请求、artifact、拒绝路径与真实导出测试
```

公共构建只编入 `ASK_THIRD_PARTY_COMPILERS` 选中的目录；不得扫描 Python `entrypoints`，也不得在公共代码中按编译器 ID 分支。`ask_compiler` 的 C++ 接口见 [`include/ask/Adapters/Compiler.h`](../include/ask/Adapters/Compiler.h)，Python 侧见 [`python/ask/adapters.py`](../python/ask/adapters.py)。

不提供融合能力时，C++ 描述符只需要一个稳定的工厂与 ID，例如：

```cpp
#include "ask/Adapters/Compiler.h"

namespace ask::adapters {
const CompilerAdapter &exampleCompilerAdapter() {
  static const CompilerAdapter adapter{"example", 1, nullptr, nullptr, nullptr,
                                      "worker.py", true};
  return adapter;
}
} // namespace ask::adapters
```

对应 `registration.json` 的 `"native_factory": "exampleCompilerAdapter"`。边界校验、融合准备与产物重签署全部可选；worker 和 artifact 契约仍是必需的。

<a id="registration"></a>

## 2. 注册字段

`registration.json` 的最小结构如下，机器可读约束见 [adapter-registration-v1.schema.json](../schemas/adapter-registration-v1.schema.json)：

```json
{
  "id": "example",
  "protocol_version": 1,
  "native_factory": "exampleCompilerAdapter",
  "supports_fusion": false,
  "package": "ask._adapters.example",
  "module": "ask._adapters.example",
  "factory": "create_adapter",
  "requires_python": true,
  "worker": "worker.py",
  "aliases": {"example_python": "python", "example_worker": "worker"}
}
```

- `id` 必须与 `registry.json` 中的目录名一致，并在整个构建中唯一。
- `native_factory` 只在提供 C++ 边界适配器时存在；`module`/`factory` 提供 Python `cache_identity` 策略。
- `worker` 相对于适配器目录解析；`requires_python` 决定是否必须提供解释器。
- `supports_fusion` 只描述值边界内联能力；不支持融合的适配器仍可走独立外部 kernel 与多 kernel 执行计划。
- `aliases` 只把旧式 `--compiler-python` / `--compiler-worker` 选项映射到环境字段，不允许 DSL 分支。

<a id="worker-protocol"></a>

## 3. Worker 请求协议 v1

请求由 `ask-opt --export-external` 或 `--fuse-external` 通过临时 JSON 文件交给 worker 子进程。字段定义见 [external-compiler-request-v1.schema.json](../schemas/external-compiler-request-v1.schema.json)，核心字段：

| 字段 | 约束 |
| --- | --- |
| `protocol_version` | `1`，整数，不能是布尔值。 |
| `source` / `entry` | DSL 原文与入口符号；入口必须是源码中唯一的同名函数（独立导出允许源码同时定义多个 kernel，见下）。 |
| `signature` | `{参数名: "*i1"、"*i32"、"*i64"、"*fp32"、"*fp16" 或 "*bf16"}`；至少一个输入和一个输出。 |
| `source_bindings` | 每个数据参数映射到唯一的 `input:N` / `output:N`；编号从 0 开始且连续。 |
| `constants` / `fixed_options` | 编译期常量与固定启动策略。数值、类型和允许键由适配器定义，但不得从 Tensor 数据推导。 |
| `target` | `{"backend": "cuda", "arch": 70..999, "warp_size": 32}`。 |
| `grid` | 三个正整数，表示逻辑启动网格。 |
| `port_shapes` | 可选；每个逻辑端口的静态形状。多输入、不同形状或混合类型必须显式提供。 |
| `fusion` | 可选 `{"enabled": bool}`；只有值边界融合请求为 `true`。 |

约束：

1. 请求格式错误返回 `InvalidRequest`；源码/入口/绑定错误返回 `UnsupportedSource`、`UnsupportedSignature` 或 `InvalidSourceBinding`；资源或产物不一致返回 `UnsupportedResources`、`ArtifactMismatch`。错误码和阶段写入 stderr 的结构化 JSON。
2. Worker 在写出完整 artifact 前不得产生成功文件；临时文件原子替换，失败不留下半成品。
3. worker 可以依赖自己的解释器和包版本，但宿主进程不导入生产者库；缓存身份必须覆盖这些依赖。
4. 独立导出允许多个顶层 kernel 定义在同一源码中；只有 `entry` 被编译，其他函数不得被隐式调度。值边界融合仍要求一个入口函数。

<a id="artifact-contract"></a>

## 4. Artifact 与执行契约

worker 成功时写出的 JSON 见 [external-kernel-artifact-v1.schema.json](../schemas/external-kernel-artifact-v1.schema.json)。最小必需字段：

- `protocol_version = 1`、`format = "llvm-ir"`、`payload`（原生 LLVM IR 文本）、`entry`（物理 kernel 符号）。
- `producer`：生产者名称、版本，以及适配器/依赖版本；只用于报告与缓存，不被 ASK 解释为调度指令。
- `target`：与请求一致的 CUDA 目标；可附加 `data_layout`，导入时校验。
- `port_map`：每个物理数据参数到 `input:N`/`output:N` 的映射，含 `argument` 序号、`shape`、`element_type`、`storage_bytes` 和 `layout = "contiguous_row_major"`；形状与类型必须与请求的 `port_shapes` 一致。
- `invocation`：`version = 2`、`kind = "cuda-kernel"`、`grid`/`block` 三维正整数、`shared_bytes`、`completion = "device-event"` 和物理参数列表；未使用的 scratch 参数绑定 `"null"`。
- `dependencies`、`validation`、`required_element_types`、`specializations` 与 `codegen`：分别记录 IR 依赖、导入/验证状态、运行时元素类型要求和代码生成策略；`codegen.fp_contract` 只能是 `on`、`off` 或 `fast`。

ASK 公共层只读取上述字段，并用 `ask::llir::importLLVMIR`、端口 ABI 校验、`ExecutionSession` 与 `CUDAProgram` 执行。`ask.external` 的静态形状、缓冲区布局和端口编号由执行计划统一分配；worker 不得依赖主机路径或进程全局状态。

<a id="cache-and-fusion"></a>

## 5. 缓存身份与可选融合

Python 适配器的 `cache_identity(request, environment, timeout)` 必须返回至少：

```json
{
  "producer": {"name": "...", "version": "..."},
  "adapter": {"policy": "...", "registration": {...}},
  "dsl": "<source 摘要>",
  "target": {"backend": "cuda", "arch": 86, "warp_size": 32},
  "numerics": {"..." : "..."},
  "config": {"..." : "..."}
}
```

- `producer`/`adapter`/`dsl`/`target`/`numerics`/`config` 任一变化都必须改变缓存身份；环境变量、worker 文件和依赖锁的影响要显式纳入。
- 浮点收缩、类型转换和整数回绕策略属于生产者；独立外部 kernel 不得被静默套用 ASK 的逐元素数值策略。
- 值边界融合是可选的：`CompilerAdapter::prepareFusion` 返回边界标记与数值策略，`finalizeArtifact` 在通用写入器替换 payload 后重新签署证据。没有这两个能力时，适配器仍必须支持独立导出与多 kernel 计划。
- 融合失败只能以明确的 `UnsupportedFusion` 表示并触发上层重切分；源码错误、worker 崩溃、LLVM 校验失败和产物损坏不得当作“可回退”。

<a id="conformance"></a>

## 6. 接入检查清单

新增适配器至少通过以下验证：

1. `adapters/registry.json` 与 `registration.json` 通过 `check_metadata.py` 的结构检查；只有被构建选中的适配器出现在 capabilities 中。
2. 请求/artifact 的 JSON 结构与 [schemas/](../schemas/) 一致；未知字段、布尔型协议版本、未知工作目录和越界形状被拒绝。
3. 独立导出一个单输入 kernel、一个多输入/不同形状 kernel 和一个使用动态共享内存的 kernel；三者都能被执行计划调度并产生数值正确结果。
4. 值边界融合（若声明）覆盖成功、类型不匹配、掩码不匹配和非法 LLVM 四类路径；失败不得改变源 artifact。
5. 缓存命中、worker 失败无残留、目标架构不匹配、`bf16` 低于 `sm_80` 和端口 ABI 不匹配均有拒绝用例。
6. 物理 GPU 测试与 CPU 协议测试分开；缺少驱动、`ptxas` 或生产者环境而跳过的测试不能算作功能通过。

现有参考实现是 [Triton 3.7.1](../adapters/triton/README.md)；它使用 `port_shapes`、多输入绑定、`num_stages` 和动态共享内存，同时保留可选的逐元素值边界融合。复杂算法（如 FlashAttention）属于上层框架，示例见 [FugaTensor 的 FlashAttention-2 前向/反向](../../fugatensor/examples/flash_attention2.py)。
