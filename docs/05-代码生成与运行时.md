# 代码生成与运行时

[返回顶层设计：编译与执行链路](核心思想.md#ask-pipeline)

本章主要描述完整图运行时的后续设计。初稿已能为自有 i32 / f32 图生成 host 目标文件，也能将受限的 ASK→Triton→ASK 图融合成原生 LLVM，再生成新 cubin 并在 GPU 上执行。后者使用独立 CUDA context、按 dtype 编码的连续缓冲区和同步完成；还没有完整混合图调度、共享 stream 或异步事件接口。当前实现见[GPU 融合与 IR 缓存](12-GPU融合与IR缓存.md)，host 入口见[框架接入](10-上层框架接入.md#7-自有图继续生成-host-代码)。

## 1. 先看 C 层留下了几个执行入口

继续使用一维 `i32` 张量上的例子，加法和乘法都按模 `2^32` 计算：

```text
P: t[i] = x[i] + 1
F: u[i] = t[i] * 2
Q: y[i] = u[i] + 3
```

基线计划有 P、F、Q 三个入口，即使三个入口都来自原生 LLVM 模块，也可以分别执行。以后启用融合 Pass，若证明两个边界都能消除，后端会收到一个联合计算体；若只消掉 `P → F`，则得到 `PF` 和 `Q`。这些入口数的差异决定了还需要哪些中间缓冲区。

```text
全部融合：      PFQ(x, y)
局部融合：      PF(x, u) -> Q(u, y)
保留全部边界：  P(x, t)  -> F(t, u) -> Q(u, y)
```

箭头表示完成依赖。Q 必须在它要读取的 `u` 写好后执行，不是等前一个入口“提交成功”就立即读取。中间缓冲区也不意味着必须多做一次复制：P 可以直接写入 F 随后读取的 `t`；只有布局或存储域确实不同时，才插入必要的转换或传送。

执行计划保留这些入口、参数对应、数据依赖和副作用顺序。它对应 A 层的静态控制流图；图级动态分支和循环仍由上层框架选择调用。单个入口内部的元素循环、条件判断和掩码不受这一限制。

如果多个外部算子的既有执行方式不兼容，计划保留其间边界。运行时不能为了减少入口数量而重新调度 F。外部产物仍只通过公开接口取得，不修改外部编译器源码或使用私有钩子。

## 2. 为每个入口确定参数和存储

有了入口划分，才能决定参数签名和临时存储。全部融合时，公开调用仍只需绑定输入 `x` 和输出 `y`；未融合时，运行时还需为 `t`、`u` 分配存储，并把它们传给对应入口。

公开 ABI 使用版本化描述，内部函数 ABI 可以由后端决定。两者不同，就由 wrapper 按明确规则封送参数；不能把某次降级恰好生成的内部结构直接当成长期公开 ABI。

```text
BufferView {
  allocation_handle, allocation_size, byte_offset
  dtype, sizes[], byte_strides[]
  memory_domain, alignment, access_mode
  ownership, lifetime_token
}
```

运行时用 `allocation_handle` 找到分配，用 `allocation_size` 检查范围，用偏移和 stride 解释视图。句柄不一定是主机能解引用的指针；目标后端负责把它变成入口可以使用的参数。`memory_domain`、对齐和访问权限用于检查实际代码能否访问这块存储。

例如，长度为 `n` 的连续 `i32` 输入通常每个元素相隔 4 字节；一个隔元素切片可能相隔 8 字节。二者的元素数相同，最后访问的位置却不同。因此，边界检查必须按实际视图计算，不能只检查 `n * 4`。

```text
element_byte_offset(indices)
  = byte_offset + sum(indices[d] * byte_strides[d])
```

计算最小和最大访问偏移时要检查整数溢出，并保证整个元素都位于分配内。负 stride、广播的零 stride、重叠视图应显式支持或拒绝，不能默认当作连续数组。零元素视图没有实际访问，检查过程也不能为它生成一次解引用。

签名还说明形状、dtype 和允许的别名关系。如果优化后的入口要求 `x` 与 `y` 不重叠，调用前必须证明或检查这一点；否则只能选择不依赖该条件的入口，或者拒绝这次调用。把同一个分配传入两个参数并不自动构成错误，是否允许由算子语义和入口要求决定。

## 3. 生成代码，资源不够时退回哪个计划

编译请求通过 `TargetProfile` 选择目标。后端用它与产物声明建立的 `TargetContext` 检查类型、指针宽度、字节序、地址空间、数值行为以及执行和存储能力。原生 LLVM 模块和独立调用产物都要有匹配的目标说明；只导入 IR 时暂缺的信息，到了代码生成和执行这一步必须补齐。

后端检查 `llvm::Module` 与目标一致后，直接使用相应 LLVM 目标代码生成和链接工具。模块可以保留 inline PTX 和目标 intrinsic，但选定后端必须真正支持它们；`verifyModule` 通过不能代替这项检查。后端不支持某条 asm 时，记录 `codegen.unsupported`，模块已通过的接入检查仍然有效。

F 若已是合法的 `CallableArtifact`，就作为独立依赖加入包，由其后端加载或链接。它不必先转换成 ASK LLIR，但必须与本次目标、调用 ABI 和执行上下文相容。形状相同不能证明两份代码能够互相调用。

首期只接 Triton。它公开的 Kernel Override 可以替换 `.llir` 阶段产物，再交给后续目标代码生成；这可作为入口 ABI、launch、shared/scratch 要求仍与原 F 一致时的验证路径。它不是任意 LLVM 文件的通用装载接口，不能假定 `triton.compile("file.llir")` 直接支持原生 LLVM 输入：该快照的文件入口对非 PTX 文件会调用 MLIR parser。需要改变物理参数或启动约定时，必须另外生成正确的 launcher 和元数据，不能沿用旧 F 的描述。[公开 override 用法](https://github.com/triton-lang/triton/blob/b89bce47e2d9e1c7fb4bd568c1e55e19c476a31e/README.md#L243-L269)、[替换阶段产物](https://github.com/triton-lang/triton/blob/b89bce47e2d9e1c7fb4bd568c1e55e19c476a31e/python/triton/compiler/compiler.py#L326-L339)、[文件输入解析](https://github.com/triton-lang/triton/blob/b89bce47e2d9e1c7fb4bd568c1e55e19c476a31e/python/triton/compiler/compiler.py#L87-L112)

最终代码生成可能发现某个优化方案资源开销过大。此时编译驱动可以恢复保存的区域和映射，把 `PFQ` 改成 `PF → Q`，或恢复三个独立入口。若要重新降级，只能调整 ASK 自有区域；F 的原始代码与配置、数值策略、启动约定以及已有的内部执行说明所对应的基线摘要保持不变。内部映射缺省不妨碍按完整调用说明执行 F。

每次尝试记录语义、目标、融合方案和 P/Q 配置。同一个失败配置不再重复，尝试次数和时间受编译预算限制。预算耗尽时使用已经验证且资源可行的计划；没有这种计划就报错。减少融合并不保证一定成功，单独的 F 也可能不适合当前目标或超过资源限制。

资源报告要标明哪些是估计、哪些来自实际代码生成，以及后端无法提供哪些项。未知不是零。性能不佳可以成为放弃一个合法方案的原因，不能成为忽略错误或放宽数值语义的理由。

## 4. 将代码和调用说明打包，再加载

Triton override 验证路径需要启用 Triton 集成。关闭第三方编译器时，原生 LLVM 仍可导入，但代码生成只能使用已经选择的独立 ASK 后端。执行包若要在没有 Triton 的环境运行，必须包含可由 ASK loader/launcher 使用的代码和调用说明，不能只保存 Triton 的 Python kernel 对象或闭包。见[构建模式与已有产物](09-构建与可选编译器.md#core)。

编译阶段最终生成 `ExecutablePackage`。它包含代码对象、入口签名、执行计划、临时缓冲区计划、目标与依赖版本、每个入口的调用和完成描述，以及可用变体和各自的运行前提。GPU 入口所需的 grid、线程组织、共享存储和 scratch 等信息必须由导出器或调用约定明确提供，不能从一段 LLVM 函数签名中猜出来。

加载器用目标要求和依赖版本判断包能否装入当前执行上下文，再解析外部符号。运行时用入口签名绑定参数，用执行计划安排先后顺序，用缓冲区计划分配临时存储。这些说明都要随代码保存，否则单独一个函数地址不足以恢复一次完整调用。

加载与提交分开：

```text
loaded = load(package, execution_context)
event  = submit(loaded, invocation, dependency_events)
```

`load` 失败可能是依赖缺失、版本不兼容或目标不支持，应在提交计算前报告。`submit` 接收具体标量、BufferView 和前置完成事件；返回的事件表示本次调用何时完成或失败。首版即使同步执行，也可以返回已经完成的事件，使缓冲区生命周期的含义保持一致。

一次编译面向一个明确目标。以后若支持多目标协作，需要显式增加设备间传送和事件协议，不能由加载器看到不兼容参数后悄悄复制到另一设备。

## 5. 提交前选择变体，提交后等待完成

加载了包，不代表任何输入都能交给其中任意入口。运行时先验证公开参数签名和视图范围，再根据该次调用的形状、布局、对齐和别名情况选择可用变体，最后才提交计算。

```text
validate_public_arguments(invocation)
variant = choose_verified_variant(package, invocation)
if variant is absent:
    return UnsupportedInvocation
submit(variant, invocation)
```

例如，包中可能有一个要求连续且无别名的融合入口，以及一个允许切片的未融合入口。守卫检查发现 stride 为 8 时，应在任何可观察写入、随机状态更新或外部调用之前选后者。描述符在执行期间必须保持稳定，否则检查通过后再修改 stride，就破坏了代码依赖的前提。

首版只支持静态形状，对不支持的形状明确报错。以后可以增加受预算限制的特化编译：守卫失败后先请求编译服务，拿到验证过的变体再提交。为融合而重编译的范围仍只限 P/Q，各变体保留本次请求已选定的 F 策略；F 本身不支持输入时，不能偷偷改变它的配置来通过守卫。运行时不自行进行图分析，而是通过明确的编译入口请求新产物。

提交之后，完成事件决定谁可以继续。未融合例子中，F 要等待 P 完成，Q 要等待 F 完成；调用方要等最终事件成功后才能使用 `y`。外部 F 的完成协议必须能接入这些依赖，不能把“函数已返回但后台仍在写入”当作完成。

`x` 和调用方提供的 `y` 默认归调用方所有，ASK 不释放它们。运行时应持有需要的生命周期令牌，或在 ABI 中要求调用方保持分配有效直到完成。这个例子中，若 `t`、`u` 是独立临时分配且没有其他消费者，`t` 可在 F 完成后释放，`u` 可在 Q 完成后释放；存在别名时，必须等所有相关访问完成。

初期可以顺序执行并保守分配。以后复用临时存储时，要证明前一次使用已完成，后一次使用尚未开始，并考虑别名及并发队列。任务在拓扑序中相邻不等于它们的内存使用时间不重叠；宿主对象被回收也不意味着异步计算已经结束。

## 6. 错误发生在哪一步，就在那一步处理

参数个数、dtype、地址范围或必需的别名前提不符合时，提交前失败，不产生计算副作用。某个优化变体的额外条件不成立，只表示不能选它；如果有符合公开语义的其他变体，可以正常执行。

合法 IR 已导入但缺少启动说明，或者当前后端不能处理其中的 asm，都可以明确报告尚不可执行。如果另有已经验证的原 F 调用产物，可以保留该调用；损坏模块不能作为回退来源，也不能因存在回退就掩盖其验证错误。加载时缺少外部符号同样必须报告。诊断应带上区域、实现与工具链版本、失败阶段和复现产物。

一旦执行开始，不能在中途失败后自动从头运行未融合版本。即使示例只有数组写入，也可能已写了一部分 `y`；更一般的图还可能已经更新外部状态。运行时报告执行错误及已提交工作状态，按执行上下文等待或清理剩余工作，不自动重放。

“此边界未融合”则是正常决策。例如缺少 F 的内部访问说明时，运行时仍按三个合法入口执行，并可返回保留边界的原因。它与非法 IR、缺失实现或执行失败使用不同的状态。

## 7. 哪些东西可以缓存

编译缓存保存代码和上述调用说明，键必须反映会改变结果的输入：高层语义、常量、外部实现及依赖内容，目标和 data layout，数值模式，形状与守卫条件，F 的完整固定策略摘要，最终融合方案，以及 ASK 契约、ABI、适配器、工具链和 Pass 配置版本。依赖库的调用契约改变，也必须使旧产物失效。

内容摘要必须把代码与它的入口、布局及执行计划绑定在一起。命中缓存后仍检查包版本、目标兼容性和依赖是否存在。不能把旧代码与新签名拼起来使用，也不能因为另一个目标更强，就未经后端兼容检查直接加载。

Triton override 的验证还要检查外部工具链自己的缓存。替换同一路径下的 IR 文件，不能默认工具链一定会重新编译；应使用按内容区分的输入和缓存记录，并核对最终代码对应的 IR 摘要。

已经加载的对象使用另一层缓存，它还依赖当前执行上下文和运行库生命周期。磁盘上保存的是可重新加载的代码与描述，不是进程里的函数指针、分配地址或设备句柄。进程结束后，这些句柄不能恢复使用。

为便于复现，序列化字段和符号命名应稳定，并保存实际选项及依赖摘要。如果工具链不能保证同样输入产生逐字节相同的机器码，就明确这一限制，不能把“能够重跑相同编译”写成“二进制必然完全一致”。

首期先验证真实 Triton LLVM IR 接入后能重新生成、加载和执行，并与 P/Q 组成正确的未融合计划；允许保留原有 inline asm，不要求先有内部访问映射。分别注入缺失 launch 信息和后端不支持的目标指令，确认“已接入”和“可执行”没有混淆。

后续启用融合时，再让融合、局部融合和未融合三个版本计算同一组 `i32` 输入，逐位比较输出，并覆盖溢出、零长度、切片和实参别名。用延迟事件检查临时缓冲区不会提前释放，用资源失败检查编译重试有界，用部分执行失败检查不会自动重放；最后改变工具链、F 配置或 ABI 版本，确认旧缓存不再命中。
