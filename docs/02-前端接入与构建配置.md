# 02. 前端接入与构建配置

返回核心思想：[构建、绑定与适配器白名单](核心思想.md#ask-frontend-build) · 相关细节：[ASK IR 与数值语义](01-ASK-IR与数值语义.md) · [外部编译器适配与边界内联](04-外部编译器适配与边界内联.md) · [工程结构与测试体系](06-工程结构与测试体系.md)

ASK 同时提供进程内 Python SDK（基于 `nanobind`）、独立 C++ 库（`ASK::Core`）以及命令行驱动 `ask-opt`。本章说明如何用最简命令拉取锁定依赖、配置不同构建模式，以及从 Python 或 C++ 框架提交计算图。

<a id="build-workflow"></a>

## 1. 依赖获取与零参数 CMake 构建

构建环境需要 C++17 编译器、CMake 3.28+、Ninja 和 Python 3.10+（含开发头文件）。ASK 使用的 LLVM/MLIR（当前锁定 `23.0.0git` 特定提交，与 Triton 3.7.1 上游 LLVM 版本对齐）和 `nanobind`（`3.1.0`）记录在 `cmake/llvm.lock.json` 与 `cmake/nanobind.lock.json` 中。

在仓库根目录只需三步即可完成拉取、构建与测试：

```bash
python3 tools/fetch_deps.py
cmake --preset core
cmake --build --preset core
ctest --preset core
```

- `tools/fetch_deps.py` 支持默认同时准备 `llvm` 与 `nanobind`，也支持 `--only llvm` 或 `--only nanobind`。它会校验归档的 SHA-256 摘要、拦截压缩包路径穿越与非法软链，并在 `.deps/<dir>/` 下写入收据文件（`.ask-sdk.json` / `.ask-nanobind.json`）；已就绪时秒级跳过重复下载。
- `CMakeLists.txt` 会自动读取 `cmake/llvm.lock.json` 并在 `.deps/` 下定位 `LLVM_DIR` 与 `MLIR_DIR`，日常本地构建不再需要手写一长串 `-DLLVM_DIR=... -DMLIR_DIR=...`。跨平台或使用外部自定义同修订 LLVM 安装时，仍可通过 `-DLLVM_DIR` / `-DMLIR_DIR` 显式覆盖。

如果需要把 ASK 作为 Python 包安装到虚拟环境中（如 [FugaTensor 的 `tools/bootstrap.py`](../../fugatensor/docs/architecture/04-ASK桥接与多后端执行.md#bootstrap-and-config) 所做的那样），直接通过 `pip` 调用 `scikit-build-core` 即可：

```bash
python -m pip install . --no-deps --no-build-isolation \
  -Ccmake.define.ASK_THIRD_PARTY_COMPILERS=all
```

## 2. 构建预设与第三方编译器白名单

`CMakePresets.json` 提供了三个常用预设：

| Preset | `ASK_THIRD_PARTY_COMPILERS` | 适用场景 |
| --- | --- | --- |
| `core` | `none` | 纯自有 CPU + 自有 CUDA 编译与运行时，零第三方 Python 依赖（无需 Triton / PyTorch / NumPy）。 |
| `triton` | `triton` | 在 `core` 基础上编译并注册 `adapters/triton/` C++ 边界校验器、worker 与专属测试。 |
| `all` | `all` | 启用 `adapters/registry.json` 中登记的全部第三方编译器适配器。 |

这里有两条关键工程约束（实现见 `cmake/AskCompilerSelection.cmake` 与 `cmake/AskCompilerRegistry.cmake`）：

1. **显式白名单，绝不自动探测环境**：启用哪些适配器完全由 `ASK_THIRD_PARTY_COMPILERS` 和 `adapters/registry.json` 决定；即便当前 Python 环境装有 `triton`，`core` 构建也绝不会隐式把它编进来。
2. **默认复用当前 Python 解释器**：当使用装有 Triton 的虚拟环境配置 `triton` 或 `all` 预设时（例如 `cmake --preset all -DPython_EXECUTABLE=/path/to/.venv/bin/python`），`adapters/triton/CMakeLists.txt` 会自动将 `ASK_TRITON_PYTHON_EXECUTABLE` 默认指向该解释器；只有当 SDK Python 与 Triton worker Python 分属两个不同虚拟环境时，才需要显式传 `-DASK_TRITON_PYTHON_EXECUTABLE=...`。

## 3. Python SDK：进程内编译器与图构造

Python 入口位于 `python/ask/`，搭配 C++ 扩展 `ask._native`（源码见 `bindings/`）：

```python
from ask import Compiler, Module, TensorType

module = Module()
t = TensorType((16,), "f32")
g = module.graph("axpy", inputs={"x": t}, results=[t])
two = g.splat(g.constant(2.0, dtype="f32"), (16,))
one = g.splat(g.constant(1.0, dtype="f32"), (16,))
g.return_(g.add(g.mul(g.inputs["x"], two, id="scale"), one, id="shift"))

compiler = Compiler()                 # 默认走进程内 nanobind C++ 绑定
prepared = compiler.prepare(module)   # 类型/形状检查 + 标记提取擦除
optimized = compiler.optimize(module) # 常量折叠 + 死代码消除 + 逐元素融合分组
```

- **进程内调用与伴生 CLI 校验**：`Compiler()` 不传参数时直接在当前进程内创建独立的 `mlir::MLIRContext` 完成 `prepare` 和 `optimize`，线程安全且无子进程开销。当后续调用 `compile_cuda` 等需要外部工具链的步骤时，`Compiler._check_companion()` 会核对随包安装的 `ask-opt --capabilities` 与内存中的 `_native` 扩展具有完全一致的构建指纹，杜绝混用不同构建产物。
- **CLI 兼容模式**：传入 `Compiler("/path/to/ask-opt")` 则显式切换到子进程 CLI 模式，返回完全相同的 `PreparedModule(ir, report)` 数据结构。
- **可直接运行的 Python 示例**：
  - `examples/framework_frontend.py`：构造 `P -> Triton F -> Q` 计算图并查看 `prepare` 报告。
  - `examples/optimize_frontend.py`：演示常量折叠、无用分支与标记消除以及共享输出融合组。
  - `examples/triton_fused_gpu.py`：端到端编译并在真实 GPU 上用 `ExecutionSession` 运行 `ASK -> Triton -> ASK` 融合核。

## 4. C++ 原生接入（`ASK::Core`）

C++ 框架无需经过 Python 解释器，直接 `find_package(ASK CONFIG REQUIRED COMPONENTS Core)` 链接 `ASK::Core` 即可使用 `include/ask/Frontend/Compiler.h` 中的 `ask::prepareModule`、`ask::optimizeModule` 与 `ask::capabilitiesJson`（完整示例见 `examples/cpp/CMakeLists.txt` 与 `examples/cpp/frontend.cpp`）。

## 5. `ask-opt` 命令行入口速查

`tools/ask-opt.cpp` 把所有底层阶段暴露成了清晰的命令行动作，方便单独调试任一阶段：

| 参数 | 输入 → 输出 | 说明 |
| --- | --- | --- |
| `--capabilities` | 无 → JSON | 输出当前构建支持的后端、已启用适配器、主机 `bf16` 硬件支持与协议版本。 |
| `--prepare` | ASK MLIR → Prepared MLIR | 校验语义与形状、提取并擦除 `ask.mark`，配合 `--report-json` 输出准备报告。 |
| `--optimize` | ASK MLIR → Optimized MLIR | 在 `--prepare` 基础上运行常量/类型折叠、DCE 和逐元素融合分组（支持 `--no-constant-fold` / `--no-dce` / `--no-fusion`）。 |
| `--emit-llvm` / `--emit-object` | 纯自有 ASK MLIR → Host `.ll` / `.o` | 生成 CPU 共享循环 LLVM IR 或本机目标文件。 |
| `--emit-cuda-llvm` | 纯自有 ASK MLIR → NVPTX `.ll` | 按 `--cuda-arch <sm>` 与 `--cuda-block-size` 生成自有 CUDA kernel LLVM IR。 |
| `--fuse-external` | 含 `ask.external` 的 ASK MLIR → Fused NVPTX `.ll` | 驱动外部适配器导出 LLVM IR，校验边界并内联前后自有算子。 |
| `--check-llir` / `--optimize-llir` | 原生 `.ll` → `.ll` | 验证或清理原生 LLVM IR（保留内联 PTX 与目标 intrinsic）。 |
