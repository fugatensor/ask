# 04. 外部编译器适配与边界内联

返回核心思想：[外部适配与通用值边界融合](核心思想.md#ask-external-fusion) · 相关细节：[ASK IR 与数值语义](01-ASK-IR与数值语义.md#external-declaration) · [图优化与自有代码生成](03-图优化与自有代码生成.md) · [常驻运行时与多级缓存](05-常驻运行时与多级缓存.md)

对于 `P: t = x + 1 → F: Triton kernel → Q: y = u + 3` 这类受支持的混合图，ASK 调用外部编译器导出原生 LLVM IR，并将前后自有计算 `P`、`Q` 内联进 `F` 的同一个 GPU kernel，消除中间结果往返全局显存的读写。当前图级融合要求恰好一个函数、一个非空静态张量输入、一个同形状同存储类型的输出，以及一个无副作用的 `ask.external`；中间张量形状也必须一致。单 kernel 融合不满足结构或边界证明时，由[图切分与执行计划](08-图切分与多Kernel执行计划.md#fusion-fallback)退化为多个 kernel。独立外部步骤不要求逐元素边界，非法图、坏导出和代码生成失败仍报错。这套机制拆分为适配器目录与编译器无关的 LLVM 值边界内联核心两部分。

<a id="adapter-architecture"></a>

## 1. `adapters/<id>/` 插件式注册架构

第三方编译器相关代码隔离在 `adapters/<id>/` 目录下，公共层通过 `include/ask/Adapters/Compiler.h`（C++）与 `python/ask/adapters.py`（Python）按显式注册表调用：

- **`adapters/registry.json`**：白名单文件，记录允许构建的编译器 ID 到子目录名的映射（当前为 `"triton": "triton"`）。
- **`adapters/<id>/registration.json`**：声明协议版本、C++ `CompilerAdapter` 工厂符号、Python 策略工厂路径、导出 `worker` 脚本名及兼容参数别名。
- **`adapters/<id>/dependencies.lock.json`**：锁定外部编译器包版本（`triton==3.7.1`）及配套 LLVM 提交哈希。

只有在 CMake 构建时由 `ASK_THIRD_PARTY_COMPILERS` 选中的适配器才会编入 `ask_compilers` 并写入生成的注册表；公共层不扫描 Python `entrypoints`，也不隐式导入环境中存在的包。Triton 目录内各文件说明见 [`adapters/triton/README.md`](../adapters/triton/README.md)。

<a id="export-protocol"></a>

## 2. 跨进程导出协议与执行契约（ABI v2）

外部编译器往往依赖特定 Python 环境并持有全局编译状态，因此 DSL 导出放在独立 `worker` 子进程（如 `adapters/triton/worker.py`）中通过 JSON 请求/响应协议（`protocol_version = 1`）执行，宿主框架进程无需导入 Triton：

1. **请求（Request）**：包含 DSL 原文 `source`、`entry`、`signature`、`source_bindings`（如 `{"inp": "input:0", "out": "output:0"}`）、`constants`（如 `N`、`BLOCK`）、`fixed_options`（由 `ask.implementation` 的 `options` 导出，如 `num_warps`、`enable_fp_fusion`）、`target`（`arch`、`warp_size`）、`grid` 以及可选融合开关 `fusion.enabled`。
2. **响应产物（Artifact）**：worker 调用外部编译器公开 API（对 Triton 3.7.1 为 `ASTSource` + `triton.compile` + `compiled.asm["llir"]`）导出原生 LLVM IR，经临时文件原子替换写出 JSON，交付 `invocation` v2 执行契约：
   - `payload` / `entry`：原生 LLVM IR 文本与物理 kernel 函数名。
   - `port_map`：逻辑端口（`input:0`、`output:0`）到物理参数序号、形状、`element_type` 和连续行主序布局的映射。
   - `invocation`：`version = 2`、`kind = "cuda-kernel"`、`grid` `[gx, gy, gz]`、`block` `[bx, by, bz]`、`shared_bytes` 以及物理参数列表（Triton 3.7.1 自动追加的未使用 scratch 指针经校验后绑定为 `"null"`，公共 CUDA 运行时直接按列表传参）。
   - `required_element_types`：包含端口类型及从 `ttir` 识别出的内部 `bf16` 依赖，供运行时拦截低于 `sm_80` 的显卡。

<a id="boundary-inliner"></a>

## 3. 通用 LLVM 值边界内联核心（`lib/LLIR/Inline.cpp`）

`include/ask/LLIR/Inline.h` 与 `lib/LLIR/Inline.cpp` 不包含特定外部编译器的判断逻辑，输入由两部分组成：

1. **已确认的值边界（Value Boundary Sites）**：指定外部 `llvm::Module` 中代表逻辑输入读取结果（`input` 站点）和逻辑输出待写出值（`output` 站点）的指令位置，支持多参数、标量（整数/浮点/`i1`）与定长向量（当外部编译器生成向量化访存时，同一逻辑边界对应多个站点）。
2. **Typed Helper 模块**：由 `lib/LLIR/Fuse.cpp` 将前驱 `P` 和后继 `Q` 的 ASK 子图降级为无内存副作用的纯值变换 LLVM 函数。

内联器在克隆出的模块副本上按顺序执行：

1. 校验 helper 模块只含纯计算指令（不含全局访存、未知外部调用或其它副作用），校验各边界站点的 LLVM 类型与 helper 签名一致，并检查支配关系。
2. 将 helper 模块链接进外部模块副本，在输入边界站点后插入前驱 helper 调用，在输出边界站点前插入后继 helper 调用。
3. 内联全部 helper 调用，移除恒等追踪标记指令，并对新模块运行 `llvm::verifyModule`。
4. 任一步骤失败则丢弃副本，保留原输入 `llvm::Module` 不变并返回诊断信息。

<a id="triton-fusion"></a>

## 4. Triton `P → F → Q` 融合检查顺序

融合时保持 `F` 的线程布局和访存方式不变，将 `P` 和 `Q` 内联到 `F` 的寄存器值流上。Triton 适配器（`adapters/triton/fusion.py` 与 `adapters/triton/lib/TritonBoundary.cpp`）依次完成四步检查：

1. **AST 静态数据流检查**：解析 `@triton.jit` 源码，确认入口只对 `input:0` 指针执行一次带掩码 `tl.load`，经纯逐元素表达式（支持局部变量重绑定、仿射偏移别名、位置/关键字参数及显式 `.to(...)` 类型转换）后，用等价的偏移与掩码对 `output:0` 指针执行一次 `tl.store`；不含 `tl.sum`、`tl.dot`、原子操作或共享内存访问。
2. **注入恒等位标记与双编译比对**：在 load 结果后和 store 值前通过 `tl.inline_asm_elementwise` 插入恒等内联汇编标记（`bool` 用 `mov.pred`，16/32/64 位分别用 `mov.b16` / `mov.b32` / `mov.b64`）。worker 同时编译未加标记版与加标记版 DSL，核对两者的 `ttgir` blocked layout、`num_warps`、`shared_bytes` 和物理参数签名一致。
3. **C++ 边界与掩码校验（`TritonBoundary.cpp`）**：在 LLVM IR 层回溯每个标记站点的指针地址计算与 `pred` 掩码条件，按元素字节宽度证明其对应 `0 <= idx < N` 的连续线性元素范围。
4. **内联 `P` 与 `Q`**：调用 `inlineValueBoundaries` 合入 `P`/`Q` helper 并移除标记；最终产物的端口形状更新为外层 ASK 图的多维形状，整条 `P → F → Q` 链由单次 `cuLaunchKernel` 执行。

<a id="fma-and-numerics"></a>

## 5. 跨编译器浮点收缩（FMA）与转换语义隔离

Triton 默认开启浮点乘加融合（`enable_fp_fusion=True`），而 ASK 自有算子 `P` 和 `Q` 默认禁止 FMA（乘法与加法各自独立 RNE 舍入）。若统一对整个模块传 `llc -fp-contract=fast` 会改变 `P`/`Q` 的舍入结果，传 `-fp-contract=off` 则会关闭 `F` 原有的 FMA。

`TritonBoundary.cpp` 通过指令级标志区分两者：

- 内联 `P`、`Q` 之前，适配器根据 `F` 的 `enable_fp_fusion` 配置，仅对 `F` 原有的 LLVM 浮点指令设置或清除 `contract` fast-math 标志；
- ASK 为 `P`、`Q` 生成的 helper 指令不带 `contract` 标志；
- 调用 `llc` 时使用 `-fp-contract=on`（仅允许带 `contract` 标志的指令生成 `fma.rn`）。

由此在同一条融合 PTX kernel 内，`F` 保留自身的 FMA 开关与 `.to(...)` 转换语义，`P` 和 `Q` 保持 ASK 的独立 RNE 舍入与饱和类型转换语义。
