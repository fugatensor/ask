# ASK IR 怎样降到 LLVM，哪些信息必须留下

[ASK IR 索引](README.md) · [返回顶层设计：B 层](../核心思想.md#ask-b) · [B 层工程设计](../03-B层多源降级与低层归一化.md)

本文描述拟实现的降级流程。ASK IR 是 A 层 `SemanticModule` 的具体 MLIR 表示，核心操作属于 `ask` dialect；ASK LLIR 则是原生 LLVM IR，两者不是同一种表示。

## 1. 先把计算分成两条路

继续使用一维 `i32` 张量上的计算，所有加法和乘法按模 `2^32` 进行：

```text
P: t[i] = x[i] + 1       // ASK 自有计算
F: u[i] = t[i] * 2       // 外部实现，首期来自 Triton
Q: y[i] = u[i] + 3       // ASK 自有计算
```

图编译的输入由上层框架准备：框架生成基础高层 ASK IR，用 `ask.external` 明确表示需要第三方编译器处理的计算，并提交对应 DSL。这个节点是编译边界，包含 `semantics` 和 `implementation` 符号引用；它与只记录追踪位置的纯 identity `ask.mark` 不同。ASK 不从任意框架 IR 猜测第三方区域，也不从 LLVM IR 反造 DSL。具体节点和实现记录见[external 的输入约定](00-结构类型与操作.md#external)。

`implementation` 解析到 `ImplementationReference`。框架提供其中的 `compiler_id`、`DSLSource`、`source_bindings`、`constants` 和 `fixed_options`。`DSLSource` 记录 `source_ref`、内容 `digest`、`language`、源入口 `entry` 和源码依赖 `deps`；语言细节由对应导出器解释。首期导出器在独立工作进程中运行，客户端接收的 callable 必须先转成 worker 可解析的源码及捕获值、全局常量和辅助函数依赖；无法完成就报不支持，不能直接传对象地址或 pickle。环境选择与启用清单见[构建设计](../09-构建与可选编译器.md#workers)。

`source_bindings` 回答“DSL 源参数对应哪个逻辑端口或编译常量”。例如源接口 `F(t_ptr, u_ptr, N: constexpr)` 中，`t_ptr` 对应输入 t，`u_ptr` 对应输出 u，`N` 对应 `constants.N=10`。图仍可表达为 `F(t) -> u`，输出指针不必伪装成一个额外高层输入。B 层核对这些关系与形状快照，再按 `compiler_id` 找到导出器，将 DSL 放入 `ExportRequest.source` 请求编译。

编译结束后，导出器才返回 `LLIRArtifact.port_map`，说明**实际 LLVM 入口**怎样接收这些端口。上例的 N 可能已被 constexpr 消除，只剩两个指针；也可能出现编译器增加的 scratch 参数。源 `entry` 与最终 LLVM 符号也可能不同。因此 `source_bindings` 不能直接当成 `port_map`：前者用于发起编译，后者依据本次产物回填，并由 importer 对照物理签名检查。

P、Q 交给 ASK 的 MLIR 降级流水线；F 的 DSL 则由首期 Triton 导出器通过公开接口编译，原生 LLVM 结果直接进入 importer。F 不需要先转回 MLIR，也不经过 ASK 对 P/Q 使用的 bufferization。直接导入已有 LLVM 文件仍是可用的低层工具入口，但不是这条图编译流程的主入口。

两条路最后汇入原生 LLVM 模块及执行计划。初期计划可以是三个独立入口，运行时依次提交 P、F、Q；不能把三个 GPU kernel 的符号当成普通设备函数，简单写三个 `call` 就认为完成了组合。入口怎样启动、何时完成、哪些缓冲区在入口之间传递，仍由执行计划说明。后续融合是 C 层的可选变换。

下表列出自有计算的主流程。它规定每步要交付什么，不规定所有目标必须使用完全相同的 Pass 列表。

| 阶段 | 输入 | 输出及下一步依赖的信息 |
|---|---|---|
| 验证与形状推导 | ASK IR、语义与形状规则注册表、具体输入特化 | 类型正确的 IR、`ShapeEnv`，以及尚未满足的约束 |
| 冻结本次编译 | 所有维度均已确定的形状结果 | 不可变 `ShapeSnapshot`、语义版本和特化条件 |
| 划分区域 | ASK IR、快照、已选定的 F 实现与固定策略 | `RegionPlan`、语义端口对应 `PortBinding` |
| 编译外部区域 | external 引用的 DSL、`source_bindings`、常量与固定选项 | 导出器返回原生 LLVM、实际 `port_map` 和调用说明，不经过下面的自有张量降级 |
| 降级自有张量计算 | P/Q 区域及其输入输出契约 | 适用的 `linalg`、`arith`、`tensor` 等操作，保留值来源 |
| 分配与绑定存储 | 张量计算、入口布局及别名要求 | buffer 形式的计算、`BufferBinding`、结果和所有权约定 |
| 选择目标执行形式 | buffer 计算、目标能力与固定 F 边界 | 循环、向量、地址计算、掩码及入口配置 |
| 类型转换与翻译 | 已能降到目标的 MLIR 计算 | 原生 `llvm::Module`、完整物理 ABI 对应 `LoweringMap` |
| 验证与封装 | LLVM 模块、调用与目标说明 | `LLIRArtifact`，再交统一接入流程和 C 层 |
| 效果链的处理 | `!ask.token` 依赖 | 执行计划的先后与完成依赖，不生成物理参数或设备伪指令 |

结构、类型和操作定义见[结构、类型与操作](00-结构类型与操作.md)。首版只处理静态图和静态尺寸；图级动态控制由上层框架处理，算子内部的循环、条件与掩码可以继续向下生成。

## 2. 形状先确定，再决定怎样存储

验证首先检查 SSA、操作类型和属性，再运行形状规则。例如 `ask.add`、`ask.mul` 的两个张量必须同形；需要广播时，图中应有显式的 `ask.broadcast`，不能等降级到循环时才猜测用户的意思。`ask.external` 的结果形状来自其已注册语义规则，与实现引用分开检查。

首版只有在所有张量的 rank 和尺寸都已确定、所需约束均已证明时，才能冻结本次编译。未解出的维度、矛盾的 reshape 元素数或不合法的 slice 范围，在这里报告；不能先生成指针，再把未知尺寸填成某个方便的值。

`ShapeSnapshot` 使用[形状推导与约束](02-形状推导与约束.md)定义的记录：`semantic_revision`、`shape_rule_versions`、按 `ValueId` 保存的 `shape_bindings`、`input_specialization`、`checked_constraints` 和 `snapshot_digest`。其中规则版本包括外部语义所用的形状规则版本。摘要标识这份冻结记录，后面的区域、调用绑定和缓存都引用它，不再读取一个仍会变化的 `ShapeEnv`。

冻结的是逻辑形状，不是内存布局。`tensor<10xi32>` 说明有十个 `i32` 元素，尚未说明地址间隔、偏移、分配大小或目标存储域。相同的逻辑张量既可能来自连续数组，也可能来自一个切片；后续必须根据入口允许的布局选择直接使用、转换布局或拒绝调用。

`PortBinding` 在此时把区域的数据输入输出端口对应到 `ValueId` 和快照中的形状记录。一个外部入口即使没有任何指令级追踪，也必须知道传入的数据对应哪个语义端口。效果 token 另行形成顺序依赖，不进入张量形状表，也不塞进外部实现的物理参数列表。

## 3. 自有操作降成计算，标记只导出关系

`ask.constant` 表示标量常量，可以降成 `arith.constant`。将标量铺到张量上由 `ask.splat` 明确表达；它与同形的 `ask.add`、`ask.mul` 可降为结构化张量计算，元素运算使用相应标量算术。`ask.cast` 沿用相同元素索引，在标量表达式中完成转换；即使前后形状相同，也不能删除会舍入或饱和的转换。bool 的 i1 计算值与一字节存储在读写边界转换。当前 cast 降级及混合精度规则见[第 15 章](../15-类型转换与混合精度.md)。后续实现 `ask.broadcast`、`ask.transpose`、`ask.slice` 和 `ask.reshape` 时，这一步还应保留它们的索引对应关系。

这不是逐个操作名称机械替换。transpose 或 slice 到了 buffer 层可能只是视图，也可能为了满足下一入口布局而需要复制；reshape 只有在实际布局允许时才能复用同一存储。无论最后是否复制，其逻辑结果都有自己的 `ValueId` 和形状记录，不能因为共享分配就把结果认作原来的逻辑值。

`ask.reduce` 还必须保留归约维度、初值、空输入规则和数值约束。浮点归约不能因为换成树形计算更方便就默认允许重排。本篇 `i32` 例子的模运算也不能被降成带未经证明的无溢出假设的指令。首版某种操作或类型没有合法降级时，就定位到该操作报错，不承诺通用 Pass 能处理所有组合。

`ask.mark(T) -> T` 只记录追踪站点，不改变计算、形状、效果或所有权。降级前先将站点关系写入可选 `MarkTable` 或追踪记录，再以输入替换结果并删除 marker。两处 SSA 定义引用可以不同，但指向同一个 `ValueId` 和 `ShapeState`；不会因此多分配一个 buffer。必须在可能擦除 marker 的普通清理 Pass 之前收集关系，之后由改写更新或使该关系失效。

最终不会生成 `ask.mark` 的运行时调用、内存写入或专用 LLVM 指令。对外部编译器，只有公开扩展点明确支持语义不变的追踪载体时，才允许插入这种标记；否则保留入口、参数、返回值等边界对应。首期 Triton 不假定存在可用的 pre-LLVM 标记注入钩子，不修改源码或复制内部编译阶段来补上它。具体规则见[标记算子与追踪](01-标记算子与追踪.md)。

## 4. Bufferization 决定哪些值可以共用存储

张量 SSA 值本身不承诺就地更新。将它变成 buffer 计算时，需要判断旧值以后是否还会被读取、输出是否允许与输入重叠，以及谁负责释放新分配。如果 P 的输入还被别处使用，就不能仅因尺寸相同而覆盖它；如果输出是调用方提供的存储，也不能默认由 P 释放。

ASK 先把自有操作降为已支持 bufferization 的操作，再对这些区域运行相应分析。MLIR 的 One-Shot Bufferize 通过 `BufferizableOpInterface` 获取读写和别名信息；未知张量操作默认不能直接完成 bufferization。允许未知操作只会留下转换边界，并不提供该操作的内存语义。因此，不能把任意 `ask.external` 留在区域中，打开一个选项就声称 F 已被正确处理。[MLIR Bufferization](https://mlir.llvm.org/docs/Bufferization/#using-one-shot-bufferize)

首版在这之前分离外部区域，将 F 的输入输出接到执行计划。若以后要在某段 MLIR 内直接表示外部调用，则必须为这种调用提供明确的 bufferization model，说明读、写、别名、结果和调用规则；该 model 也不能把异步 GPU 启动伪装成同步函数返回。

每个实际存储视图形成 `BufferBinding`。它记录逻辑 `ValueId` 与 `BufferId` 的关系，并保留逻辑形状、元素类型、字节 stride、字节 offset、分配大小、目标存储域、对齐、读写权限、别名和所有权。执行计划用它分配和传递临时存储，后端用它生成地址，运行时用它检查实参范围。MLIR memref 中以元素计的 stride/offset 转成字节描述时，必须按元素大小进行有溢出检查的换算。

结果约定也在这里确定。首版可以让跨入口的输出使用调用方或执行计划提供的目标 buffer，避免含糊的“返回一个指针以后再猜谁释放”。如果选择返回新分配，就要显式记录所有权转移；如果返回视图，就要保留它与原分配的别名和生命周期关系。

One-Shot Bufferize 本身不插入释放操作；MLIR 另有基于所有权的释放流程，并有自己的函数边界规则。ASK 只能在这些规则成立的自有同步区域内使用它。跨异步入口的 buffer 由执行计划持有，直到相关完成事件满足后再释放，不能在发起 launch 的宿主函数返回时释放。[MLIR Ownership-based Buffer Deallocation](https://mlir.llvm.org/docs/OwnershipBasedBufferDeallocation/)

## 5. 形状、向量宽度和掩码分别记录

有了存储以后，目标后端选择循环组织、向量宽度和地址计算方式。这些是实现选择，不能反过来改写已经冻结的张量尺寸。P/Q 可以调整来适配 F 的既有布局和调用约定；F 已冻结的布局、执行映射、启动配置和数值策略不因此重选。多个外部要求冲突时，保留边界或插入明确的相邻布局转换。

例如 `N=10`，某个 P/Q 实现每次处理 `W=4` 个元素：

```text
i = 4 * block + lane       lane ∈ {0, 1, 2, 3}
valid = i < 10
若 valid：读取 x[i]，计算 x[i] + 1，写入 t[i]
```

三组索引分别为 `0..3`、`4..7` 和 `8..11`，最后一组的有效掩码是 `[true, true, false, false]`。`ShapeSnapshot` 中尺寸仍为 `[10]`；`W=4` 属于这份实现的配置；掩码属于具体访问的有效条件。不能把逻辑尺寸改成 12，也不能仅凭代码用了四个 lane 就认为分配多出了两个可访问元素。

若 `t` 是从零偏移开始的连续 `i32` 分配，最小容量是 40 字节，合法元素首地址为 `0, 4, ..., 36`。最后两个 lane 的 load 和 store 必须被真正抑制；先执行越界 load 再用 `select` 丢掉结果不成立。后端可以选择有相应语义的 masked 访问，或生成条件控制流。目标不支持所选形式时，P/Q 可以退回标量循环。

首版先保证连续布局及明确支持的视图。负 stride、零 stride、重叠写入或特殊地址空间没有实现时，应明确拒绝，不能套用连续数组的地址公式。零尺寸同样需要单独检查：没有有效元素，就不产生一次“占位”的内存访问。更完整的调用范围检查见[代码生成与运行时](../05-代码生成与运行时.md)。

## 6. 类型转换不能丢掉参数的来历

从 memref、循环和向量继续降到 LLVM 时，张量类型逐步消失。一个逻辑输入可能变成指针、offset、sizes 和 strides 等多个参数，也可能因为特化只剩一个指针。ASK 用 `LoweringMap` 记录这些转换，至少覆盖所有物理入口参数、返回值、隐藏资源参数和被特化消除的逻辑参数。

`LoweringMap` 是调用正确性所需的对应关系。例如它应能回答“物理参数 2 是哪个 buffer 的 offset，由谁填入”，但不必回答“某条 LLVM load 对应 `t` 的哪个逻辑元素”。后一个问题属于可选 `BoundaryMap`。不能因为尚未追踪到每条指令，就拒绝一个已有完整参数对应的入口。

MLIR 的 `TypeConverter` 和签名转换机制允许一个源类型转成多个目标类型，也允许删除已由其他值替代的参数。ASK 的转换代码必须同步记录这种变化，不能在最后按参数序号拼回旧映射。每一阶段声明允许留下哪些操作和类型；到最终导出阶段，不得还留未处理的 `ask` 操作或未解决的 `unrealized_conversion_cast`。[MLIR Dialect Conversion](https://mlir.llvm.org/docs/DialectConversion/#type-conversion)

自有路径可以把 MLIR LLVM dialect 作为最后一个短暂中间表示，然后翻译成原生 LLVM IR。MLIR 官方流程区分 dialect conversion 与 LLVM IR translation；ASK 也在翻译前完成目标所需的类型与操作转换，再验证生成的 `llvm::Module`。这不是将 ASK LLIR 改成 MLIR LLVM dialect。[MLIR LLVM IR Target](https://mlir.llvm.org/docs/TargetLLVMIR/)

目标 data layout、指针宽度、index 位宽、地址空间和调用 ABI 必须在这些转换中一致。MLIR 默认 memref descriptor 不是 Triton 的通用调用 ABI；如果选择它作为自有入口的内部表示，跨入口仍需按明确规则封送。LLVM 中出现一个 `ptr`，既不能据此恢复张量尺寸，也不能推断它对应 memref descriptor 还是一段裸数据。

## 7. 将形状和调用说明一起交给现有接入 API

自有路径生成原生 LLVM IR 后，也形成 [LLIRArtifact](../08-第三方LLIR接入API.md)。形状记录以随产物保存的版本化附属数据保留，不再发明一套执行程序的低层 IR。已有字段承担以下工作：

| 既有字段或参数 | 与本次形状、调用的关系 |
|---|---|
| `binding` | 引用已注册语义及输入特化，关联本次 `ShapeSnapshot` 的摘要和语义版本 |
| `specializations` | 保存已固化的尺寸、常量与实现配置；其内容须与快照一致 |
| `port_map` | 由 `PortBinding` 和 `LoweringMap` 生成实际入口的逻辑端口到物理参数、结果或常量对应 |
| `invocation` | 按版本化调用约定使用 `BufferBinding` 封送参数，记录启动、临时资源和完成方式 |
| `target`、`dependencies` | 绑定地址空间、data layout、工具链及相关依赖版本 |
| 可选 `trace` | 携带标记及指令级 `BoundaryMap` 等分析，绑定产物摘要和 IR revision |

这里是 ASK 图编译如何填充既有接口的约定，不要求所有 LLVM 文件携带这些记录。直接调用 `import_artifact(artifact)` 检查一份原生 IR 时，可以没有 shape、`binding` 或 `trace`。只有要把入口用于这张张量图，才必须补齐形状、语义端口与调用契约；所需字段缺失时报告缺项，不能从 LLVM 指针猜出答案。

外部 F 的导出器以 DSL、`source_bindings` 和本次编译结果共同建立 `port_map`，返回特化和调用说明。ASK 再与冻结快照核对，包括参数是否被特化删除、结果是否通过输出指针写回、隐藏 scratch 参数由谁提供。源码依赖 `DSLSource.deps` 用来确定本次编译输入；产物的 `dependencies` 则描述后续链接或加载需要的依赖，不能遗漏其中任何一类。Triton 首期可以没有内部 `BoundaryMap`；它导出的 inline PTX 与目标 intrinsic 原样进入原生 LLVM 模块，能否生成代码由目标后端检查，能否优化其访问另行分析。

## 8. 改了什么，就使相应记录失效

每次转换发布的是代码和对应记录的一致版本。若一个变换会同时修改签名、布局和计划，应先在副本上完成，再一起验证和提交；不能先让执行计划看到新参数表，却继续引用旧函数。

| 变化 | 必须重建或核对的记录 |
|---|---|
| 输入尺寸、形状规则或高层计算改变 | 新 `semantic_revision` 或规则版本下重新推导并冻结快照；重新检查区域和特化产物 |
| 仅调整 P/Q 的 stride、分配、视图或目标存储域 | 逻辑形状可不变；更新 `BufferBinding`、地址计算、调用说明、相关资源与别名检查 |
| 参数拆分、删除、重排或入口结果改变 | 更新 `LoweringMap`、`port_map`、物理签名与调用封送，并使旧调用产物失效 |
| 改写循环、索引或指令 | 更新 IR revision，使受影响的 `BoundaryMap`、`ExecutionMap` 和其他分析失效或重算 |
| 消除中间 buffer | 删除其实际分配和传参，但保留逻辑值的形状及来源；不能继续声称旧 `BufferId` 对应当前存储 |

例如以后合法地消掉 `t` 的存储，`t` 在高层仍是一个形状为 `[10]` 的逻辑值。它可以被记录为未物化，其消费者直接使用某个计算结果；不能为了避免留下一个没有 buffer 的值，把历史形状一并删除。相反，旧的 `t` 地址和访存追踪必须失效，避免可选 Pass 再使用已经不存在的访问。

形状与 ABI 校验失败是编译错误，不是“这次不融合”。可选分析缺失只让依赖它的优化跳过；合法代码在某个目标上生成失败，则保留明确的目标诊断。资源不足时可以有界地调整 P/Q、降低向量化程度或恢复未融合计划，但不能修改 F 的固定策略。已有独立合法 F 调用产物时可以选择它，并记录 LLVM 路径未完成；损坏 IR 不能包装成回退产物。

## 9. 首版怎样验证这条链路

先由上层框架提供带 external 节点的 ASK IR 与 Triton DSL，让 `N=10` 的 P/F/Q 分别执行，检查 ASK 自有操作的降级、DSL 路由编译、原生 IR 导出、重新生成和执行都经过真实路径。逐阶段断言快照引用、源码参数绑定、语义端口、buffer 视图和实际入口参数一致，并验证 N 在源绑定中存在、在本次物理 ABI 中已经消除，再比较模 `2^32` 的逐位结果；融合和指令级追踪都不是这一步成功的前提。

测试应把逻辑形状与实现形式分开改变：保持 `[10]`，让 P/Q 分别使用标量循环和宽度 4 的尾部掩码；保持元素数，改变已支持的视图 stride；改变输入尺寸或形状规则版本，确认旧快照及缓存不会命中。再构造错误的参数重排、隐藏参数缺失、错误分配大小和过期追踪，检查错误出现于对应阶段。

marker 测试比较插入前后的计算结果和存储行为，并确认最终可执行 IR 不含 marker 调用。追踪缺失时应仍可导入和执行；追踪过期时只能丢弃相关分析。异步测试则检查中间 buffer 在最后一次访问完成前不会释放。示例与验收组织见[示例与验证](04-示例与验证.md)。
