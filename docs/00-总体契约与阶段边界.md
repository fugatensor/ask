# 一次编译怎样经过 A、B、C

[返回顶层设计](核心思想.md#ask-architecture) · [文档索引](README.md)

下面从驱动程序的角度说明一次编译。函数名是设计伪代码；核心对象的详细字段分别在对应阶段和[接入 API](08-第三方LLIR接入API.md)中定义。

## 1. 先区分两种入口

图入口接收上层框架已生成的基础 ASK IR、其中 external 区域关联的第三方 DSL、输入特化、数值规则和目标。框架侧先完成自己的 IR 到 ASK IR 的转换。A 层检查 ASK IR，补全形状和读写顺序，再产生执行分区；B 层才按 external 的实现引用将 DSL 交给指定编译器。具体输入见[ASK IR 结构](ask-ir/00-结构类型与操作.md)。首版形状在编译时确定，数据相关的图级控制由调用方处理。

低层工具入口接收已经导出的原生 LLVM IR。用户可以只解析、检查和保存它，不必创建 `SemanticModule`，也可以附语义引用检查端口绑定。图编译主入口仍要求上层提供 ASK IR 及 external 对应的 DSL；复用已有编译产物时，要核对它与这份实现记录及固定配置一致。

两种入口在 B 层汇合。上游用没用 MLIR，不改变 B/C 层接收的是 `llvm::Module` 这一点。

## 2. A 层先给出正常执行方案

```text
graph = load_and_verify_ask_ir(request.ask_ir, registry_snapshot)
shapes = infer_and_freeze_shapes(graph, request.input_specialization)
plan = build_execution_partition(graph)
if request.enables("fusion"):
    plan.candidates = propose_fusion_candidates(graph)
```

`graph` 是 `SemanticModule`，保存语义、类型、形状和依赖。`plan` 是 `RegionPlan`，先说明哪些区域分别编译和执行。例如 `P → F → Q` 默认就是 `[P] [F] [Q]`。

融合候选可以重叠，最终执行分区不能让同一个有要求的操作执行两次或漏执行。关闭融合后，候选可以为空，正常分区仍然存在。细节见 [A 层](01-A层高级IR与区域规划.md)。

## 3. B 层取得产物，分别检查表示和调用信息

```text
external = export_or_reuse_external(plan, target)
units = import_external_and_lower_own_regions(plan, external, target)
```

外部导出只使用公开接口。首期实际导出器只有 Triton；第三方回调只需交出产物，由 ASK 完成解析和检查。离线文件也走同一导入函数。

`LoweredBundle` 保存一个区域的低层结果。`representation` 为 `LLVMModule` 或 `CallableArtifact`：前者可以包含普通指令、目标 intrinsic 和 inline asm；后者只提供可调用代码，不提供可改写的实现体。

模块解析成功后，继续检查目标、入口参数、符号依赖和调用方式。下面的结果不能混在一起：

| 检查结果 | 驱动接下来做什么 |
|---|---|
| LLVM IR 无法解析或结构错误 | 返回错误，不把损坏模块送给 Pass |
| 模块已读入，但缺少启动配置或端口绑定 | 可以检查和保存；执行编译前要求补齐 |
| 调用信息齐全，但后端不支持其中的指令或汇编 | 报告代码生成不支持；有独立合法调用产物时可选用它 |
| 模块可生成代码，但某项分析返回未知 | 保留模块，只跳过依赖该结论的变换 |

`invocation` 记录启动与完成方式，是运行时安排任务的依据；可选的 `ExecutionMap` 记录代码内部各执行实例之间的关系，供相应分析使用。`BoundaryMap` 记录访问与高层元素的关系，也可以缺省。后两者由产物的 `trace` 提供或由 ASK 按需计算，不决定一个模块能否读入或原样生成代码。

外部 F 的实现与执行配置在本次处理时固定。需要重新编译以取得同配置 IR，可以按原配置导出；不能为了某项优化改变 F 的布局或启动策略。详细检查见 [B 层](03-B层多源降级与低层归一化.md)。

## 4. C 层按本次配置运行 Pass

```text
current = units
for pass in requested_passes:
    facts = get_required_analyses(pass, current)
    if not pass.preconditions_hold(facts):
        record_skipped(pass, facts.missing)
        continue
    trial = pass.run_on_copy(current, facts)
    if not verify_trial(trial):
        report_transform_error(pass)
        discard(trial)
        continue_or_fail_according_to_error_policy()
    current = commit(trial)
```

`requested_passes` 可以没有任何可选优化，但入口和输出处的必需检查仍要运行。每个 Pass 依据自己要改写的范围决定需要什么信息，不能先给整个模块贴一个“可优化”或“不可优化”标签。

例如一个模块中含有内联 PTX：列举函数和符号不需要解释 PTX 的算法；移动有依赖关系的访存则必须知道相关副作用。未知操作可能影响其他指令，不能只把它本身排除后任意优化周边。

如果启用了融合，才需要 `RegionPlan` 的候选、相关 `BoundaryMap` 和具体证明结果。`FusionDecision` 是这个 Pass 的产物，不再是所有代码生成必须具备的输入。详见 [C 层](04-C层统一处理与可选优化.md)。

## 5. 模块通过检查后直接生成目标代码

```text
validate_invocations(current)
package = generate_link_and_validate(current, target)
```

后端直接从原生 LLVM IR 生成代码，处理受支持的 target intrinsic 和内联汇编；运行时使用入口说明和依赖计划来调用它。

`ExecutablePackage` 保存代码、参数绑定、缓冲区安排、依赖库和完成事件。生成之前缺少信息应明确报出，不能用猜测的 grid 或参数顺序补齐。

某项可选变换导致资源超限时，可以恢复原来已验证的模块并重新生成，次数受预算限制。如果原始代码也无法生成，必须返回错误。细节见[代码生成与运行时](05-代码生成与运行时.md)。

## 6. 保存和修改哪些对象

| 对象 | 何时需要 | 后续谁使用 |
|---|---|---|
| `SemanticModule` | 从图入口编译时 | 类型、效果及图级分析 |
| `RegionPlan` | 安排多个图区域时 | 导出、降级和执行计划；候选供可选融合使用 |
| `LoweredBundle` | 某个区域降级或导入后 | C 层与后端 |
| `BoundaryMap` | 需要跨层访问分析时 | 依赖该映射的具体 Pass |
| `invocation` | 准备执行某个入口时 | 运行时的参数封送、启动与完成处理 |
| `ExecutionMap` | 需要内部执行关系时 | 依赖实例、顺序和同步分析的 Pass |
| `TargetProfile` | 检查和生成具体目标代码时 | B/C 层、后端与加载器 |
| `ExecutablePackage` | 代码生成完成后 | 运行时 |

稳定 ID 说明来源，revision 说明当前版本。修改代码或链接模块后，相关参数和指令引用可能改变，已有分析要更新或失效。没有追踪表是正常状态；使用过期追踪表是错误。

缓存保存 IR、调用说明及已有分析的版本和内容摘要，不拼接不同次编译的文件，也不序列化进程内 LLVM 对象指针。实现组织见[工程组织与验证](06-工程组织与验证.md)，逐步验收见[实施路线](07-实施路线与端到端示例.md)。
