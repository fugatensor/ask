# 工程组织：把一次编译跑完，并能查出哪里出错

[返回顶层设计：工程约束](核心思想.md#ask-engineering) · [文档索引](README.md)

本文说明准备怎样组织代码和测试，目录与工具名称均为设计草案。继续用 `P: t=x+1 → F: u=t*2 → Q: y=u+3` 这条 i32 模 2^32 计算链；首期 F 只接 Triton，先跑通它与 ASK 的兼容流程。

## 1. 编译驱动拿到请求后，先固定这次用什么

一次请求包括框架生成的基础 ASK IR、external 关联的第三方 DSL、具体输入形状、数值规则和目标。框架的其他 IR 在提交前已经转成 ASK IR。驱动还要固定操作注册表、适配器版本和 Pass 配置。否则，同一请求可能前半段使用旧操作定义，后半段却查到刚注册的新定义，后面的结果便无法复现。

接下来调用 A 层检查图，得到 `SemanticModule` 和 `RegionPlan`。图级运行时分支由上层框架处理，不进入这条流水线。计划先写清 `[P] [F] [Q]` 怎样通过 t/u 连接，谁要等谁完成；关闭全部可选优化时，也要能沿这份计划编译和执行。

进入 B 层后，Triton 适配器通过 `export(request) -> LLIRArtifact` 交出原生 LLVM IR 和调用所需信息。B 层解析成 `llvm::Module`，检查 IR、目标、数据布局和入口，再把 A 层的输入输出端口绑定到参数。P/Q 也降到原生 LLVM IR，但此时不必为了融合改成 F 的执行方式。公开接口不能交出合法原生 IR 时，不能宣称这次 LLIR 接入成功，也不能转向私有钩子或源码补丁；若另有可调用产物，可以保留独立调用路径。

B 层检查通过后，C 层在原生 LLVM 模块上运行本次启用的 Pass。检查入口、整理符号、链接依赖，不要求先生成完整的元素追踪；融合若启用，再枚举候选并请求它需要的分析。inline PTX 和目标 intrinsic 可以留在模块里，目标后端负责处理它们。后端完成代码生成，确认参数布局、资源和启动方式可用后，驱动才发布 `ExecutablePackage`。

这样，一份产物可以已被导入，却因后端不支持某条目标指令而不能执行；也可以已经执行成功，却因分析不清某次写入而不能融合。驱动分别报告这些结果。可选优化失败时保留原来的合法分组，不要求每次提前生成两套机器码。F 的已选分块、布局和启动配置不进入融合搜索；需要配合时只调整 P/Q。

## 2. 按这条调用顺序分代码

A 层用 MLIR 的 `ask` dialect 表达图，具体定义见[ASK IR](ask-ir/README.md)；B 层接收的是原生 `llvm::Module`，C 层使用 LLVM New Pass Manager。下面的目录跟着实际调用路径走；语言绑定只调用公开入口，不直接修改某个 Pass 的内部状态。

```text
bindings/                 # 必需的 nanobind 绑定，只调用公开编译/运行时接口
python/ask/               # 框架构图、设备张量与编译 API
include/ask/               # 构图、编译、第三方接入的公开接口
lib/IR/                   # A 层操作、类型和图检查
lib/Import/               # 原生 LLVM IR 解析、校验和入口绑定
lib/Analysis/             # 图分析，以及 Pass 按需请求的 LLVM 分析
lib/Planning/             # 正常执行分组；启用融合时才生成候选
lib/Provenance/           # 身份、可选 BoundaryMap、版本与引用更新
lib/Lowering/             # ASK 自己的 P/Q 降到原生 LLVM IR
lib/Passes/               # C 层统一处理、依赖声明和分析失效
lib/Passes/Fusion/        # 可选的边界检查与融合变换
lib/Codegen/              # 选择后端、收集代码、打包
lib/Runtime/              # 校验参数、加载代码、管理缓冲区与完成事件
adapters/triton/          # 首期唯一真实插件，负责从公开接口导出
backends/                 # 目标 intrinsic/inline asm、代码生成和启动
tests/fixtures/adapters/  # 模拟不同返回结果，测试第三方接入接口
```

A 层只保存 F 的语义和实现引用，不链接 Triton 的内部类型。ASK 核心处理统一的原生 LLVM IR 和调用说明，不按 `TritonAdapter` 的私有字段分支。适配器只负责导出；比如产物里的 PTX 汇编是否合法、能否为目标生成代码，由目标后端回答，不能让每个来源适配器各写一套。交换内容见[第三方 LLIR 接入 API](08-第三方LLIR接入API.md)。

其他外部编译器暂不写真实插件。测试夹具可以模拟“只有调用产物”“缺少映射”“格式版本不匹配”等情况，用来检查 API 是否容易接入和是否正确拒绝错误输入；它们不能计入已支持的编译器名单。

上述目录不必全部参与每次构建。`ASK_THIRD_PARTY_COMPILERS=none|all|名称列表` 决定第三方适配器集合，`ASK_TARGET_BACKENDS` 独立决定目标后端。未选中的适配器不创建 target，也不查找或安装其依赖；核心始终保留 LLVM/MLIR 和基础 Python 绑定；`none` 不表示只构建 C++。具体配置、安装与 CI 规则见[构建设计](09-构建与可选编译器.md)。

运行时接到的是代码、参数布局和调用顺序，不接编译期 `RegionPlan` 或分析缓存。这样执行已经编译好的图，不必重新加载 Triton 或运行融合分析。调试工具可分别暴露单个 Pass、完整编译及产物执行入口，便于缩小问题范围。

## 3. 每个 Pass 都要交代自己改了什么

考虑一个具体变换：P 原来一次处理 4 个元素，现在改成 8 个。它读的是 P 的循环和类型信息，写的是 P 的循环、向量类型、访存与掩码。它不会改 F，但会让原有 P→F 对应关系失效。

因此每个 Pass 要声明需要的分析和运行范围，并通过 LLVM 的 `PreservedAnalyses` 告诉后续哪些结果还可用。对于已经建立的 `BoundaryMap`，只有三种选择：没有影响所以保留；已经重算所以更新；还没重算所以使其失效。没有任何后续 Pass 请求它时，不必为了每次改写重建完整追踪。不能因为“计算结果应该没变”就保留全部分析。

函数 Pass 只在其拥有的范围内修改代码；涉及多个函数、入口签名或模块级表的变换，放到能管理这些对象的模块级 Pass。LLVM 已提供分析缓存和失效机制，ASK 要补的是跨区域表与函数分析之间的依赖，不能只因表放在模块层就把它永久保留。[LLVM New Pass Manager](https://llvm.org/docs/NewPassManager.html)

Pass 的范围也决定它怎样处理不认识的指令。入口签名检查可以不解释函数体里的 inline asm；删除 t 的 store 却必须排除那段汇编读取 t 的可能。缺少这些信息，只停下依赖它的改写；若未知行为可能影响整个候选，就不能声称跳过那条指令后其余部分仍可融合。

## 4. 用版本把旧分析挡在下一步之前

上面的向量化完成后，P 的 IR 版本递增。P 的访问分析、P→F 的元素对应、掩码覆盖以及依赖它们的融合结论，都不能继续使用。若 Pass 已重新生成访问关系，可以直接交出新结果；否则下一次查询触发重算。

其他改动也按实际用途处理。改 GEP 索引要重查地址、别名和相关内存依赖；改控制流要检查支配、循环和路径条件；改变整数溢出或浮点设置要重新检查变换是否合法。只改打印名称且没有影响任何引用时，才有理由保留原分析。LLVM 自带的别名、支配和 MemorySSA 分析，与 ASK 的索引和访问映射都需要纳入失效处理。

克隆、内联和链接还会改变对象身份。能够取得旧 `Value` 到新 `Value` 的对应表时，用它重新绑定引用；没有完整对应表时，丢弃受影响的可选映射，再从当前模块分析。链接后函数可能改名或合并，不能拿旧函数名直接认定找到了同一段实现。细节见[跨层追踪](02-跨层身份与追踪契约.md)。

分析缓存的键需要包含分析名称、输入快照及 revision、目标和相关假设。涉及 F 的结果还要绑定 F 的固定配置。不能只用 `RegionId`：同一个区域在重降级前后仍叫 P，内容却已经不同。

失效与未知分开记录。失效表示“这份答案针对旧代码，不能读”；未知表示“已经分析当前代码，但答不出来”。前者在再次请求时重算，后者使依赖该答案的变换停止。两者都不自动使原本合法的 LLVM 模块失去执行资格。

## 5. 同时改多份数据时，检查完再替换原件

以可选融合 Pass 为例。它准备把 F 对 t 的 load 换成 P 的 SSA 结果时，先在隔离副本或受控事务里修改。随后可能还要删 t 的 store、调整参数和更新边界表，这些改动不能一条条发布给其他阶段。其他会同时改变代码与调用计划的 Pass 也按同一方式处理。

提交之前按顺序检查三件事。首先，新 IR 的类型、定义使用和控制流仍合法；然后，所有端口、buffer 和映射都指向新代码，最终分区没有漏算或重复执行 F；最后，重新确认删除访存所用的前提仍成立，例如没有忘掉图外还要返回 t。

LLVM 的 `verifyModule` 只能解决第一类问题。一个类型正确的函数仍可能把 `t[i+1]` 当成 `t[i]`，所以它通过不代表融合正确；它也不保证后端支持模块里的所有目标指令。语义检查与实际代码生成各有自己的结果。

检查通过，才一起发布新 IR、已存在的映射、调用计划和版本。失败则丢弃这次改动，恢复原来的合法分组。若直到代码生成才发现优化版本不可用，也要保留回到原分组的输入。开发时可以每个 Pass 后都保存快照；正常运行至少在导入、跨模块变换提交和产物发布前检查，不能让调试开关关闭必需检查。

## 6. 再处理并行、缓存和编译时间

有了明确的所有权后，才能并行。互不依赖的区域可以同时降级，各自持有 `LLVMContext`、模块和 Pass 临时状态，不能让两个线程同时改同一个模块。只有启用需要配合 F 的优化时，相应 P/Q 版本才要等 F 的执行信息固定后生成。适配器若不是线程安全的，驱动就串行调用它，而不是假定多个实例能够共享内部缓存。

首期将 Triton 编译放进独立 Python 工作进程，隔离工具链故障以及 LLVM/MLIR 依赖版本。框架提交的 DSL 先整理成 worker 可解析的源码包；进程间传递源码、文本 IR 或 bitcode 及有版本号的说明，不能传 C++ 对象、Python callable 或裸指针。进程隔离只解决加载和故障影响，不会让不同版本的 IR 自动兼容；首期锁定经过整链测试的工具链组合，导入时仍检查版本、目标和数据布局。

持久缓存与分析缓存分开。复用机器码时，键至少覆盖图内容、具体形状、数值设置、目标、编译流水线版本、Triton/适配器版本和 F 的配置。缓存文件先写到临时位置，全部验证成功后再发布；超时、取消和进程退出留下的半成品不能被下一次请求命中。

可选优化每次重降级还要记录已尝试的 P/Q 配置。比如宽度 4 已经失败，不能绕一圈又原样尝试。限制候选数量、分析步数、重降级次数和外部编译时间；优化预算耗尽时选已有合法分组。若导出或必需代码生成本身超时，且没有合法实现，则返回编译失败，不能把所有失败都写成“跳过优化”。F 的策略不进入这项搜索。

## 7. 失败信息要指向一条具体边

假设 N=8，当前 P 的向量 lane k 产生 `t[4*q+k]`，F 同一 lane 却读取 `t[4*q+3-k]`，并把结果写回对应逻辑位置。两边计算的元素集合相同，但 lane 顺序相反。当前方案若只支持同 lane 直接连接，又没有生成 lane 重排，就应拒绝这次直通。

诊断可以直接写成：

```text
P.out → F.in：当前方案不做 SSA 直通
P 的 lane k 提供 t[4*q+k]
F 的 lane k 需要 t[4*q+3-k]
缺少把两个 lane 对齐的变换；F 的顺序保持不变
本次保留 P→F 边界，可另行尝试调整 P
```

这条信息说明为什么没有优化，属于 remark。可选映射里的悬空引用要报告并使该映射不可用；输入形状矛盾、必需参数绑定错误、没有目标可执行实现，则会阻止编译或执行。不要都归到“未命中模式”，否则用户不知道是少做了一项优化，还是程序根本无法运行。

诊断旁边附 LLVM 模块、函数及当前版本，能够追溯时再附 A 层的源操作和端口，同时记录 Triton 与适配器版本。导出的模块没有完整调试信息时，也应能定位到所保存快照中的指令；不能为了打印一条错误要求全部元素映射先建立。机器可读记录使用同样的内容，避免日志与 API 返回不同解释。

需要复现时，保存这一阶段的最小 IR、映射、目标、工具链版本和 Pass 参数。能用固定种子的输入生成器重现，就保存种子，不必默认记录真实张量内容。

## 8. 用测试分别堵住这些错误

ASK IR 的结构、标记、形状规则和降级交接先按[专项示例与验证](ask-ir/04-示例与验证.md)检查：框架提交完整的 ASK IR 与 DSL 引用，形状在编译外部 DSL 前冻结，删除纯标记后形状和调用关系仍然完整。AST/文本格式检查与设备执行验证分开记录。

先把接入跑通与优化正确分成两组测试。否则，融合分析缺一项就会被误报为 Triton 接入失败，而一个 mock 模块上融合成功又容易被写成真实工具链已支持。

接入先用 API 夹具检查输入处理：非法 LLVM IR 应被解析或 verifier 拒绝；错误的入口、目标和参数绑定应在执行前报错；没有 `BoundaryMap` 的合法模块应继续进入代码生成。再放入保留 inline asm 或目标 intrinsic 的样例，检查导入不会因 ASK 不理解其高层含义而删除它。夹具可以稳定制造这些情况，但不能证明 Triton 实际能导出相同格式。

因此首期必须有真实 Triton 的整链测试：锁定版本和公开导出点，编译 F，导入实际原生 LLVM IR，完成 parse/verify 和入口绑定，再由目标后端生成代码，执行 `[P] [F] [Q]` 并检查结果。这条链不要求融合；它验证的是所选 Triton 与 ASK 工具链确实能够交换和执行产物。有 inline PTX 的真实产物还要经过实际后端，不能止步于 LLVM verifier。

之后才测按需追踪。用同一 buffer 的两次写入检查是否误把存储身份当成值身份；用 N=10、宽度 4 检查最后两个有效 lane；改变 GEP 索引、克隆函数或链接模块后故意留下旧 revision，确认旧映射不会被复用。测试原生 LLVM 的 PHI 和循环，检查路径与迭代没有被丢掉。这些小测试可以在没有设备时运行。

再测启用的变换。对允许直通的 P→F 检查相应中间 load/store 被删除；增加 `R(t)` 后检查仍保留 R 要读的写出；插入可能读写 t 的 inline asm 后检查相关改写停止；让 F 写状态后检查顺序没有改变。用 `lit`/`FileCheck` 检查必要特征，不整份冻结无关的 SSA 名称和打印顺序。若称某个真实 Triton 产物支持融合，还须分别运行原分组与融合版本，本例按 i32 位模式逐位相等，包括会溢出的输入。仅夹具通过时，只报告该 Pass 的夹具测试通过。

运行时测试另查缓冲区何时可以释放、依赖事件是否真正等待、执行失败后是否错误重跑有副作用的图。未来加入优化守卫时，再测守卫失败是否在任何受影响操作执行前切换版本。

最后测驱动本身：取消外部编译后缓存中不能出现完整条目；升级适配器版本后不能命中旧产物；分析预算耗尽后不能无限重试；并行请求不能互相覆盖映射。这些错误往往不改变一个单独 Pass 的输出，却会让整个编译过程不可靠。

## 9. 把真实验证结果与性能记录一起留下

没有目标设备的 CI 运行数据结构、原生 LLVM IR 和接口夹具测试，真实 Triton 执行测试则在具备所选目标的任务中运行。未运行要明确标记，不能用夹具测试代替成功状态。报告分别列出“导入通过”“实际执行通过”和“某项优化通过”；依赖升级时重跑真实整链，以及此前宣称支持的可选 Pass，不能只确认包还能安装。

正确性通过后，再比较未融合与融合版本：编译用了多久，尝试了多少候选，最终调用几次，中间 buffer 有多少字节，真实执行耗时如何。IR 中少了 t 的存储，不代表最终机器码一定更快；寄存器不够而产生的额外访存等开销也要计入。测量记录同时写明目标与版本，避免把某次结果说成所有设备的结论。

首期先把导出到执行这条流程在 Triton 上跑通，再依据实际差异调整[第三方接入 API](08-第三方LLIR接入API.md)。可选 Pass 如何进入统一流水线，见 [C 层](04-C层统一处理与可选优化.md)；分期验收见[实施路线](07-实施路线与端到端示例.md)。
