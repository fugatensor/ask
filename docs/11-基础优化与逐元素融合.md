# 基础优化与逐元素融合

[返回顶层设计](核心思想.md#ask-c) · [框架接入](10-上层框架接入.md) · [完整 C 层设计](04-C层统一处理与可选优化.md)

现在有两个可选入口：`--optimize` 处理高层 ASK IR；`--optimize-llir` 处理原生 LLVM IR。普通 `--prepare` 继续只验证图、推导形状和提取标记。

## 1. 高层优化按什么顺序执行

```text
验证图并推导具体形状，提取 ask.mark
  -> 折叠已知常量
  -> 从后向前删除无用的纯计算
  -> 为同形状的逐元素计算建立融合分组
  -> 再次验证，生成当前图的 ShapeSnapshot
```

常量折叠处理 i32 的 `add`、`mul`。两个输入都已知时，使用 32 位整数运算得到结果，溢出保留低 32 位。例如 `2147483647 + 1` 变成 `-2147483648`，不会附加 `nsw` 或 `nuw`。常量通过 `splat` 形成的均匀张量也可折叠：两个均匀张量相加，变成一个标量常量和一次 `splat`，不会在编译器内分配整块张量数据。

死代码消除检查已知纯操作的结果是否还有使用者。没有使用者的 `constant/splat/add/mul` 被删除，再检查其生产者，所以一整条无用链可以一起删除。图输出仍然是使用者。`ask.external` 和语义/实现声明保留；本版不靠外部节点的声明推测是否可以取消一次外部调用。

优化先验证原始图。即使一个错误形状的操作最终没有使用者，也会被报告为输入错误，不会先删除它来绕过验证。

## 2. 融合到底改变了什么

已有的 host 降级会沿单个输出的依赖链生成逐元素表达式，所以 `x -> add -> mul -> y` 原本就不需要物化中间张量。这次新增的分组让多个输出共用一次遍历，并复用共享的中间计算。例如：

```text
t = x + 1
y = t * 2
return t, y
```

未分组时，host 后端为 t 和 y 分别生成一个循环，第二个循环重新读取 x、重新计算 t。分组后生成：

```text
for i in 0 .. N:
    value = x[i] + 1
    t_out[i] = value
    y_out[i] = value * 2
```

两个输出仍有各自的存储，调用 ABI 不变。一个循环内的 LLVM SSA 值会复用；缓存不会越过迭代边界。零元素输出不产生访问，零维 tensor 按一个元素处理。标量输出保持独立。

分组只接受具体形状完全相同的纯 `splat/add/mul`，至少包含两个张量操作。标量纯计算可以夹在组内。遇到不同形状、外部节点或不支持的操作，就结束当前分组。相同元素总数但不同形状也不会合并。

计划写成操作上的 `ask.fusion_group` 字符串属性；原操作、SSA 连线和类型仍可直接检查。host 后端重新核对分组，再合并同组输出。这个实现依赖已有 ABI：输出互不重叠，且不与输入重叠。它没有硬件型号、线程块大小或模板匹配规则。跨 Triton 内核的融合仍待实现。

`optimization.fusion_groups` 报告高层计划。实际代码生成结果看 `abi.lowering`：`loop_count` 是生成的循环数量，`unfused_output_loop_count` 是逐输出生成时的数量，`fused_output_groups` 是实际合并的多输出组数，`input_load_count` 是生成的输入 load 指令数量。`statistics_stage="host_lowering"` 表明它们记录 host 降级刚完成时的结构；后续 LLVM Pass 可能继续改变代码，不能把这些数值当作当前 LLVM 分析或耗时测量。

## 3. 标记、逻辑身份和形状怎样保留

折叠一个操作时，结果继续使用原来的 `ask.id` 和 `ask.value_id`。张量折叠需要的新标量使用独立 ID。死代码消除会真正移除不再需要的逻辑值；标记不充当保活引用。

报告保存优化前的 `input_shape_snapshot` 和 `input_markers`，当前 `shape_snapshot` 则从优化后的图重新生成。标记记录增加状态：

| 状态 | 含义 |
|---|---|
| `exact` | 当前高层逻辑值及引用端口未被改写 |
| `rewritten` | 值仍存在，但定义或引用端口经过常量折叠 |
| `eliminated` | 对应值或端口已被死代码消除 |

这里的 `exact` 只针对高层图，不表示已经恢复了外部 LLVM 指令中的位置。消除后的标记保留为历史记录，不能拿来定位当前 SSA。

常量折叠或死代码消除改变逻辑图后，同时更新 semantic revision 与 IR revision，再生成新快照。仅添加、删除融合分组时只更新 IR revision，逻辑形状快照保持不变。对没有更多可优化内容的图重复运行，不继续增加版本号。

## 4. Python、CLI 和 C++ 怎样调用

```python
optimized = compiler.optimize(module)
print(optimized.ir)
print(optimized.report["optimization"])

# 单独关闭某项。
optimized = compiler.optimize(module, fuse_elementwise=False)
```

三个 Python 选项分别是 `fold_constants`、`eliminate_dead_code`、`fuse_elementwise`，默认均为 `True`。关闭融合也会清除输入 IR 上已有的融合计划。

可运行例子见 [optimize_frontend.py](../examples/optimize_frontend.py)。其中有可折叠常量、一条带标记的无用链，以及共享中间值的两个输出：

```bash
PYTHONPATH=python python3 examples/optimize_frontend.py --emit-only > build/optimization-input.mlir
build/core/bin/ask-opt build/optimization-input.mlir --optimize \
  -o build/optimized.mlir --report-json build/optimization.json
build/core/bin/ask-opt build/optimization-input.mlir --optimize --emit-llvm \
  -o build/fused.ll --report-json build/fused.json
build/core/bin/ask-opt build/optimization-input.mlir --optimize --no-fusion --emit-llvm \
  -o build/unfused.ll --report-json build/unfused.json
```

CLI 还提供 `--no-constant-fold` 和 `--no-dce`。这些开关必须与 `--optimize` 一起使用。`--emit-object` 同样可以接在高层优化后，用目标文件做数值对照。

C++ 调用 [optimizeModule](../include/ask/Transforms/Optimize.h)，配置放在 `OptimizationOptions` 中。接口会修改传入的 Module；需要回退时，像现有 C++ 示例一样先复制模块，成功后再接收结果。安装后的 `ask-frontend-example --optimize` 会走这个入口。

## 5. 原生 LLVM IR 的基础清理

```bash
build/core/bin/ask-opt build/fused.ll --optimize-llir \
  -o build/cleaned.ll --report-json build/llvm-optimization.json
```

此入口先用 LLVM reader 和 verifier 检查输入，再通过 LLVM 新 Pass Manager 运行 `InstCombine`、`SimplifyCFG`、`ADCE`。它们处理常量表达式、可简化的指令和控制流，以及不影响结果的死指令。优化后再次验证模块，并核对目标信息和外部函数 ABI。`optnone` 函数跳过。

这一流水线不选择 O2/O3，不启用函数内联、向量化或跨内核融合。标准库函数名推断也被关闭：不能仅凭一个外部函数叫 `strlen` 就假定它具有宿主 libc 的语义；显式 LLVM intrinsic 仍可优化。数值规则与副作用由输入 LLVM IR 的属性决定：不能把带副作用的 asm、volatile 访问或未知效果调用当成普通纯表达式删除，也不从 PTX 字符串猜访存行为。

模块级 `!ask.abi` 和 `!ask.shape_snapshot` 保留。已有的 ASK 指令定位附件，以及模块、函数和全局对象上已知的追踪/BoundaryMap 元数据会失效；未知的 ASK 顶层元数据会在报告中列为未验证。调用方放在模块外面的低层映射也必须同步作废。LLVM 自身的目标和控制流元数据由各 Pass 按 LLVM 规则处理。

C++ 入口见 [optimizeLLVMIR](../include/ask/LLIR/Optimize.h)。导出外部 DSL 与运行这个优化是两个明确步骤：正常的 Triton 导出仍保存原始 IR；只有显式请求时才改写其 LLVM 模块。

## 6. 怎样验证

测试同时检查 IR 结构和实际执行结果：常量折叠后的 i32 位模式、带标记的死链、外部节点保留、快照版本、重复运行、不同形状的分组边界，以及优化前后目标文件的输出。多输出例子还核对循环从两个变为一个，共享的输入 load 和加法只生成一次。

原生 LLVM 测试另外检查常量分支消除、volatile 与 side-effect asm 保留、目标和 ABI 元数据保留，并编译优化前后的 LLVM 文件作数值对照。测试不以“文件变短”代替结果正确。
