# Rin 成本与验证价值评估

<a id="decision"></a>

## 结论

对 ASK 当前三条固定数值约束，生产准备阶段采用通用 Rin 推理的成本偏高。专用校验原型保留相同验收条件、失败诊断和缓存，32 步真实计划准备从 568.752 μs 降到 28.457 μs，512 步从 9.987 ms 降到 0.437 ms。建议生产路径采用专用静态校验，将 Rin 用于分配与调度算法开发阶段的独立验证及候选规则实验。

该调整可保持现有计划验收接口和用户 API，生产维持单一校验路径。对长期复用的已准备计划，Rin 已经退出执行循环；本次主要收益发生在新计划准备和首次执行。

本次比较当前 Rin 与一个执行相同计划约束的专用 C++ 校验器，衡量通用推理的额外成本。ASK 基线为 `2ff8c54`，Rin 基线为 `218caf3`。生产代码、依赖锁和安装 SDK 保持当前版本；专用校验器与实验 Runtime 放在独立临时目录中。

两条路径都验证索引、单一生产者、公开端口、完整槽位映射、读取可用性、容量及严格生命周期分离，保留相同完整键和成功缓存。专用校验器从原始计划计算产生/使用边界，直接比较数值，收集全部失败目标；Rin 路径构造事实与目标，再执行三条固定规则。

<a id="method"></a>

## 测量与正确性

环境为 Intel Xeon E5-2696 v4、WSL2、GCC 14.2.0，C++17、`-O3 -DNDEBUG`；物理 GPU 为 NVIDIA RTX 3080。计时使用标准分配器，堆分配另起进程统计请求字节、峰值存活字节和保留字节。

校验矩阵按链式、宽图、跳跃连接 × 4/32/128/512 步 × 64/4096 B 基础字节参数 × 合法/非法输入生成。新键、内部校验、缓存命中及键构造分别计时；Rin 另测证据构造与已有证据的证明，共 336 个配置。其中 288 个对照配置各取 31 对交替样本，48 个 Rin 分层配置各取 31 个样本，均预热 5 次。内存另起进程，每配置预热 5 次后统计 1 次。所有计时配置均得到预期的 `PASS` 或 `FAIL`；新键阶段在计时前同时递增缓冲区大小和槽位容量，保持约束关系。

真实 Runtime 对照复用生产构建的同一份 `CUDA.cpp` 和 `CUBLASLt.cpp` 目标文件，只替换链接的计划校验静态库。两个版本在独立进程运行，交替次序，共 21 对进程。链/宽图 × 4/32/128/512 步分别测新计划准备、命中证明缓存的准备、准备到首次 GPU 完成，以及已准备 Graph 的热提交到完成。每个 kernel 对四个 i32 元素加一，逐次验证结果。

Runtime 新/热准备和首次完成各预热 2 次，热提交预热 3 次；新/热准备各取 7 个样本，准备到首次完成取 5 个，热提交取 21 个。汇总采用 21 对进程内中位数的中位数。context 创建、kernel 加载与调用参数生成位于计时之外；首次完成包含工作区分配和 Graph 构造，公开输入输出的分配及数据传输位于计时之外。新键测量在计时前同时改变缓冲区大小与槽位容量，维持合法关系。

独立 oracle 按每个缓冲区的产生/使用事件以及同槽所有区间对判定合法性：672 个正交组合、2,400 个确定性随机 DAG/映射、648 个结构与生命周期变体、6 个同一步多输出场景，共 3,726 份计划。两条路径对 1,545 个合法、2,181 个非法计划的结果与诊断完全一致。该矩阵和另 31 个规模边界场景均通过 ASan/UBSan。

实验 Runtime 另通过现有 `ask-runtime`、`ask-matmul` 两个物理 GPU 套件，包含 360 组矩阵乘法。方法、编译源哈希及独立验证摘要见[验证记录](assets/Rin对照验证记录.json)。

## 成本结果

下表为合法链式计划的中位数，单位为 μs，校验使用 64 B 基础参数。完整校验包含键构造、查询成功缓存、校验和写入缓存；真实准备另外包含 Runtime 端口与 ABI 检查、槽位分配及参数布局准备。

| 步数 | 完整校验：Rin | 完整校验：专用 | 真实准备：Rin | 真实准备：专用 |
| ---: | ---: | ---: | ---: | ---: |
| 4 | 68.630 | 2.394 | 76.621 | 4.574 |
| 32 | 544.965 | 7.311 | 568.752 | 28.457 |
| 128 | 2,269.360 | 19.667 | 2,349.350 | 107.245 |
| 512 | 9,233.810 | 78.474 | 9,987.160 | 437.301 |

32 步完整校验中的分层测量为：证据构造 75.434 μs，已有证据的 Rin 推理 439.071 μs；专用核心校验为 2.219 μs。分层分别采样，数值不作严格相加。主要成本来自关系事实的构造、索引和通用匹配。

同一物理 GPU、相同 Graph 节点与槽位映射的结果如下，单位为 μs：

| 步数 | 准备至首次完成：Rin | 准备至首次完成：专用 | 热提交至完成：Rin | 热提交至完成：专用 |
| ---: | ---: | ---: | ---: | ---: |
| 32 | 871.278 | 299.870 | 75.480 | 75.486 |
| 128 | 3,147.780 | 838.684 | 169.266 | 168.662 |
| 512 | 12,831.800 | 3,071.360 | 537.710 | 539.415 |

这组四元素微型 kernel 用于观察框架成本，实际算术工作很小。32–512 步链的首次完成时间减少 65.6%–76.1%，热完成差异在 0.4% 内。4 步链的热完成为 44.984 → 39.857 μs，其他热控制场景差异较小；两版热执行使用相同目标文件且均不调用证明器，该差异不计为 Rin 求证的收益。全部 32 个 Runtime 场景保留在[测量表](assets/Rin真实运行时对照.csv)。

已准备 Graph 的自有显存相同：四元素链占 64 B（输入、输出、两个内部槽），宽图占 48 B（输入、输出、一个内部槽）。对应分配次数分别为 4 与 3。该口径记录 ASK 请求的自有存储，驱动的分配粒度与 Graph 存储另计。

完整新键校验的主机分配如下，字节数含成功缓存保留的键：

| 步数 | 堆分配次数：Rin → 专用 | 累计请求字节：Rin → 专用 | 峰值存活字节：Rin → 专用 |
| ---: | ---: | ---: | ---: |
| 32 | 2,560 → 26 | 411,048 → 7,104 | 273,656 → 3,976 |
| 512 | 38,500 → 38 | 6,594,296 → 110,912 | 4,371,720 → 61,576 |

成功键保留量一致：32 步为 3,976 B，512 步为 61,576 B。命中缓存的算法和分配量完全相同，32 步计时为 Rin 1.402 μs、专用 1.529 μs；该阶段的计时差异作为控制组结果保留。完整校验矩阵，包括非法输入、缓存和分层计时，见[校验测量表](assets/Rin校验成本对照.csv)。

校验表的 `cold/core/hot/key/evidence/proof` 分别表示完整新键校验、无缓存校验、缓存命中、键构造、证据构造和已有证据的证明；`fault=1/2/3/4` 分别为提前读取、容量不足、生命周期重叠和缺少分配，`0` 为合法输入。`evidence/proof` 仅测 Rin，对照列留空。Runtime 表的 P95 为 21 个进程内中位数的 P95；显存和分配次数仅在 `hot_complete` 行采集，其余行的 `0` 为占位。

<a id="limits"></a>

## 通用推理预算对计划规模的影响

等大小缓冲区的链式与宽图，在 833 步时两版均通过；834 步时 Rin 返回 `UNKNOWN`，专用校验器通过。每步同时读取前一步和跳跃前驱的图，在 714 步时两版通过，715 步时出现同样差异。独立 oracle 确认这些计划合法。

这两组事实闭包分别为 `12n−1` 和 `14n−5`，跨过 Rin 的 10,000 事实上限。当前 ASK 对 `UNKNOWN` 拒绝准备计划。这是通用推理预算造成的接受范围差异，边界场景单独统计；上面的性能矩阵位于两版都完成验证的范围内。

## 值得验证的优化候选

<a id="capacity-slots"></a>

### 容量感知的 GPU 槽位分配

当前 [槽位选择](../lib/Runtime/CUDA.cpp) 找到第一个生命周期结束的槽，再将容量扩大到所需字节。候选策略可比较复用各个空闲槽时的容量增量，优先选择增量最小的槽。现有 Rin 容量和生命周期规则已经能验证这种候选，执行循环仍使用冻结映射。

已独立验证一个四步计划：先同时产生 small 和 large，下一步消费二者形成公开结果，随后产生另一个 large，最后读取它形成公开输出。前两个内部缓冲区的生命周期均为 `[0,1]`，后一个为 `[2,3]`。

small 为 4 KiB、large 为 1 MiB 时，现策略需要两个 1 MiB 槽；容量感知候选使用 4 KiB 与 1 MiB 两个槽，私有工作区减少 **49.8047%**。按两种 small 大小 × 两种 large 大小生成四组，真实调用现有 `checkAllocationPlan`：8 个合法映射通过，8 个容量不足或生命周期重叠变体被拒绝。数据见[槽位候选验证](assets/Rin槽位候选验证.csv)。

这是候选映射与所需容量的验证结果；生产分配器尚未切换。节省来自槽位选择，Rin 提供候选验收。

<a id="host-temporaries"></a>

### CPU 物化临时区复用

[Host 降级](../lib/Lowering/Host.cpp) 将需要物化的张量逐个追加到临时区，再依次物化并计算公开输出。候选优化可依据实际生成的物化与读取顺序计算生命周期，复用整槽；容量、可用性和生命周期分离可以沿用当前规则。

事实必须对应 ScalarEmitter 实际读取的物化值；对齐与地址加法溢出继续由专用数值检查处理。候选收益以生成的工作区字节和执行时间衡量，并核对数值结果；当前临时区已合并为一次 `malloc`，分配次数作为控制指标。

<a id="graph-dependencies"></a>

### CUDA Graph 的必要依赖边

当前 Runtime 将 Graph 节点串成单链，[分区器](../lib/Frontend/Partition.cpp) 已导出数据依赖。候选设计可在准备阶段结合数据依赖与共享槽位冲突建立必要边，使独立分支获得并行机会。

Rin 可表达边的可达关系，验证每次读取晚于生产、每次覆盖晚于旧值的产生与全部读取，并通过每条边上的严格递增序号检查无环。DAG 生命周期需要检查所有旧访问节点与新写入者之间的顺序；现有单 stream 的最后使用序号不足以表达这个条件。完整传递闭包会增加事实数量，采用该方向前应对照专用 DAG 分析的成本。

<a id="scope"></a>

## 验证职责与落地次序

优先评估容量感知槽位策略，其次评估 CPU 临时区复用。两者都产生明确的内存分配候选，验证发生在构建计划或生成代码时。Graph 并行化同时改变调度与内存复用模型，应单独设计和测量。

类型、形状、融合分组和外部签名已有直接的编译期检查。cubin 参数布局来自真实产物；实参设备、地址重叠与对齐来自每次提交；完成事件与工作区可用状态来自 GPU。浮点舍入和复杂索引等值证明则需要算术或位向量语义。这些职责继续由相应的专用检查承担。

另有一项可直接减轻热提交成本的候选：准备时固定公开端口属性和需要比较的端口对，提交时只检查这些实参。目前提交过程反复查找输入成员，并按输出扫描全部逻辑缓冲区。该优化保留实际地址检查，收益来自消除无用扫描。

本次独立验证器、实验 Runtime、测量驱动和临时数据在归档报告后删除，保留测量表与验证结论。
